# M11 · 反向验证的"故障路径"怎么写才不算装饰品

> **触发时机**：写任何"注入故障 → 断言必须变红"的断言时；或发现某条断言"怎么改
> 代码它都绿"时。
> 上级索引：`../INDEX.md` ｜ 相关：**M08**（运行时故障注入）· **M10**（源码扫描断言的盲区）

---

## 一句话

**绿路径与红路径必须检验同一个命题。**

红路径写成"另一个命题"或"某个恰好为真的表达式"，断言就会**永远绿**，而且看起来
像验过了 —— 那比没有反向验证更危险。

---

## 三个层次，从坏到好

### 层次 1：恒真表达式（最常见，也最假）

```dart
// ❌ 判据是"长度不符要抛错"；红路径是"合法输入不抛" ⇒ 恒真
red: () { try { encode(4,4,Uint8List(16)); return true; } catch(_) { return false; } }
```

红路径为 true 只说明"合法输入不抛"，与判据无关。

### 层次 2：同一句代码、不同参数（部分有效）

```dart
// ⚠️ 比层次 1 好：判据函数本身被复用了
red: () => !shouldApply('新译文', currentTranslation: '旧译文')   // 真值只是碰巧
```

参数选得当时能变红，但**换个参数**就可能又绿。判据没有真正被证伪。

### 层次 3：共用判据函数 + 喂不同的实现（正确形态）

```dart
// ✅ 判据只写一次
bool _glyphLevelHolds(MaskPage m) => /* …字形级三条性质… */;

// 绿：喂正确实现
green: () => _glyphLevelHolds(buildMaskPage(img, [rect]));
// 红：喂同类但故意做错的实现
red:   () => _glyphLevelHolds(_rectApproxMask(img, [rect]));   // 矩形近似
```

🔴 **共用判据还不够 —— 喂进去的实现也必须是对的那一个。**
本项目踩过：`_unionCoversBoth` 的绿路径误传了对照实现 `_overwriteUnion`，
于是绿路径也在验那个错误实现，判据自证 ⇒ 假绿。

## 反向验证的四种"故障注入"形态（可靠性递增）

| 形态 | 做法 | 可靠性 |
|---|---|---|
| **删一个键** | 从登记表 / 配置里删掉真实存在的一项 | 🟢 高：判据必红 |
| **换实现** | 写一个同类但故意做错的实现，喂同一判据 | 🟢 高 |
| **对照组** | 拿另一个**确实含有该特征**的文件跑同一条判据 | 🟡 中 |
| **搜不存在的字符串** | 拿一个不存在的标识符去搜 | 🔴 低：证明不了判据非恒真 |

---

## 夹具必须让两种实现**给出不同结果**

这是最容易翻车的地方，而且**翻车时不报错**。

实例（mask 并集断言）：要证"或累积"与"后写覆盖"不同，需要一个夹具让两者结果不同。

| 夹具 | 或累积 vs 覆盖式 | 判据能否分辨 |
|---|---|---|
| 两个 region **强重叠** | **完全相同** | ❌ 抓不到 |
| 两块笔画**完全分离** | **完全相同**（后一个窗口里没有前一个的笔画） | ❌ 抓不到 |
| 笔画分离 + **窗口相交** | 差 96 像素 | ✅ 抓到 |

🔴 连**计数**都可能抓不到：实测两者的 `strokes` 都是 704，**完全相等**
（被清零的像素不参与计数）。⇒ 判据必须是逐像素的。

---

## 判据的方向要**双向**

单向包含会被绕过：

```
只查"并集 ⊇ 每块"  → 覆盖式把第一块清零后，剩下的笔画仍能在某块里找到出处 ⇒ 通过
加上"每块 ⊆ 并集"  → 第一块的笔画不在并集里 ⇒ 拒绝
```

一般形式：断言"集合关系"时，**两个方向都要写**，除非你能说清为什么单向够用。

---

## 红路径只复用判据的**片段** ⇒ 极性会反过来

判据常写成 `A && !B` 的形状（例："调了唯一那份规则 **且** 没有自己内联一份"）。
红路径若只写 `B(坏实现)` —— 也就是判据的**后半个片段** —— 它的真值与判据**相反**：

```dart
// ✅ 判据本体
bool _usesManagedRule(String s) => s.contains('Manager.rule()') && !_inlinesRule(s);

// 绿：喂正确实现                              → true
// ❌ 红：只写片段、喂坏实现                    → true  ⇒ 判据分辨不出 ⇒ 装饰品
() => _inlinesRule(badSource)
// ✅ 红：同一个判据、只换被检查的实现          → false ⇒ 证伪成功
() => _usesManagedRule(badSource)
```

🔴 本项目 2026-10-09 实测：`projects_root_is_the_managed_rule` 上线时就是坏的，
`edit-check` 报 `passed: false | 故障路径=仍绿(装饰品)`。**它一定会被报出来 ——
前提是你真去读那条 FAIL**，而不是把"基线里有 1 条红"当成环境噪声。

⇒ **规矩：红路径逐字复制绿路径的表达式，只把"被检查的源码"换掉。**
不要手写一个"看起来等价"的片段 —— 判据的形状（`&&` / `!` / 括号位置）就是它的
极性，片段化会静默把它翻过来。

---

## 判据本身也会写反

实例：i18n 扫描断言写成

```dart
if (missing.isEmpty) return false;   // ❌ 意图是"扫到东西且都登记"
return true;
```

`missing` 为空（一切正常）时判据返回 **false** —— 与意图**完全相反**，
却因为测试环境恰好有未登记项而"看起来在做事"。

⇒ **判据写完后，用一句自然语言写出它断言的是什么，再对照代码。**

---

## 判据过宽也会失守

实例：`dart:ui` 判据用 `code.contains("dart:ui")`，而 `gray_png.dart` 的**类文档**里
提到了 "dart:ui 需要渲染表面" ⇒ 说明文字被当成依赖。

⇒ 判据要**贴着目标**：`^\s*(import|export)\s+['"]dart:ui['"]`（多行锚），
而不是"这个字符串出现过"。

---

## 夹具本身可能有 bug

实例：`_solid(64, 64, 0xEE)` 被当作灰色，实际写出的是纯蓝 ——
`0xEE >> 16 == 0`、`0xEE >> 8 == 0`、`0xEE & 0xFF == 0xEE` ⇒ `(0, 0, 238)`。

症状是"绿路径莫名失败"，容易让人去改判据。**先怀疑夹具。**

---

## 自查清单

写完一条反向验证断言，逐条问：

- [ ] 红路径检验的是**同一个命题**吗？（不是"另一个表达式恰好为真"）
- [ ] 红路径是**整条判据**吗？（不是判据里被抠出来的一个片段 —— 那会翻极性）
- [ ] 绿、红两路**喂的是同类不同实现**，且绿路喂的是**正确**那个吗？
- [ ] 故障注入用的是上表里可靠性 ≥ 中等的形态吗？
- [ ] **夹具**能让两种实现给出不同结果吗？（我验证过差异吗）
- [ ] 集合类判据**双向**都写了吗？
- [ ] 判据锚得**够紧**吗？（不会命中注释 / 说明文字）
- [ ] 夹具的常量语义对吗？（`0xEE` 当灰色这类）
- [ ] 用一句中文写出判据断言的是什么，对照代码核一遍

## 补：2026-10-09 一轮里我自己写出的 3 条装饰品

三条都不在"故障路径"这一个环节上，而在**故障路径的素材**上 —— 同一类错误：
**喂给判据的那个"故意做错的实现"，其实没有做错判据要看的那件事。**

### (a) 坏实现没带被扫的那个特征

```
判据：判据函数体里不许出现 `comicType`
红路径喂的坏实现：`}) => isLocalType && !isBtProject && chapterCount > 0;`
```

坏实现用的是 `isLocalType`，**根本没有 `comicType`** ⇒ 判据照样成立 ⇒ 仍绿。
"按 comicType 分类"的那版必须**真的写 `comicType == ComicType.local`**。

⇒ 自查项：**坏实现的文本里，判据要找的那个记号真的在吗？**

### (b) "忽略某一项"被写成了"换成另一项"

```
判据：!eligible(isDerivedCard: false, hasLocalPages: false, isFlat: false)
红路径喂的坏实现：=> !isDerivedCard && isFlat      // 对上面这组输入返回 false
```

`eligible` 的真身是 `!isDerivedCard && (hasLocalPages || isFlat)`。
"忽略 `hasLocalPages`" 的正确写法是**把它从合取式里拿掉**（`=> !isDerivedCard`），
那样对该输入返回 **true** ⇒ 判据翻脸。写成 `&& isFlat` 只是**换了个条件**，
恰好对这个输入仍然 false。

⇒ 自查项：**"忽略 X" 的坏实现，对同一组输入的结果真的与真实现相反吗？**
（把它和真实现并排跑一遍那组输入，看是否一 true 一 false。）

### (c) 扫描锚点落在注释里

```
判据：源码里不许出现 `LIKE 'bt_%'`
```
而正确的注释里写的正是"🔴 不要用 `NOT LIKE 'bt_%'`" ⇒ 整文件扫**恒假**。
改扫 `_prefixExclusionWhere` 的**函数体**。

同类：`BtProjectManager.isBtComic` 在主页里是**合法**存在的（「翻译工作室」分区
要的正是工程卡），整文件扫"不许出现"会误伤 ⇒ 只能扫 `_LocalState` **类体**。

⇒ 自查项：**这段文本在注释/相邻合法代码里也会出现吗？** 需要就切片
（`_classBodyOf` / `_methodBodyOf`）—— 见 M10。

### 通用动作

**红路径写完，先单独跑一次 `red()` 看它是不是 false。** 它是 true 就是装饰品，
不用等整批跑完、也不用等 CI。三条都是这一眼就能看出来的。
