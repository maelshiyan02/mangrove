# M09 · Windows 批处理（.bat）的四个陷阱

> **触发时机**：在 Windows 上**写或修改** `.bat` / `.cmd` 脚本**之前**。
> 上级索引：`../INDEX.md` ｜ 相关：`M02`（反向验证）· 项目附录 `A01`（环境通道）

## 为什么值得单独一篇

这四个陷阱的**症状与真因毫无相似之处**：你会看到"不是内部或外部命令"、
"系统找不到指定的路径"、"文件名、目录名或卷标语法不正确"、
或者脚本**静默少跑了几行**。它们全都浪费过一小时以上，
而且排查方向全都指错（会以为是路径错、权限错、依赖没装）。

更要命的是第四条：**脚本"跑了一半"也不会报错退出** —— 构建脚本漏掉中间几步、
日志里只剩最后两行，看起来就像"工具坏了"或"构建很慢"。

## 陷阱 1 · 必须 CRLF

`LF` 换行的 bat 在 cmd.exe 下会被**乱解析**（表现为某一行突然变成未知命令）。

- 很多编辑器 / AI 写文件工具默认写 **LF**。
- 判据：`od -An -c` 看行尾是 `\r \n` 还是裸 `\n`。
- 修法：写完统一转一次
  ```python
  data = open(p,'rb').read()
  if data.count(b'\n') != data.count(b'\r\n'):
      open(p,'wb').write(data.replace(b'\r\n',b'\n').replace(b'\n',b'\r\n'))
  ```

## 陷阱 2 · `rem` 注释里的重定向符照样会被解析

```bat
rem 原因：外层用了 `call x.bat >> build.log 2>&1`  ← 这一行会真的去做重定向
```
cmd 在**识别命令之前**就扫描重定向符，`rem` 挡不住。
⇒ **注释里不要写 `>`、`>>`、`2>&1`、`|`**，改写成文字描述（"the greater-than sign"）。

## 陷阱 3 · 括号块里的括号

```bat
if not "%RC%"=="0" (
  echo === BUILD_FAIL (pub get) ===   ← (pub get) 被当成嵌套命令组
  exit /b 1
)
```
⇒ 块内文本**一律不含 `()`**。最省事的做法是改用 `goto`：

```bat
if not "%RC%"=="0" goto fail_pubget
...
:fail_pubget
echo === BUILD_FAIL pubget rc=%RC% ===
exit /b 1
```

## 陷阱 4 · 非 ASCII（UTF-8 中文）会把一行切成两条伪命令

在 GBK 代码页下，UTF-8 中文字节会被误读，某些字节让 cmd 认为一行已结束
⇒ 下一半变成一条"命令" ⇒ `'?xx' 不是内部或外部命令`。

⇒ **bat 脚本只写 ASCII 注释**。项目约定/原因写进同目录的 `.md`，bat 里只留
"see xxx.md" 一行英文。

## 附赠：两条让诊断变容易的习惯

1. **脚本第一行写一个探针文件**（`echo started %time% > probe.txt`）。
   "脚本到底有没有被执行到"是最该先确认、却最难从症状看出的一件事。
   没有它，"跑得慢"和"根本没启动"完全无法区分。
2. **关键步骤各自重定向到独立日志**（`call tool > step_2.log 2>&1`），
   并回显 `%errorlevel%`。父脚本用 `>>` 捕获子进程输出**在部分场景下是无效的**
   （实测过：子批处理与子进程的 stdout 一个字都进不来）——
   所以**让每一步自己写文件**，别指望外层统一收集。
