# M05 · 验证产物与源码的一致性

> **什么时候读**：构建/打包/热更之后，判断"我改的代码到底生效了没"。
> 上级：`../INDEX.md` ｜ 相关：`M02`（反向验证）

---

## 症状

- 改了代码、重新构建，行为**没有任何变化**。
- 用 `grep` 在产物里搜自己新写的私有符号，搜不到 → 以为"没构建进去"。
- 产物目录里有一份**很旧的残留**，被误当成新产物。

## 规矩

1. 🔴 **不要用 `grep` 私有符号判断代码是否进产物。**
   优化编译（AOT / tree-shaking / minify）会**重命名或内联**私有字段、私有方法与局部变量。
   搜不到 ⇒ **假阴性**，不是证据。
2. **字符串字面量是可靠的锚点。**
   编译通常**保留字面量**：给自己的新代码加一句独特的日志/错误文案（如 `"pipeline-check OK"`），
   再在产物里 `grep` 那个字符串。
3. **时间戳顺序**：`产物 mtime > 源码 mtime`，并且构建日志里有**链接步骤**（而不是 `Up-to-date` / `Nothing to do`）。
4. 🔴 **不要在构建运行途中改源码。**
   构建系统按**启动瞬间的快照**计算依赖图 —— 构建中途的改动不会进这次产物，但会让你以为它进了。
5. **先确认真实产物在哪。**
   很多工程有两三份"看起来像产物"的目录，其中若干是**陈旧残留**。
   **明确写出"判断新代码一律看 `<路径>`"**，并把它写进记忆。
6. **构建工装必须用正确的解释器/环境。**
   用错的解释器 → 工装抛异常 → 外层读到**上一轮的旧日志** → 得到一个假的"构建失败"。

## 反例

- 改了 `studio_page.dart` → `grep _viewportWidth app.so` 无结果 → 误判"没构建进去"（实际只是被重命名）。
- `VeneraX/build/` 是十几天前的残留，被当作新产物拿去验证。

## 检查清单

- [ ] 我验证的是**产物的真实位置**吗？
- [ ] 我用的证据是"字符串字面量 + mtime + 链接步骤"吗？
- [ ] 构建期间有没有动过源码？
- [ ] 工装用的解释器/环境与文档一致吗？
