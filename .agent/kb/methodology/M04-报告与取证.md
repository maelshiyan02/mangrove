# M04 · 报告与取证纪律

> **什么时候读**：写诊断报告、交接文档、结论、issue 描述之前。
> 上级：`../INDEX.md` ｜ 相关：`M03`（静默分歧）

---

## 一句话

**报告的顺序与措辞本身就是结论。** 一个数字看起来正常、成因却是另一回事 —— 这是发生在**人读的报告**里的静默分歧。

## 规矩

1. 🔴 **顺序即诊断：上游先于下游报。**
   若把"结果为空"排在"某环节全失败"**之前**，读者第一眼会去查结果生成器，而真正的断点在更上游。
   正确顺序：**上游失败 → 中间缺失 → 下游无产出**。
2. 🔴 **缺失原因必须报到根因那一层。**
   写"按第一个成立的条件取原因"时，很容易把真实错误藏到第二层。**根因（如"解码失败"）必须成为第一支判断。**
3. **能机器读的痕迹一定要落日志。**
   人只看现象、事后无法复算。例：跑完打一行 JSON 摘要（页数/成功数/失败数/跳过数/开关状态）——
   这是后续任何结论的**唯一凭据**。
4. **结论必须带数字。**
   "基本通过"没有信息量；"94 页中 failures=0、blocks=187、skipped=12"才有。
5. **区分「观测」与「推断」，并把推断标出来。**
   文档里一句未经实测的归因会被后续所有人当作事实继承（本项目就发生过：把"跑不了"归因为"缺模型"，
   实际是缺渲染表面，一年多没人验证）。
6. **不确定就写"未验证"，不要写"应该没问题"。**
7. **给出可复现的命令**，而不是描述"我跑了一下"。
8. **把"走过的弯路"写进报告。**
   弯路的价值常常高于结论 —— 它阻止下一个人重走。

## 报告模板（推荐）

```
结论一句话：
证据（原始输出/日志行/文件路径 + 数字）：
未验证 / 未知：
下一步（可执行命令）：
弯路（如果重来会怎么走）：
```

- [ ] 结论里的每个数字都能复现吗？
