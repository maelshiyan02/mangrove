# M08 · 运行时故障注入（一次构建验证全部断言）

> **什么时候读**：验证成本高到「每条断言都要重新编译/重新部署一次」时；
> 断言数量在涨、而反向验证在拖（越攒越多"未验证"）时。
> 上级：`../INDEX.md` ｜ 相关：`M02`（反向验证的总体纪律）、`M01`（断言设计）

---

## 一句话

**把故障注入从「改源码」搬到「换输入」——同一个判据跑两遍，一次喂对的、一次喂错的。**

## 症状

- `M02` 要求每条断言都被故障打红过，但**每次注入都要重新构建**（本项目：一次 Flutter release 构建
  10~15 分钟）⇒ 50 条断言 = 50 次构建 ⇒ 现实里一定会被跳过，最后攒出一串
  「写了但从未验证」的 `pending`。
- 有人提出「先跳过反向验证，以后补」——**"以后"永远不会来**，而且那些断言会一直冒充已验证。

## 根因

`M02` 默认的注入姿势是**改源码**（把某一行改错 → 重建 → 看断言红不红）。这个姿势把
「验证成本」和「构建成本」绑死了。但断言真正守卫的对象通常不是某一行源码，而是
**一份产物 / 一次输出 / 一个决策结果**。

⇒ 只要把断言写成**「对一个值的判据」**（而不是「对一段过程的检查」），故障就可以在
**运行时**构造，不需要动源码，也就不需要重建。

## 规矩

1. **断言写成纯判据函数** `P(value) -> bool`，被测代码负责产出 `value`。
   不要写成 `P() -> bool` 再在函数内部去读全局状态 —— 那样就没法喂不同的 `value`。
2. **每条断言配一对输入**：`green`（正确输入，`P` 必须为 true）与 `red`（故意做错的输入，
   `P` 必须为 false）。通过条件 = `green() == true && red() == false`。
3. 🔴 **`red()` 仍为 true 就要当场判 FAIL**，并在报告里写明"仍绿(装饰品)"。
   这才是对 `M02`「未检出」那一类记账的自动化版本。
4. **`red` 必须是真的做错，不是换个无关输入。**
   换一个"本来就合法的其它输入"只会证明判据有分辨力，证明不了它守的是哪条性质。
   ⇒ 每条 `red` 都要能回答："它模拟的是哪个具体 bug？"（写进注释。）
5. **两条路径共用同一个 `P`** —— 一旦各写一份，就退化成"两个测试"，再也证明不了
   `P` 本身有分辨力。
6. **探针抛异常时默认判 FAIL**（初值取失败那一侧），不要让"没跑完"伪装成通过。
7. 仍然要满足 `M01` 的**空结果判 FAIL**：一个探针都没定义出来 → FAIL。
8. **这套办法替代不了所有反向验证。**
   它验证的是"判据能分辨"，验证不了"被测代码真的调用了它" —— 后者仍要靠
   `M05`（产物与源码一致性）或至少一次真实的源码级注入兜底。

## 反例

- `red()` 只是把输入换成"另一个正确值" → 判据没被瞄准，`green` 永远绿 ⇒ 假验证。
- 探针抛异常被吞掉、默认值取 true ⇒ 异常路径变成了假绿。
- 把 `green` 和 `red` 写成两个独立的判据函数 ⇒ 只是两个普通测试，失去"反向"的含义。

## 检查清单

- [ ] 每条断言都是「对一个值的判据」吗（而不是对过程的检查）？
- [ ] 每条 `red` 都能说清它模拟的是哪个 bug 吗？
- [ ] `green` / `red` 调用的是**同一个**判据函数吗？
- [ ] 探针抛异常时判 FAIL 吗？
- [ ] 报告里能看出"哪条是装饰品"吗？
- [ ] 有没有至少一次源码级注入（或 `M05` 的一致性检查）兜底"代码真的用上了这个判据"？
