- **验收**：BUILD_OK；reader-ux-check **93/93**；`tools/_p70_inject.py` 3 组各只红一条且 sha256 还原；真实数据模拟 69/69 目录全部命中编号+UUID 两 key、64 个 UUID 待自动并回。

## P71 · 存量重复章节矩阵自愈（P70 验收后 138 格 / 卡顿）

- **现象**：P70 修完蓝标后，用户看到《大公的華麗婚姻騙局》章节列表同一话出现两次、载入很卡、刷新仍提示新增。
- **证据**：`local.db` id=`ngdgdhlhypj` → `chapters` **138 格**（69 编号 + 69 UUID）、`downloadedChapters` **137 条**（P70 蓝标自愈把两套 key 都并了）。截图显示同话号两套写法交替。
- **根因**：P70 只修了**增量**（以后不再翻倍），P69 已写库的 138 格没人清；`LocalComic.fromRow` 读库不做归一；章节网格按 `allVersionKeys` 逐格渲染且每格查一次下载状态 ⇒ 双倍查询 + 双倍布局 = 卡。
- **修复**：`ComicChapters.deduplicatedWithRemap()`（按话号+组+语种判等，`_canonicalCellScore` 选「目录名同形」的编号 key）+ `remapKeys()`（下载 key 保序重写）+ `_migrateDuplicateChapterKeys()`（`init` 与 `restoreFrom` 双接线、幂等、只改 chapters/downloadedChapters）；`mergedWith` 改为先各自 `deduplicated` 再合。
- **验收**：BUILD_OK；reader-ux-check **97/97**（93+4）；`tools/_p71_inject.py` 4 组各只红目标且 sha256 还原；真实数据验算 **138→69 格 / 137→69 条 / 0 孤儿 / 69 个规范 key 全可读话号**。
- **断言坑**：`c.ids.toList() == const [...]` 是 Dart **引用比较**，恒假 —— 首版基线 96/97 由此产生。列表比较必须逐项或 `listEquals`；「从未绿过的断言」会让注入看起来只红目标。
- **构建坑**：`builds/mangrove/mangrove.exe` 的 mtime 必须晚于源码，否则 headless 跑的是旧版（本次先跑出 93 条假基线，核对 mtime 才发现）。
