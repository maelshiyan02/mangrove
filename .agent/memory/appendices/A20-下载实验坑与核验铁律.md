## 1. 三条会让"看起来下完了其实没下完"的判据 bug

### 1.1 没有 manifest 记录 ≠ 完整

```python
# ❌ prev_nodes == 0 时括号恒真 ⇒ 所有旧版残章永远跳过
and (prev_nodes == 0 or len(have) >= prev_nodes)

# ✅ 必须有依据
and prev_nodes > 0 and len(have) >= prev_nodes
```

Ch.2 只有 12 页却活了一个多月，就是这条判据保的。
**副作用（期望行为）**：旧版无 manifest 的章节下次跑会自动判"需重下"。

### 1.2 `--force` 不会清理旧页

清理逻辑写在 `if not args.force:` 里 ⇒ `--force` 跳过整个块。
新旧扩展名算法不同就并存（Ch.49：95 页变 **190 个文件**，阅读器显示 190 页）。
**规则**：`--force` 也必须先走旧页隔离，再下载。

### 1.3 页数少 ≠ 源站缺页

先怀疑 HTTP2 失败（A17 §2）。`saved == nodes 且 pending == [] 且 failures == []` 才算完整。

## 2. 🔴 删除配额：移动替代删除（本机硬约束）

`safe-delete` 守卫**单回合删除 > 50 个文件**要人工确认，触发即
`SAFE_DELETE_BULK_CONFIRM_REQUIRED`，**子进程 rc=1 静默退出**（无 traceback）。

⚠️ 它是**删到一半**才停：Ch.3 从 64 页变 **15 页**，比不删更糟。

| 场景 | ❌ 不要 | ✅ 要 |
|---|---|---|
| 整章重下 | 删旧页 | `shutil.move` 到 `ch_dir/.stale/<时间戳>/` |
| 清理隔离区 | 逐个删 347 个 | **整体 `shutil.move` 目录**（1 次操作） |
| 合并重复扩展名 | 删其一 | 先 md5 比对，再 `os.replace`（覆盖） |
| 批量改名 | `rm` + 重写 | `os.rename`（不写盘、不计数） |

**判据**：任何"批量删"都要先问一句——能不能改成"移动/覆盖/改名"？

> 同源约束：Python 层 `_safe_remove` 也有 50/轮配额（A01 §4），构建本身就会吃掉配额。

## 3. 扩展名必须按 magic 定，不能按 URL 猜

comix 的图片 URL **一律写 `.jpg`，实际返回 WEBP**。按 URL 猜 ⇒ 全库 **877 个**
`.jpg` 里装的是 WEBP 数据。Flutter 解码看 magic，所以**阅读正常、问题被长期掩盖**。

`sniff_image_ext()`（12 字节）：

| magic | 判定 |
|---|---|
| `RIFF` + `WEBP` @8 | webp |
| `FFD8` | jpg |
| `8950 4E47` | png |
| `GIF87a` / `GIF89a` | gif |

### 🔴 改名必须分类，一刀切会把好文件改坏

| 类别 | 本次数量 | 处置 |
|---|---|---|
| 假 `.jpg`（内容是 WEBP） | 877 | 改 `.webp` |
| 真 JPEG（封面 8 + cos写真 1332） | 1,340 | **不动** |

**流程**：先跑只读预检（统计"扩展名→真实格式"矩阵 + 冲突 + 非预期格式）→
人工看分布 → 再改名 → 改名后再统计一遍确认"名实不符 = 0"。

## 4. 判断"是否卡住 / 是否被封"的正确姿势

### 🔴 `ls -t` 不能当进度

并发写入顺序是乱的，**最后落盘的不是页码最大的**。两次误判都源于此：

- "磁盘没变化" → 实际正在写
- "Ch.13 下到 80 页就断/被封" → Ch.12 实际 86 页全在，`080` 只是最后写入

### 唯一可信判据

```python
m = json.load(open('_manifest.json'))[章节目录名]
(m['nodes'], m['saved'], len(m['pending']), len(m['failures']))
```

### 真拦截的三个信号（任一成立才算）

1. `pending` / `failures` 非空
2. 日志出现 `Third-party` / `Just a moment` / `Cloudflare` / `503`
3. 进入 300s 熔断

**三信号全零 = 没被拦**，去找进程/批次调度问题，别怀疑站点。

## 5. 进程管理

- `nohup … &` 在非交互会话里会**被 shell 退出一起带走** ⇒ 用受任务托管的后台，或前台逐章。
- Git Bash `ps -ef` 是 **MSYS 虚拟 PID**，`taskkill` 打不中。要查真实 PID：
  ```powershell
  Get-CimInstance Win32_Process -Filter "Name='py.exe' OR Name='python.exe'" |
    Where-Object { $_.CommandLine -like '*comix_browser_dl*' }
  ```
- 后台跑必加 `-u` / `PYTHONUNBUFFERED=1`（块缓冲会导致日志滞后，A17 §1）。

## 6. `--numbers` 两个陷阱

1. 解析成 **`set`**，顺序由 `chapters.json` 决定 ⇒ **不能用它控优先级**，要分批调用。
2. **永远带 `--group`**：不带会命中该话**所有组**（`--numbers 48` 曾命中 7 个组，建 7 个目录）。

跨组事实：本书 Rokari 到 49 话，**第 50 话只有 Lux Manga**。别假设单组覆盖全书。

## 7. 验收五项（页数够 ≠ 完整）

| # | 检查项 | 判据 |
|---|---|---|
| 1 | 页数 | 逐章 `落盘 == manifest.nodes` |
| 2 | 扩展名 | 章节内**零**非 `.webp` |
| 3 | 页号连续 | 排序后 == `1..N`，无跳号 |
| 4 | 字节完整 | `RIFF` 声明长度 + 8 == 实际大小 |
| 5 | 目录命名 | 匹配 `<话号> [组] [站]`（D1，见 A19） |

只查页数会同时漏掉：截断文件、重复文件、跳号、命名漂移。

### 假警报：小于 1KB 的 webp

487 个 <1KB 文件全在 `扔掉的渣男`（baozimh）—— 640 宽长图切片的边缘（`640x1`、`640x4`）。
**源站特性，不是损坏**。⇒ 小文件要**解码看尺寸**再判，不能按体积一刀切。

### 缺口报告（`comix_gap_report.py`）的误报面

第 4 条判据"无 manifest 却有图"**只对 comix.to 有效**。
baozimh（133 章）、copymanga（UUID 目录）、cos写真（本地导入）本来就不写这种 manifest
⇒ **真缺页只在 comix.to 源**，看报告先按源过滤。

## 8. 提速阶梯（实测，`--restart-each`）

| workers | 单章耗时 | 取链 |
|---|---|---|
| 8（默认） | 238–523s | 75–80s |
| 12 | 142s | 16s |
| 20 | 90s | 43s |
| **28** | **58–190s** | 17–49s |

- **瓶颈在取链（DOM 收集）不在下载** ⇒ 130+ 页的大章节反而更快（132 页 / 58s）。
- `workers=28` 全程 39 章**零失败**，没触发 Cloudflare/503。
- 🔴 提速只能提**单章内并发**，**不能提章间频率**（每章一次文档导航是反爬底线，A07c）。
  章间用 `--gap 20,35` 随机冷却 + `--restart-each` 不复用会话。

## 9. 旁支：构建卡 INSTALL ≠ 构建失败

`mangrove.exe` 被运行中 App 占用时 install 阶段卡住/rc≠0。
**先比对 `app.so` 时间戳与 Dart 源码 mtime** —— `app.so` 比源码新就说明编译早成功了，
重跑时 build 阶段显示 "up-to-date" 是正常的。让用户关掉 App，别重复分析代码。
