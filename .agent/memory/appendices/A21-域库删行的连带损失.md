# A21 · 域库删行的连带损失（history / favorites / works）

> 上级索引：`.agent/memory/MEMORY.md` §1
> 触发时机：要删 `data/data/mangrove.db` 里的 `comics` 行、或把漫画从远端身份转成本地身份之前
> 相关：**A20**（下载坑）、**A19**（目录命名）、**P16 日志**（`local-comic-P16-…-20261024.md` §7）
> 建立：2026-10-24（P16 实际踩了一次，798 条阅读史被误删）

---

## 1. 一句话规则

**删 `comics` 行 = 删这本书的阅读史。** 动手前先数依赖；要保留就先改挂身份，再删旧行。

---

## 2. 为什么

域库（`data/data/mangrove.db`）的从属表全部带 `ON DELETE CASCADE`：

| 表 | 外键 | 删 comics 行的后果 |
|---|---|---|
| `comic_sources` | `comic_id` CASCADE | 来源记录消失（预期） |
| `local_library_items` | `comic_id` CASCADE | 书架条目消失（预期） |
| `chapters` | `comic_id` CASCADE | 章节记录消失（预期） |
| `chapter_sources` | `chapter_id` CASCADE | 来源章节映射消失（预期） |
| `favorites` | `comic_id` CASCADE | **收藏没了** |
| `history_events` | `comic_id` CASCADE | **阅读史全没**（P16 实测 798 条） |

`chapter_id` 那条更阴：`history_events.chapter_id` 是 `ON DELETE SET NULL`，
所以章节重建后历史行**还在**，只是指向空 —— 从条数上看不出来，只有页面上"读了哪章"消失。

这些级联都是**静默**的：`DELETE` 返回 `rowcount=1`，不会告诉你带走了 798 行历史。

---

## 3. 正确顺序（身份迁移场景）

把 `remote:X` 转成 `local:X` 这类操作，**先迁后删**：

```
1. INSERT 新身份（comics / comic_sources / local_library_items）
2. UPDATE history_events SET comic_id = 新 WHERE comic_id = 旧
   UPDATE favorites     SET comic_id = 新 WHERE comic_id = 旧
3. 确认新身份行数 = 旧身份行数（逐一比对，别只看总数）
4. DELETE FROM comics WHERE comic_id = 旧
```

确认不了就**别删**：只把 `comic_sources` 里的旧来源摘掉，comics 行留着当孤儿，
顶多多一行记录，比丢阅读史强得多。

---

## 4. 真要删时的三件套

```bash
# ① 删前数依赖（一条 SQL，别靠印象）
SELECT
  (SELECT COUNT(*) FROM history_events  WHERE comic_id = ?) AS hist,
  (SELECT COUNT(*) FROM favorites       WHERE comic_id = ?) AS favs,
  (SELECT COUNT(*) FROM works           WHERE comic_id = ?) AS works,
  (SELECT COUNT(*) FROM local_library_items WHERE comic_id = ?) AS items;

# ② 整库备份（改库脚本必须自己备份，不靠人记）
py -3.12 -c "import shutil,time; shutil.copy2('data/data/mangrove.db',
  f'data/data/mangrove.db.bak_{time.strftime(\"%Y%m%d_%H%M%S\")}')"

# ③ 删后立刻对账：总数差值必须等于"预期作废的那部分"
```

## 5. 事后怎么发现已经丢了

- `history_events` 总数在两个时间点对不上（P16 是 7132 → 6154）
- 备份库还在：`data/data/mangrove.db.bak_*`，按 `comic_id` 捞回来即可
- 捞回来时注意 `chapter_id`：**能置空就置空**。新旧 `chapter_index` 的排序规则
  往往不同（网络源按站上顺序、本地按话号升序），按序号硬搬会指到别的章上——
  章节粒度信息丢了只是少一点细节，指错章是污染数据

P16 的补救脚本：`tools/_p16_restore_history.py`（`--check` 只读 / `--apply` 执行）。

---

## 6. 一条更宽的边界

域库里 `history_events` / `favorites` 是**用户的**数据，`comics` / `chapters` 是
**程序的**数据。凡是要动程序数据的身份主键，先问一句：
**这会牵到用户数据吗？** 会，就先迁；迁不了，就停手问用户。
