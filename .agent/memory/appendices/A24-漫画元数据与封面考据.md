> 首次建立：2026-10-27（P48 补档，样本《灭门家族的重生者》/ 멸망한 가문의 회귀자）。

## 1. 权威源分层（按可信度，别倒着用）

| 层级 | 要什么 | 去哪拿 | 为什么是它 |
|---|---|---|---|
| ① 官方 API | 韩文原名、连载日、**更新星期**、总话数、三分工 | `comic.naver.com/api/search/all?keyword=<韩文名>` | `publishDescription`（如 `토요웹툰`）是**官方排期**；`communityArtists[].artistTypeList` 是**机器可读的三分工** |
| ② 官方页面 | 各地正版名、排期、进度 | WEBTOON / LINE WEBTOON / 咚漫 / B 站 | 平台自己标的更新日与话数 |
| ③ 聚合 wiki | 多语言别名一次拿全 | `bgm.tv/subject/<id>` | 日/繁/英/非官方四套译名通常都在一行 |
| ④ 二手 wiki | 交叉校验 | anisearch / MAL / 百度百科 | 只用来互证，**不作为唯一依据** |

### 1.1 Naver 三连（最值钱的一步）

```
GET https://comic.naver.com/api/search/all?keyword=<urlencoded 韩文原名>
```

一次拿到：

- `searchWebtoonResult[0].titleId` —— 后续所有查询的钥匙（本例 819946）
- `thumbnailUrl` —— **带 UUID**，封面考据的起点（见 §3）
- `publishDescription` —— `토요웹툰` / `금요웹툰` …＝**官方更新星期**
- `articleTotalCount` + `lastArticleServiceDate` —— 总话数 + 最后更新日
- `synopsis` —— 韩文官方简介（可翻译后作 description）
- `communityArtists[].artistTypeList`：
  - `ARTIST_NOVEL_ORIGIN` → **原著小说作者**
  - `ARTIST_WRITER` → **改编/剧本**
  - `ARTIST_PAINTER` → **作画**
  这套比任何 wiki 的"作者：A,B"都清楚——wiki 经常把三个人混成一串。
- `searchNbooksNovelResult` / `searchNbooksComicResult` —— 分别对应 Naver Series 的
  **小说**与**电子书**条目，能直接给出原著小说话数与收官日（本例小说 500 话）。

`GET /api/article/list?titleId=<id>&page=N` 拿章节清单（每页 20）。注意
`serviceDate` 在新版 API 里常为 `null`，**话数可用、日期别指望**。

### 1.2 三条判据铁律

1. **别用「首发日期」推星期**。2024-01-05 是周五，但官方 `publishDescription` 是
   `토요웹툰`（周六）。首发日与正式排期可以差一天（首周提前上架是常态）。
2. **`매일10시무료` = 22:00 KST**。Naver 的通用标签，看到它就能确认更新时间点，
   不用另找公告。
3. **各地进度必然不同**，一律分别标注。本例（2026-10-27）：
   韩 157 / 简 150 / 繁 133。用一个数字代表"全部正版"是错的。

## 2. 正版渠道的判定（尤其简体≠繁体）

- **简体**：常由一家引进再做渠道分发。本例：北京咚漫娱乐 2024-07-05 首发 →
  分发到 **哔哩哔哩漫画（`manga.bilibili.com/detail/mc<id>`）** 与 **快看漫画**。
  三家标题相同、话数可能不同（B 站页面写 150 话，移动版"全部章节(120)"是**分页**，不是 120 话）。
- **繁体**：看 `webtoons.com/zh-hant/...&title_no=<id>`。LINE WEBTOON 繁中由
  NAVER WEBTOON 直营，**译名可能与简体完全不同**（本例：灭门家族的重生者 → 復仇者羅根）。
- **繁体排期与韩版不同步**：页面标"在週五更新"，但话次上架日期实测落在**周四**
  （2026-10-22 / 10-15 / 10-08…全是周四）。**两个都记**，别二选一：
  > 官方标注周五更新（话次上架日期显示为周四，即周四深夜/周五零点上线）
- 港澳台若无独立代理（直接吃 LINE WEBTOON 繁中），就写"繁中＝LINE WEBTOON，无独立港澳代理"。
  有独立代理才展开写。

## 3. 封面沿革取证（本文最硬的一段）

### 3.1 核心洞察

**Naver 封面 URL 带随机 UUID：`thumbnail_IMAG21_<uuid>.jpg`。换封面必然换 URL。**
所以"URL 序列 + 时间戳"就是封面沿革的直接证据，不需要人肉翻公告。

### 3.2 四步法

```bash
# ① 列全部出现过的封面文件（含首次被抓时间）
curl -x http://127.0.0.1:7890 \
  "https://web.archive.org/cdx/search/cdx?url=image-comic.pstatic.net/webtoon/<titleId>/thumbnail*&output=json&collapse=urlkey&fl=timestamp,original,statuscode"
```

```bash
# ② 页面快照：某天页面上挂的是哪张
curl -x http://127.0.0.1:7890 \
  "https://web.archive.org/cdx/search/cdx?url=comic.naver.com%2Fwebtoon%2Flist%3FtitleId%3D<titleId>&output=json&fl=timestamp&filter=statuscode:200&collapse=digest"
# 再逐快照取 HTML（id_ 取原始版），抽 thumbnail_IMAG21_<uuid>
```

③ **按尺寸分组，只数主视觉**（这是最容易数错的地方）：

| 前缀 | 尺寸 | 用途 |
|---|---|---|
| `IMAG21` | 480×623 | **主视觉封面**（唯一该计入"第 N 张"的） |
| `IMAG19` | 220×202 | 推荐位小方图，画面同主视觉 |
| `IMAG06` | 125×101 | 更小缩略图 |
| `IMAG08` | 217×165 | 移动/横版变体 |

同一画面会同时存在 2–3 个规格 + 带/不带标题字的两种，**md5 全不同**。
所以：**md5 不能当"是否换了封面"的判据** → 必须 ④。

④ **拼 contact sheet 目视确认**（PIL 缩略图并排，标日期），人眼判断"同一张画 vs 新画"。
本例 8 个 UUID 目视为 **3 张真正不同的主视觉**，其余是同画的无字版/小图版。

### 3.3 定日期：把"首抓时间"变成"区间"

- 图片文件首抓时间 = **该封面已上线的最晚时点**（下界不成立，上界成立）
- 前后两个页面快照夹逼 → **闭区间**
- 本例：
  - 第 3 张：2025-09-16 快照仍是第 2 张，2025-09-29 该图文件首见
    ⇒ **2025-09-16 ～ 2025-09-29 之间更换**（有界，可断言）
  - 第 2 张：2025-01-04 图文件首见、2025-01-08 快照确认；但 2024 年的快照抓回来
    只有 1.8KB 重定向空壳 ⇒ **下界缺失，只能写"最晚 2025-01-04 起"**
- 🔴 **无证据的一端如实写"无可靠存档"，绝不编具体日期**。写"最晚/之间"不丢人，
  编一个精确日期被用户发现才致命。

### 3.4 关联线索（可选增强）

- 封面更换常在**周年 / 季播 / 百话纪念**节点。本例第 2 张首见 2025-01-04
  ≈ 开载一周年（2024-01-05），强提示但不作为证据。
- `namu.wiki` 会记 `시즌` 划分，但 Cloudflare 拦（WebFetch 拿不到），别指望。

## 4. 网络通道（实测，照抄即可）

| 目标 | 1393（沙箱代理） | 7890（本机代理） | 直连 |
|---|---|---|---|
| `web.archive.org` CDX | ❌ 502 | ✅ | ❌ 超时 |
| `image-comic.pstatic.net` | ❌ CONNECT 502 | ✅ 200 | ❌ 超时 |
| `comic.naver.com/api/*` | ✅ | ✅ | — |
| `namu.wiki` | Cloudflare 拦 | — | — |

- **Naver 是 SPA**：WebFetch 抓 `comic.naver.com/webtoon/weekday` 只能拿到空壳
  （标题一行"네이버 웹툰"）。**必须走 `/api/`**，不要抓 HTML。
- B 站漫画详情接口是 **POST**（`twerp/comic.v1.Comic/ComicDetail`），GET 返回
  `{"code":"bad_route"}`。
- Wayback 偶发 `SSLError: UNEXPECTED_EOF`，重试 3 次即可；连续失败就隔几分钟再来。

## 5. 落点：写到 App 的哪里

写入 **`data/data/mangrove.db` → `comic_field_overrides`**（KV 覆盖层，见 A18）：
三层合并 `覆盖值 > 网络值 > 兜底`，所以**不会被下一次源刷新冲掉**。

```python
comic_id = f"remote:{sourceKey}:{sourceComicId}"   # 本例 remote:baozi:miemen...
value_json = json.dumps(value, ensure_ascii=False)  # 与 ComicOverrideStore._upsertRow 一致
```

字段分配（`ComicOverrideStore.field*`）：

| 字段 | 放什么 |
|---|---|
| `subtitle` | `멸망한 가문의 회귀자 ／ A Flame Reborn`（原名／官方英文名） |
| `author` | `原著小说 Painkiller ｜ 分镜改编 양평 ｜ 作画 성구` |
| `status` | `连载中 · 韩国 157 话（2026-10-23）` |
| `tags` | 题材 + 更新节奏 + 正版渠道（结构化，每条短） |
| `description` | 完整信息块（原名/别名/三分工/小说/三地正版/封面沿革/简介） |

🔴 **别直接写 `comics.description`**：本作实测该列被程序写成 `第 152 章 - 第 86 页`
（阅读进度），下一次刷新就冲掉。工作台工具：`tools/write_flame_meta.py`。

🔴 **写库前必须**：① App 未运行（否则 sqlite 连接 + 内存缓存双写冲突）；
② 备份 `mangrove.db` 到 `*.bak_p48_meta_<时间戳>`。

## 6. 一次完整跑通的顺序（照这个顺序就不会返工）

1. 韩文原名（用户给的别名也算线索）→ Naver search API → titleId + 三分工 + 排期
2. `article/list` 数总话数 + `lastArticleServiceDate`
3. `searchNbooksNovelResult` 拿原著小说话数与收官日
4. comix.to / MAL / Bangumi 交叉校验英文名与多语言别名
5. 简体：百度百科找引进方 + B 站 `mc` 页 + 快看；繁体：`webtoons.com/zh-hant`
6. 封面：CDX（文件）→ CDX（页面快照）→ 分组（只认 IMAG21）→ contact sheet 目视 → 夹逼区间
7. 写 `comic_field_overrides`（先备份、先确认 App 已关）
8. 把结论连同**证据等级**（确认 / 最晚 / 区间 / 无存档）写进日志与记忆
