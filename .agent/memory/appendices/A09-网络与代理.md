# A09 · 网络与代理（GitHub / 外网）

> **触发时机**：跑任何**需要访问 `github.com` 或外网**的命令**之前**
> （`git push` / `gh` / 拉依赖 / 商务抓取）；**遇到"莫名网络超时"时第一时间**；
> **推送弹出凭据 / 账户选择框时**（§6）。
> 上级索引：`../MEMORY.md` ｜ 相关：`A01`（环境通道；本附录原为其 §7）· `A07`（comix 源要求 WebView 取字节，属另一类网络问题）

## 1. 🔴 核心事实：`github.com` **直连不通**

**实测（2026-10-07）**：

| 路径 | `github.com` | `api.github.com` |
|---|---|---|
| **直连**（剥掉所有 proxy 变量） | ❌ **挂起 20s+ → 超时** | ✅ 200 / 1.35s |
| **经 `http://127.0.0.1:7890`** | ✅ **200 / 8.3s** | ✅ 200 / 0.60s |

- **`127.0.0.1:7890`** 在监听且实测可达 GitHub 全部端点（含 `/login/device` → 302）。
  *推断*（未直接确认进程）：这是 Clash for Windows 的默认**混合端口**（HTTP+SOCKS）。
- ⚠️ **症状极具迷惑性：`api.github.com` 能直连，`github.com` 不能。**
  ⇒ `curl api.github.com` **永远成功**，于是误判「网络没问题」；而真正打 `github.com` 的操作
  （`gh auth login` 的 device flow、`git push`）会**静默挂起**，报错形如
  `read tcp …: wsarecv: A connection attempt failed because the connected party did not properly respond`。
- **浏览器等图形程序不受影响**（自动吃 Windows 系统代理）；**命令行不会读系统代理**
  ⇒ 出现「网页能开 GitHub、终端连不上」这种看似矛盾的现象。

## 2. 已固化的代理配置（2026-10-07，用户选定）

新开的终端**自动带代理**，不必再手动 `set`：

| 位置 | 内容 | 撤销 |
|---|---|---|
| `HKCU\Environment`（`setx`） | `HTTP_PROXY` / `HTTPS_PROXY` = `http://127.0.0.1:7890`；`NO_PROXY=localhost,127.0.0.1,::1` | `reg delete "HKCU\Environment" /v HTTPS_PROXY /f`（HTTP_PROXY、NO_PROXY 各删一次） |
| `~/.gitconfig` | `http.https://github.com.proxy = http://127.0.0.1:7890`（**只作用于 github.com**） | `git config --global --unset http.https://github.com.proxy` |

- ⚠️ 临时手动设置（仅当前窗口）：`set HTTPS_PROXY=http://127.0.0.1:7890`
  （cmd 里**不要加引号**，`set X="v"` 会把引号一并写进值）；PowerShell 用 `$env:HTTPS_PROXY="..."`。
- ⚠️ **`setx` 只对新进程生效** —— 改完必须**关掉当前窗口重开**，旧窗口不会自动获得变量。
- 🔴 **副作用要记住**：代理客户端（7890）没开时，终端里所有 HTTPS 操作都会失败 ——
  **包括本来能直连的 `api.github.com`**。**出现莫名其妙的网络故障时，第一个怀疑这里。**

## 3. 反向验证（两侧都测过，别只测一边）

1. 剥掉全部 proxy 环境变量后 `git ls-remote origin` **仍成功** ⇒ `~/.gitconfig` 那条能**独立生效**。
2. Python `winreg` 读 `HKCU\Environment` ⇒ 三个变量均在。
   ⚠️ **`reg.exe` 被沙箱安全策略禁用**（Program Blacklist），读注册表只能绕道 Python `winreg`。
3. 配置优先级实测：`git push` **不加任何 env 覆盖也成功** ⇒ **git 的 `http.proxy` 压过环境变量**
   （libcurl 显式 `CURLOPT_PROXY` 优先）。

## 4. 🔴 沙箱代理 5486 对 `github.com` 不稳（只影响我，不影响用户）

- 本会话 Bash 工具**自带代理** `HTTPS_PROXY=http://127.0.0.1:5486`（沙箱注入）
  ⇒ **我这边 `git push` / `curl` 成功，不代表用户在 cmd 里也能成功。** 最容易犯的取证错误。
- ⚠️ 但 5486 对 `github.com` **不稳**：实测 `CONNECT tunnel failed, response 502`。
  ⇒ 我推 GitHub 时**主动改用 7890 覆盖**（**四个变量都要覆盖**，libcurl **小写优先**，
  只设大写会被继承的小写 `https_proxy=5486` 顶掉）：
  ```bash
  export HTTPS_PROXY=http://127.0.0.1:7890 HTTP_PROXY=http://127.0.0.1:7890 \
         https_proxy=http://127.0.0.1:7890 http_proxy=http://127.0.0.1:7890
  git push
  ```
  （注：自 §2 写入 gitconfig 后，**git 已自动走 7890**，此覆盖主要用于 `gh` / `curl` 等非 git 工具。）

## 5. 代理客户端**换节点**会不会影响推送？（2026-10-07 问答）

客户端：**Clash for Windows 0.20.16**（ikuuu 订阅）。

**结论：配置层面零影响，但"能不能推成功"会受影响。**

- ✅ **本地端口不变**：`127.0.0.1:7890` 是 Clash 的**本地监听口**，换节点只换**上游出口**。
  ⇒ `setx` / `gitconfig` 里写的是本地地址，**换节点不需要改任何配置**。
- ⚠️ **实际会变的三件事**：

  | 维度 | 影响 | 严重度 |
  |---|---|---|
  | **稳定性 / 可达性** | 部分节点连不上或频繁断流 → `push` 报 `502` / `Empty reply from server` / 超时 | 🔴 最常见的失败模式 |
  | **速度** | 影响首次全量推送（36 MB 已传完）；**之后每次只传增量 diff**（几 KB~几十 KB）⇒ 日常几乎不吃节点速度 | 🟡 低 |
  | **GitHub 侧风控** | 出口 IP 频繁跳变通常无碍（HTTPS token 不绑 IP）；若某节点 IP 被标记，可能 403 / 要求验证 | 🟡 低 |

- 🔴 **最需要避免的一种**：切到 **「不使用节点 / Direct」**（面板右下角）⇒ `github.com` **直连 → 必挂**。
  同理，Clash 处于**规则模式**且规则把 `github.com` 判给 `DIRECT` / `REJECT` 时，一样挂。
- **怎么排查**：Clash 的 **Connections** 面板看 `github.com` 命中哪条规则、走哪个节点；
  或终端直接 `git ls-remote origin` 试连通。
- **失败怎么办**：**切回一个稳定节点重试即可** —— `git push` 是幂等的，重复执行安全。
  推荐优先选 **香港 / 日本 / 新加坡 / 美国 的 IEPL 节点**；避开「免费」前缀与「不使用节点」。

## 6. 🔴 两个 Git 并存 + `credential.helper` **多值累积** ⇒ `git push` 每次弹凭据框

**症状**：用户每次向 GitHub 推送新提交都弹「选择凭据 / 账户」的框。

**根因（2026-10-07 查明）**：本机有**两个 Git**：

| Git | 版本 | system 配置位置 | 自带凭据后端 |
|---|---|---|---|
| `D:\Git\cmd\git`（**用户自己装的**） | 2.55.0.windows.**5** | `D:/Git/etc/gitconfig` | ✅ `D:/Git/mingw64/bin/git-credential-manager.exe` |
| `<WorkBuddy>/resources/vendor/PortableGit/mingw64/bin/git`（**沙箱自带**） | 2.55.0.windows.**3** | PortableGit 的 `etc/gitconfig` | ✅ 自己的 `git-credential-manager.exe` |

🔴 **`credential.helper` 是「多值累积」语义，不是覆盖** —— 配置里出现几条就**依次调用几个**。
用户自己的 Git 实际看到的链（`git config --show-origin --get-all credential.helper`）：

```
file:D:/Git/etc/gitconfig   → manager                            ← 用户自己的 GCM，正常
file:~/.gitconfig           → !"<WorkBuddy>/…/PortableGit/mingw64/bin/git-credential-manager.exe"
```

**两条都会被调用**。两个独立的 GCM 副本各有各的 `*.exe.config` 与凭据存储
⇒ 第一个存下了、第二个查不到 ⇒ **弹框要求重新登录 / 选账户**。

🔴 **那条 global 里的 PortableGit 路径是本 AI 会话的 Git 写进去的**（`~/.gitconfig` 的 mtime
与 AI 跑 git 的时刻吻合）—— 沙箱 Git 的 GCM **首次运行**时把 `credential.helper` 写进了**用户全局配置**。
**⇒ 教训：AI 会话跑 git 会污染用户的全局 git 配置，写入指向沙箱安装目录的绝对路径。**
（沙箱路径一旦随 WorkBuddy 升级 / 迁移而变，用户的 git 就会指着空气。）
⇒ **收工前应 `git config --global --show-origin --get-all credential.helper` 检查一次。**

**修法（三条命令）**：

```bash
git config --global --unset-all credential.helper                  # ① 清掉外来 helper
git config --global --unset credential.helperselector.selected     # ② 清掉 helper-selector 残留
"C:/Program Files/GitHub CLI/gh.exe" auth setup-git                # ③ 让 gh 接管 github.com 凭据
```

- ② 的背景：global 里有 `[credential "helperselector"] selected = manager`，是**历史上某次 helper-selector 弹框**留下的。
- ③ 让 `gh`（token 存 keyring，**非交互、无 GUI**）接管 `github.com` ⇒ **两个 Git 行为一致、彻底无弹框**。
  它写的是 `credential "https://github.com"` 专属段（空的 `helper =` 起**重置**作用，再接 gh）。
- ✅ 用户另有 Azure DevOps 用法（`D:/Git/etc/gitconfig` 有 `credential.https://dev.azure.com.usehttppath`），
  **不受影响** —— 那段没有 helper，仍走用户自己的 `manager`。
- **回滚**：`git config --global credential.helper '!"<WorkBuddy>/…/PortableGit/mingw64/bin/git-credential-manager.exe"'`。
- **回归判据**：`git push --dry-run` 返回 `Everything up-to-date` 且**全程无弹框**。

⚠️ **动手前先要弹框截图**确认弹的是 GCM / 凭据选择框（而非 IDE 或 GitHub Desktop 自带的框）。
