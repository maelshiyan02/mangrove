## 1. 需求 1 —— 「用了一会儿鼠标拖动，空格就失效」

### 1.1 先分清现象与根因

用户描述的是「拖动用一会儿之后」失效。实测把两件事拆开了：

* **拖拽本身不夺焦点**：连续三次后台拖拽后连打 12 次指针结束事件，`hasFocus` 恒为 `true`。
  所以「拖一下就坏」并不成立。
* **真正夺焦点的是弹层**：右键菜单 / 设置抽屉 / 章节抽屉 / 对话框 pop 之后，
  `focusNode.hasFocus` 由 `true` 变 `false`，`FocusManager.instance.primaryFocus` 落到**裸 `FocusScopeNode`**
  （"焦点掉进虚空"）。此后 Flutter 的 `KeyboardListener` 不再收到任何按键 —— 空格、↑↓、WASD 全哑，
  只有**再点一下页面**才回来。用户之所以觉得「用一会儿才坏」，是因为期间开过弹层。

诊断日志（临时诊断通道，已完成使命并删除；原始行摘录）：

```
2026-11-16T14:35:11.885385 SYNTHHOLD down offset=0.0
2026-11-16T14:35:11.886049 KEY KeyDownEvent null hasFocus=true primary=FocusNode page=1 total=82 ...
2026-11-16T14:35:12.833749 POINTER_END canceled=false drag=false long=true fingers=0 hasFocus=true primary=FocusNode
2026-11-16T14:35:12.835992 KEY KeyUpEvent null hasFocus=true primary=FocusNode page=3 total=82 ...
2026-11-16T14:35:12.844014 SYNTHHOLD up start=0.0 end=1569.6 moved=1569.6
```

修复前的对照（同一诊断通道，弹层关闭后）：

```
POINTER_END ... hasFocus=true  primary=FocusNode        <- 弹层打开前
（打开并关闭右键菜单）
SYNTH before hasFocus=false primary=FocusScopeNode      <- 焦点落空，没人还
KEY KeyDownEvent ... hasFocus=false                     <- 按键仍被投递到 widget，但焦点不在
```

### 1.2 修法：两条自愈通道 + 一个纯函数守卫

`reader.dart` 新增 `ensureReaderFocus()`：

* 通道 A —— `FocusManager.instance.addListener(_onFocusManagerChanged)`：报告焦点变化后推到下一帧再看，
  避开路由切换的中间态（弹层 push/pop 时焦点会短暂落空）。
* 通道 B —— `gesture.dart` 的 `onPointerDown` 每次指针落页都调一次：**鼠标在哪，键盘就该跟到哪**。

守卫抽成零 Flutter 依赖的纯函数（`foundation/reader_ux_policy.dart`），便于 headless 喂真值表：

```dart
bool shouldReaderRestoreFocus({
  required bool routeIsCurrent,      // 不是当前路由 → 不动（别打断别的页面）
  required bool hasFocus,            // 自己已有焦点 → 不动（避免每次点击都 requestFocus）
  required bool editableFocused,     // 评论区输入框在打字 → 绝不动
  required bool primaryIsBareScope,  // 只认 null / 裸 FocusScopeNode 两种"虚空"态
});
```

> 为什么必须"只补虚空态"：阅读器侧栏里有评论输入框。无脑 `requestFocus` 会让用户打字打一半被抢走焦点 ——
> 那是比"空格失效"更难查的 bug。所以 `editableFocused` 是硬条件，且有独立断言钉住。

### 1.3 反向验证（注入）

| 注入 | 目标断言 | 结果 |
|---|---|---|
| `gesture.dart` 删掉 `reader.ensureReaderFocus();` | `reader.focus_self_heal_wired` | 只红这一条 |
| `reader.dart` 的 `ensureReaderFocus` 退回「只看自己有没有焦点」的裸守卫 | `reader.focus_guard_wired` | 只红这一条 |

纯函数行为由 `reader.focus_guard_truth_table` 的 `broken_would_pass` 口覆盖：
故障实现「只看 hasFocus」在「路由不当前 / 不是裸 scope / 输入框持有焦点」三种现场下均被拒。

### 1.4 证据边界（必须说清）

后台自动化**无法把系统按键投递给 Flutter**：窗口即使处于前台，
`PostMessageW(WM_KEYDOWN)` 投给顶层窗口或 `FLUTTERVIEW` 子窗口，`onKeyEvent` 都收不到
（本轮实测：清空诊断日志 → 单次投递 → 日志 0 行；投给子窗口同样 0 行）。
规则也禁止 `SetForegroundWindow` / `SendInput` 抢焦点。
因此"空格是否真的翻页"只能由**焦点态 + 按键策略真值表**间接证明，不能直接拍成录像。
这条限制写进 §8，不做"复跑不复现"式结案。

## 2. 需求 2 —— 单击 vs 长按，长按更快且能急刹

### 2.1 设计

| | 单击（tap） | 长按（hold） |
|---|---|---|
| 判定 | 按住 < 180ms（`kReaderHoldTriggerDelay`） | ≥ 180ms |
| 落地 | 一次半屏 + 200ms `Curves.ease`（沿用 P56 参数，未改手感） | 自建 16ms ticker，每帧 `scrollBy(delta)` |
| 速度 | 0.5 视口 / 次 | 1.1 → 3.0 视口/秒（smoothstep 900ms 爬坡） |
| 停止 | 动画自停 | 松手当帧停（无惯性、无回弹） |

关键实现点：

* **KeyDown 只起算，KeyUp 才判定**。若 KeyDown 就翻一屏，按住时会"先跳一屏再从新位置加速"。
* **系统按键重复（`KeyRepeatEvent`）一律忽略**：长按速度必须由自己的 ticker 决定，
  叠加系统重复会忽快忽慢，且松手后系统可能还补发一串重复消息。旧代码 `event is KeyDownEvent || event is KeyRepeatEvent`
  直接翻页的写法已删净（`reader.hold_ignores_os_repeat` 断言钉住）。
* **自刹车**：`_tickHold` 里两个出口 —— `!focusNode.hasFocus`（KeyUp 可能永远不来）与
  `held > kReaderHoldMaxDuration`（12s 安全上限）。
* gallery 模式没有像素插值，退化为每 240ms 翻一页（`kReaderHoldPageInterval`）。

### 2.2 实测（真实二进制，鼠标长按驱动同一条按键链路）

| 动作 | 结果 |
|---|---|
| 按住 948ms | 位移 **1569.6px**；**11 秒后仍是 1569.6px** → 无惯性、无 coast，急刹成立 |
| 按住 147ms（< 180ms） | ticker 未产生位移；松手补一次 `CONT forward … delta=552.0 target=2121.6` = 经典半屏缓动；`moved=0.0` |

口径校准：策略层 1 秒长按（含 180ms 判定窗）≈ 1602px（按 1000 视口计）= **约 3.2 次单击**；
进入满速后 3.0 视口/秒 ≈ **每秒 6 次单击**。此前口头说的「4.8×」是把满速瞬时值套到了 1 秒整段上，
以本条为准。

## 8. 已知限制与待办

1. **按键无法后台投递**（见 §1.4）：窗口虽是前台，Flutter 原生层仍按自身 `GetFocus` 判定，
   `PostMessageW` 投给顶层或 `FLUTTERVIEW` 都进不了 `onKeyEvent`。要真验「空格翻页」必须有人坐在
   交互桌面按键盘，或允许 `SendInput`（规则禁止）。
2. **最终二进制的 GUI 冒烟做在「重建之后」这一版上**（`p64_f02…p64_f15`）：
   首页正常、「作品评论 / 章节评论」已是中文、章节条与「选择章节」对话框都是中文、
   阅读器右缘评论 → 「章节评论」侧栏加载出当前话真实留言。
   唯一麻烦是**本机沙盒里 GUI 子进程会被作业对象随父 shell 一起收走**：
   `Popen` 直接起会「窗口出现 3 秒后消失」，`CREATE_BREAKAWAY_FROM_JOB` 被拒（WinError 5），
   必须让**父任务本身保活**（后台跑一个长 `sleep`）才能稳定截图。这不是应用 bug，
   但下次要在后台验 GUI 得照这个套路起进程，否则会误判成「新构建崩了」。
3. `CommentsPage` 的错误文案（`No comments` / `No chapter comments`）直接走 `Res.errorMessage` 展示，
   没有过 `.tl`；翻译键已补，但要在展示处接上才有意义 —— 留作下一轮一致性清理。
4. 评论列表只做了「看」。发评论走的是各来源原有的 `sendCommentFunc` / `sendChapterCommentFunc`，
   本轮未在真机验证发送（避免往用户账号里灌测试内容）。
