## 2. 拷贝漫画空白：三层根因（代码 + 实测）

### 2.1 判活接口选错 → 通道自锁 12 小时

| 层 | 旧行为（1.9.0） | 后果 |
|---|---|---|
| `ensureChannel()` 探针 | `GET /api/v3/homeIndex`，看 `results.recComics.list.length` | 匿名 + `region=0` 下该接口 `topics/topicsList/recComics` **全部 `list=[] total=0`**（实测），于是探针恒判"App 通道已死" |
| 死标记 | `markAppDead()` 写 `_app_dead_until` = now + **12h** | 之后 12 小时内所有搜索/详情/章节都不再走 App 通道 |
| 回落通道 | 网页端 `/api/kb/web/searchci/comics` | 对**任意**关键词都返回 `200` + `list:[]` + `total:0`，**永不报错** → 静默空白 |
| 与此同时 | 签名后的 `/api/v3/search/comic` **能返回真实结果**（斗罗/海贼/恋爱/重生/一拳 5/5 有数据） | 说明不是源站封禁，是自锁 |

### 2.2 v1.9.1 的修法（`comic_source/copy_manga(5).js`）

1. 探针换成 **`/api/v3/search/comic?limit=1&offset=0&q=a`**：能返回 `results.list` 数组才算活；210/非 200/结构缺失才判死。
2. **探活成功即 `clearAppDead()`** —— 删掉 `_app_dead_until`，通道自愈，不用等用户清数据。
3. `webSearch()` 遇到空列表**显式抛错**（`网页端搜索无结果(接口返回空列表, 可能已失效)`），不再默默返回 `[]` 冒充"没搜到"。
4. 详情/章节的**软风控**（HTTP 200 + `results` 空）改为**按接口分流直降网页端**，不再 `markAppDead()` —— 旧逻辑会因为一次详情软风控把搜索一起拖死（这就是"搜一次 → 之后全空白"的传播路径）。

### 2.3 反向验证（`test-materials/runs/copy_v191_channel_check.cjs`，19 条断言）

真加载源文件，注入内存 store + 可编程 `Network` 桩，驱动 `ensureChannel` / `webSearch` / `viaChannel`：

| 轮次 | 结果 |
|---|---|
| 基线 | `PASS = 19 / FAIL = 0` → `SELFTEST PASS` |
| 注入① 探针改回 `homeIndex` | `PASS=14 FAIL=5`，**只红** A、A′、B、C、I′（探活/自愈/空列表报错相关） |
| 注入② 删掉空列表抛错 | `PASS=16 FAIL=3`，**只红** E、E′、I″ |

> 两次注入各自只红目标子集，未连带红无关断言 —— 符合"一条注入只红它该红的那几条"。

## 3. 卡顿：退避值被当成节流阀（根因 + 修复）

| 事实 | 证据 |
|---|---|
| `data/comic_source/copy_manga.data` 里留着 **`"_adaptive_delay":"38400"`** | 历史封禁留下的持久化值 |
| `throttle()` 每次请求前 **按这个值 sleep** | 章节列表要 2–3 跳 → 80–120 秒"转圈" |
| 章节重试 **6 次指数退避**（4.8→9.6→19.2→38.4→60s）后抛 `Network error` | 用户看到的"点了没反应" |
| `comic2` 详情返回 `200` + 空 `results`（软风控）→ App 通道**永远不可能成功**，只能靠 6 次重试耗完 | 详情页长时间空转 |

### 修复

- `throttleBase = 800`：节流基准**与退避值解耦**，不再读 `_adaptive_delay`。
- `backoffMaxSession = 8000` + `_getBackoffDelay()` **夹紧**：读到超限值就地改回 8s，把历史残留自动收敛。
- `loadEp` 重试 **6 → 3**，单次退避封顶 **8s**，软风控**零等待**直降网页端。
- 清掉持久化里的 `_adaptive_delay` / `_app_dead_until`（备份 `copy_manga.data.bak_p63`）。
- 顺带修 `ComicListState.storeState()` 的 `mounted` 守卫：`_loadPage` 的 `finally` 在页面已销毁后仍调 `PageStorage.of(context)`，抛 `Null check operator used on a null value`（P62 日志里那两条未捕获异常的来源）。

### 实测

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 124 话章节列表 | >20 s 转圈 | **23:58:28 → 23:58:32 = 4 s** |
| 119 话章节列表 | >20 s | ~5 s |
| 57 话章节列表（本轮新增） | — | ~3–7 s（`p63_66` → `p63_67_wait2`） |

## 4. 本轮新挖出的缺陷：本地记录陈旧 → 阅读器白屏报错

### 4.1 现象（`p63_49_state.png`，旧二进制）

打开 `大公` 搜索结果的第 3 行第 3 张 → 详情页正常（共 69 话）→ 点 `第02話` → 阅读器白屏 + **原始 OS 异常**：

```
PathNotFoundException: Directory listing failed, path =
"D:\...\Mangrove\ComicLibrary\downloads\那個大公的華麗婚姻騙局\28911d66-632e-11ee-9733-d3d228a76de6"
(OS Error: 系统找不到指定的路径。, errno = 3)
```

### 4.2 根因（DB 投影 vs 磁盘真相）

| 事实 | 值 |
|---|---|
| `data/local.db` 记录 `id=ngdgdhlhypj`、`comic_type=557997769`（拷贝网络源） | `directory = 那個大公的華麗婚姻騙局` |
| 该记录的 `chapters` | `{"默認": {"230c97f8-…":"第01话", "28911d66-632e-11ee-9733-d3d228a76de6":"第02话", …}}`（**69 话，key 是 UUID**） |
| 该记录的 `downloadedChapters` | **5 个 UUID**，含第 2 话 → `isDownloaded()` 判"已下载" |
| 磁盘该目录 | **存在，71 个子目录**，但命名全是 `1 [copymanga]` … `69 [copymanga]` |
| 第 2 话的 UUID 子目录 | **不存在** |

也就是说：**同标题的"本地导入记录（id=8）"与"网络记录（ngdgdhlhypj）"共用了同一个漫画目录**，磁盘上是导入命名，网络记录却按 UUID 命名登记了 5 话 —— 记录是磁盘的**投影**，投影与真相分叉了。

`lib/pages/reader/images.dart::load()` 旧逻辑：

```dart
if (reader.type == ComicType.local || LocalManager().isDownloaded(...)) {
  try { images = await LocalManager().getImages(...); }
  catch (e) { setState(() => error = e.toString()); }   // ← 直接把 OS 异常当结论
}
```

`isDownloaded()` 只查 `downloadedChapters`（DB），`getImages()` 才碰磁盘 —— 于是白屏报错。

### 4.3 修复（`Mangrove/lib/pages/reader/images.dart`，+170/−? 重构）

把 `load()` 拆成 `_loadLocalPages` / `_loadNetworkPages` / `_applyImages` / `_fail` 四段，并规定：

- 本地方失败时，**`type == local` 才如实报错**（没有网络通道可回落）；
- **网络漫画本地读失败 = 换一条路**，回落 `_loadNetworkPages()` 重取这一话；
- **不去改用户的 `downloadedChapters`**（账目清理由下载侧的磁盘对账负责），只保证"读不到就换路，不静默改账"。

### 4.4 反向验证（同一输入，新旧二进制 A/B）

| | 旧二进制（`app.so` 23:47:27） | 新二进制（`app.so` 00:10:28） |

| 详情页画面 | `p63_48_state.png` md5 `d04390214496c136430ff293088dd45a` | `p63_57_state.png` md5 **完全相同** `d0439021…` |
| 点 `第02話` | `p63_49_state.png`：白屏 + `PathNotFoundException` | `p63_58_state.png`：`Ch.2/69`、`第02話 · 1/112`、真实画面「好委屈。」 |

详情页两版 md5 逐字节相同 ⇒ **同一输入、同一状态**，差异只来自 `images.dart` 这一处改动。这就是本缺陷的反向口：改回去，白屏必然复发。
