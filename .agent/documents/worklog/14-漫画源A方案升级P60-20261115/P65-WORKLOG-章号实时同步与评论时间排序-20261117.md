## 1. 需求①：右上角章号卡住

### 1.1 人工验收现象与取证

用户反馈「通过右上角章节跳转按钮前进/后退时，章节数字不实时更新，与左下角第几话形成鲜明对比」。

复现步骤（后台 ctypes 驱动，不抢焦点）与结果：

| 帧 | 操作 | 右上角胶囊 | 左下角话数 |
|---|---|---|---|
| `p65_a03_continue_after.png` | 进入阅读器 | `Ch.162 / 229` | `第162话 · 1/137` |
| `p65_a06_next_after.png` | 点胶囊 `›` 下一话 | **`Ch.162 / 229`（没动）** | `第163话 · 1/137` ✅ |

### 1.2 根因（不是切章没生效）

`ChapterCapsule` 是 `StatelessWidget`，且在 `scaffold.dart` 里以 `const ChapterCapsule()` 挂载：

- 无缝跳章走 `_ContinuousModeState.jumpToChapter()` → 只调 `context.readerScaffold.update()`；
- `readerScaffold` 重建时，`const` 子 widget 被 Flutter **规范化复用**，`ChapterCapsule.build()` 根本不重跑；
- 胶囊里的 `reader.chapter` 是通过 `findAncestorStateOfType` 取的（不是 InheritedWidget），没有依赖注册，章号变化不会主动通知它；
- 左下角话数属于连续模式自己的滚动状态，滚动监听器里显式 `update()` 了，所以实时变化 —— 这就是「两处对比鲜明」的来源。

滚动跨章（`images.dart` 两处 `reader.chapter = entry.chapter`）同理不会让胶囊刷新。

### 1.3 修法（复用现有章号通道，不新造一套状态）

1. `_ReaderState.chapter` 由裸字段改为 **getter / setter**：任何一次真实赋值都推进 `chapterRevision`（`ValueNotifier<int>`）；`dispose()` 里回收。这样三条改章路径（remount / 无缝跳章 / 滚动跨章）自动全覆盖。
2. `ChapterCapsule` 用 `ValueListenableBuilder<int>` 订阅 `chapterRevision`；胶囊文案抽成零 Flutter 依赖纯函数 `readerChapterCaption(current, total)`，便于 headless 钉住「章号变了文案必须变」。

改动文件：`foundation/comment_order_policy.dart`（新）、`pages/reader/reader.dart`、`pages/reader/chapter_capsule.dart`。

## 2. 需求②：评论时间从旧到新

### 2.1 现状取证

`p64_f05_comments_after.png`（P64 帧）从上到下：`2026-11-16 15:23:17 → 2026-11-15 00:06:43 → … → 2026-11-11 13:05:48`，确实是拷贝 App 的「最新在前」。

`comic_source/copy_manga(5).js` 的 `loadComments` / `loadChapterComments` 都把 `e.create_at` 映射到 `time`，分页用 `offset=(page-1)*20`；`maxPage` 由 `total` 算出。⇒ 要真正从旧到新，**不仅要页内排序，还要反向分页**。

### 2.2 纯策略层（新文件 `foundation/comment_order_policy.dart`）

| 函数 | 职责 |
|---|---|
| `commentTimeKey(String?)` | ISO `YYYY-MM-DD HH:MM:SS` / Unix 秒 / 毫秒统一成可比较整数；解析失败返回 null |
| `orderedCommentIndices(times, order)` | 稳定排序下标；同键保原序，未知时间沉底（不伪造时间） |
| `orderComments(list, order, timeOf)` | 按上面下标重排，不改入参 |
| `commentFirstPage(maxPage, order)` | 旧→新首屏取服务端最后一页 |
| `commentNextPage(page, maxPage, order)` | 旧→新往回翻（`maxPage→…→1`），新→旧沿原方向递增 |
| `readerChapterCaption` | 需求①的胶囊文案 |

### 2.3 UI 落地（复用 P64 已建的两条评论管线）

- `CommentsPage`（详情页 / 评论中心的作品与单话分栏）与阅读器内 `ChapterCommentsPage` 共用上述纯函数；
- 首屏：先取 page 1 拿 `maxPage`，旧→新时改取 `maxPage` 页展示（多一次请求，避免动 JS 源脚本被源更新覆盖）；
- 每次加载后对当页按时间排序，「加载更多」按方向递进；
- 两个页面各加一行 `⇅ 从旧到新 / 从新到旧` 切换条（点击只重排已加载列表，不重新取数，保住滚动位置）；默认 **旧→新**；
- i18n 补 `Oldest first` / `Newest first` 简繁两条。

### 2.4 实测（最终构建）

**作品评论**（`p65_b07_comments.png`，控件显示「从旧到新」）：

```
2022-05-25 22:15:05 → 2022-08-24 09:58:58 → 2023-06-28 13:48:54
→ 2023-08-26 10:19:27 → 2024-06-25 11:05:46 → 2025-01-29 12:08:05
```

（对比 P64 帧首条是 2026-11-16 ⇒ 反向分页确实生效，不是只翻了页内顺序。）

切换后（`p65_b08_toggled.png`，控件显示「从新到旧」）：同一批评论整组倒排，首条变 `2025-01-29 12:08:36`。

**章节评论**（`p65_b09_chapter_comments.png`，`第163话`）：控件同样默认「从旧到新」；缩略图上小字一度疑似倒退，用纯标准库裁剪放大 4 倍（`p65_b09_times_zoom.png`）逐字核对为

## 4. 本轮新坑（写给下一次）

1. **`_read(packageRoot, …)` 的路径基准是包根 `Mangrove/Mangrove`**：源码要写 `lib/pages/...`，翻译表要写 `assets/translation.json`（不是 `../assets`；`../` 是项目根的 `comic_source/`、`data/`）。漏 `lib/` 时读到的空串会让接线类断言**静默红**，且 detail 看不出路径错。
2. **翻译表注入要抹掉所有 locale**：`zh_CN` / `zh_TW` 都有 `Oldest first`，只改一处另一处仍喂绿断言（本轮第 4 组注入首次 FAIL 即此因）。
3. **`List<int?>.join(',')` 把 null 变成空串**，断言里期望 `'2,1,null'` 会假红；必须先 `map((v) => v?.toString() ?? 'null')`。
4. **缩略图小字不能当证据**：`2024-10-06` 被我读成 `2024-10-16`，差点误判成排序 bug。用 `png_probe.load_rgb` + 手写 PNG 编码裁 4 倍放大后逐字核对才定案（本机无 Pillow）。
5. **构建途中的改动不会进当次产物**：本轮为修断言里的 join 与路径连跑四次构建；`app.so` mtime 是唯一可信的新鲜度凭据，别看「构建成功」就当新代码已生效。
