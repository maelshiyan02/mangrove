## 1. 结论速览

| 用户问题 | 判定 | 根因 |
|---|---|---|
| 包子 / 拷贝在线源无法显示 | **不是源站全封，也不是 UI 代码 bug** | 本机 Clash 分流把漫画域名导向 `🌩️ Cloudflare → 🔰 选择节点 → 🇦🇺 澳大利亚Y01`，该节点**间歇性切断 TLS 握手**；Mangrove 默认 `proxy='system'` 跟随系统代理 `127.0.0.1:7890` |
| 拷贝漫画「连接不到」 | 同一根因；此刻网络层 **6/6 端点全通** | 22:51–22:52 的 15 次失败全部走同一个澳洲节点；重启后同名 URL 已恢复 200 |

**一句话**：三个现象是**同一条代理链路故障**的三种表现 —— 握手被切断 → 请求失败 → 串行重试与退避把界面拖成分钟级无响应。

## 2. 在线源：握手失败根因（证据链）

### 2.1 代码链路（只读）

| 层 | 事实 |
|---|---|
| `data/appdata.json` | `proxy = "system"`、`ignoreBadCertificate = false` |
| 系统代理注册表 | `ProxyEnable=1`、`ProxyServer=127.0.0.1:7890` |
| `lib/network/proxy.dart` | `_getProxy()` 经 MethodChannel `getProxy` 取系统代理字符串 |
| `lib/network/app_dio_io.dart` | `createIOHttpClient` 设 `findProxy = 'PROXY <系统代理>'`；所有请求走 `_IOProxyAdapter` |
| `lib/foundation/js_engine.dart` | 漫画源 JS 的 `http` 回到 `_http()` → `AppDio` → 上述适配器 |
| `lib/network/app_dio.dart` | `connectTimeout = 15s`、`receiveTimeout = 15s` |

### 2.2 决定性 A/B 实测（22:5x，故障窗口内）

走 `127.0.0.1:7890` 做 CONNECT + TLS，对漫画域名全部 **`SSLEOFError`（3.14s）**；`www.baidu.com` 走 DIRECT 正常 0.07s。

| 域名 | DIRECT | PROXY 7890 | PROXY 8476 |
|---|---|---|---|
| `cn.kukuc.co`（包子） | `HTTP/1.1 200 OK` | `SSLEOFError 3.14s` | `200 OK` |
| `api.copy-manga.com` | TLS 超时 12s | `SSLEOFError 3.14s` | 超时 |
| `api.copy202601.com` | `404`（可达） | `SSLEOFError 3.14s` | `404` |

**3.14s** 与用户 `logs.txt` 里 15 次请求每次固定的 **3.15s** 间隔吻合到毫秒级 → 不是源站随机失败，是同一处 TLS 被切断的固定超时。

## 3. 卡顿根因（分层结论）

### 3.1 先排除整机层（不是这些）

| 项 | 实测 | 判定 |
|---|---|---|
| CPU | 三次采样 5.1% / 1.7% / 0.0% | ✅ 不是 CPU 瓶颈 |
| 磁盘 | 142KB/s / 130KB/s / 118KB/s，`% Disk Time = 0` | ✅ 不是 IO 瓶颈 |
| 系统句柄 | 85,626，`MTKBTSVC` 仍 `Stopped + Disabled` | ✅ 句柄泄漏未复发 |
| 上轮写放大源 | `data/logs.txt` 5 秒增长 **0 B** | ✅ artifact-index 16MB 写放大已消失，未复发 |
| Clash 日志写速率 | 561 B/s | ✅ 正常 |

内存侧确实偏重但非 CPU 瓶颈：WorkBuddy 8 进程 ~1.97GB、Chrome 11 进程 ~1.83GB、dwm ~603MB、Mangrove ~724MB。**这是内存压力，不是本次「卡」的主因**。

### 3.2 主因：网络等待串行放大（应用内）

| 证据 | 数值 |
|---|---|
| 失败重试链 | 22:51–22:52 共 15 次请求，每次固定 3.15s，累计约 **45s 纯等待** |
| 阅读器连续帧 | 8 帧 / 17s，`distinct_md5=1`（**画面完全静止**） |
| 阅读器进程状态 | CPU `0.016s / 3s`、零 TCP 连接 → **挂起等待，不是算不动** |
| 点击到出图 | 23:10:02 点击「阅读」→ 23:12 正文图出现，约 **2 分钟** |
| 拷贝搜索连续帧 | 6 帧 / 17s，`distinct_md5=1`，结果区空白 |
| 封面 | 发现页初为青色占位，回访后才变真实图 → 图片延迟到达以分钟计 |

放大机制（代码级）：
- `copy_manga(5).js` 1.9.0 的 `adaptiveBackoff`：`newDelay = clamp(max(cur×blockFactor, Retry-After, cur), floor=600ms, maxDelay=60s)`，`_backoffOnBlock` 在首页/详情 210/章节 210 多处调用 → **一次风控最多等 60s，且多镜像串行重试会累乘**
- 5 个镜像域名 × 3 类接口逐个尝试，全部走同一个故障节点时，每次都吃满 3s 超时
- `lib/components/comic.dart`：`_loadPage` 的 `finally` 无条件调 `storeState()` → `PageStorage.of(context)`；widget 已 dispose 时抛 `Null check operator used on a null value`（日志里 2 条未捕获异常）→ 列表加载失败后状态错乱

### 3.3 独立卡顿源：CF 自动验证拉起真实 Chrome

`data/logs.txt`（重启后）明确记录 23:19:19–23:20:39：

```
seedRealProfile: copied real Chrome cookies → false
copy failed ... Cookies / Cookies-journal (errno=32 另一个程序正在使用此文件)
launching chrome: C:\Program Files\Google\Chrome\Application\chrome.exe
cdp ready on 127.0.0.1:9222
verifyViaCfT: ✅ cf_clearance len=383
bundled chrome exited: 0   (23:20:39)
```

- 约 **80 秒**的后台浏览器生命周期，期间复制 Chrome 用户目录、起 CDP、做 CF 挑战
- Cookies 复制因**用户的 Chrome 正在占用**而失败（`errno=32`）→ 可能反复重试。**23:31 后台启动任务返回后补证**：GUI 进程 stdout 共有 **4 条** `Cookies` 复制失败（`logs.txt` 只记了 2 条），说明 CF 验证至少重试了两轮，卡顿放大比日志所示更严重
- 这条与包子/拷贝无关，但会**整机级**拖慢（11 个 chrome 进程 / 1.83GB）
