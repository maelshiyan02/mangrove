| 现象 | 真正原因 | 判定证据 |

| 章节列表同一话出现两次（一次「第1话」、一次「第01话」风格） | P69 跨形态合并用**旧话号口径**（`parseChapterTitle` 认不出 `1 [copymanga]`），同一话的编号 key 与 UUID key 各落一格，**并且已经写进 `local.db`** | `local.db` 中 id=`ngdgdhlhypj` 的 `chapters` = 69 编号 key + 69 UUID key = **138 格** |

## 1. 取证链

1. `local.db`（`data/local.db`，`%LOCALAPPDATA%\.mangrove_datapath` 指向 `Mangrove/data`）：
   - id=`ngdgdhlhypj`（本地导入）`chapters` 138 格、`downloadedChapters` 74 条；
   - id=`8`（拷贝漫画）与 id=`7`（comix.to）是另两条同书不同源记录，不与本地行混用（详情页按 id 精确取行）。
2. 用户截图：章节区出现 `第1话 / 第01话` 两套写法交替，行数明显超出 69 话，页面滚动/载入明显迟滞。
3. 源码链路：
   - `ComicChapters.mergedWith`（P70 版）只在**两个来源之间**按 `_chapterMergeIdentity` 去重，**不清理任一侧矩阵内部的重复**；
   - `LocalComic.fromRow` 直接把库里的 `chapters` JSON 反序列化，**读的时候不做归一**；
   - `chapters.dart` 按 `allVersionKeys` 逐格渲染并逐格查下载状态 ⇒ 138 格 = 138 次查询。
4. P69 的归一入口 `_chapterMergeIdentity` 当时用 `parseChapterTitle`（只认 `第N话` / `Ch.N` / 纯数字），`1 [copymanga]` 读不出话号 ⇒ 身份退化成 `k:1 [copymanga]` 与 `n:1` 两种，各有各的格。

## 2. 修复

### 2.1 矩阵内部去重 `deduplicatedWithRemap()`

`foundation/comic_source/models.dart` 新增：

- 用 `_canonicalCells()` 摊平，按 `_chapterMergeIdentity`（话号 + 翻译组 + 语种，刻意忽略站标）判等；
- 同一身份保留**规范格**：`_canonicalCellScore` 给「key 能读出话号 + key 与目录名同形」的格子加权 ⇒ 选 `1 [copymanga]` 而不是 UUID key（UUID key 算出的目录名读不到磁盘）；
- 同时产出 `remap`：被丢弃的 `bucketKey` / `chapterKey` → 规范 key；
- `deduplicated` 为幂等版（无重复时结构不变）。

`mergedWith` 改为**先各自去重再合**（`left.deduplicated._mergeDeduplicated(right.deduplicated)`），阻断"下一次刷新又把脏数据带回来"。

### 2.2 下载记录随迁移改写 `remapKeys()`

`ComicChapters.remapKeys(keys, remap)`：按映射改写并**保序去重**。否则折叠后旧 UUID key 成孤儿，蓝标全丢。

### 2.3 存量迁移 `_migrateDuplicateChapterKeys()`

`foundation/local.dart`：`LocalManager.init()` 与 `restoreFrom()` 两处接线（恢复备份后也要自愈）。

- 逐行读 `comics`，`deduplicatedWithRemap()`；
- `remap` 为空即跳过（幂等，不产生无谓写库）；
- 有重复则一次性写回 `chapters` + `downloadedChapters`，并打日志：
  `Deduplicated chapter keys of '<title>': 138 -> 69 entries, 74 -> 69 downloaded keys`；
- 只改章节矩阵与下载 key：目录名、历史话号、缺页表都不动（规范 key 是编号 key，与磁盘目录本来就一致）。

### 3.4 本次踩到的坑

- **`List == const [...]` 是引用比较**：首版断言 `c.ids.toList() == const ['1 [copymanga]']` 恒假，基线 96/97。改为逐项比较后才真绿。这类"恒假断言"与"恒真断言"一样危险 —— 它会让后续注入看起来"只红目标"，其实是目标本来就没绿过。
- **`Iterable` 没有 `containsAll`**：`allVersionKeys.containsAll(...)` 编译期报 `undefined_method`，须先 `.toSet()`。
- 构建产物时间戳要核对：`builds/mangrove/mangrove.exe` 若早于源码 mtime，说明上一轮构建没包含改动（本次因此先跑出 93 条假基线）。
