## 1. 包子源 `baozi.js` v1.3.0

### 1.1 真 bug ①：appcn 官方域回落 100% 断裂（用户点名的「包子 app 端」）

**证据链**：
- `comic_source/baozi.js:935` 调用 `collectPages(...)`；全项目 grep 只有这一处调用 + 一处注释，**没有任何定义**。
- 旧版 `data/comic_source/baozi.js.bak_active_1.2.7_20261102_125637:763` 里 `collectPages` 是 `loadEp` 内的局部函数（逐页抓 + `seen` 去重 + 越界/无新图 break + 首图残缺识别）。
- v1.2.8/v1.2.9 把网页路径重构成内联循环（为支持 per-comic 后缀自愈），**删掉了定义，漏改了 appcn 回落分支**。
- 后果：`_isFallbackError` 判定镜像残缺 → 进 appcn 回落 → 立刻抛 `ReferenceError: collectPages is not defined` → P48「最新章只有 App 能看」的自愈通道从不生效。

**修法**：appcn 回落改为**内联逐页收集**（`appSeen` / `appImages` / `appTotal`），复用同作用域的 `parseImages` / `pagerOf` / `pagePath`，不依赖任何引擎全局注入。保持两条 P48 铁律：
- `CloudflareException` 原样透传（Dio 抛的 Error 直接冒泡，UI 靠它触发离屏 WebView 验证）；
- 源层不塞 `User-Agent`（交由引擎注入 `consts.webUA`）。

### 1.2 真 bug ②：分页钳制误判（用户症状「150 页只拿 50 页」）

**根因**：原 `if (pgAdded === 0) break; // 无新图即到底`。站点在 per-comic 后缀缺失时会把第 2 页起**钳制回第 1 页**，URL 去重后 `added=0`，旧逻辑当成"到底"提前 break → 整章静默截断成首页的 50 张。

**修法（分页对账）**：
- 引入 `productivePages`（贡献了新图的页数，首页有图记 1）。
- `total == null`（无分页标记站点）时保留 `added===0 break`；
- `total != null` 时即使某页 `added=0` 也**继续抓到 total**；
- 末尾对账：`total > 1 && productivePages < 2` ⇒ 判「分页钳制失效」，抛 `DomainBlock: chapter pagination clamped`，经 `withDomains` 换镜像、全失败则回落 appcn。
- 正常单页章（total 缺省/1）、正常多页章（每页有新增）均不触发。

**设计取舍**：不试图"猜"后缀或从钳制页反推——站点钳制回首页不给任何线索。对账的价值是**不再静默截断**，把控制权交还既有的换域/回落通道。

### 1.3 测试桩修正（重要：不是放水）

P48 桩 `baozi_p48_check.cjs` 里 `Network.get` 用 `url.includes("0_150")` 映射，`0_150_2.html`（第 2 页）也命中 → 一直返回首页副本，等于**从 P48 起就在模拟钳制**。而真实样本 `v_150.html` 的 `<title>` 明写 `第151话(1/2)`，第 2 页应有新图。

修正：
- 合成 `GOOD_P2`（基于真实首页，title 改 `(2/2)`、图 URL 加 `p2-` 前缀使其与首页不同）；
- 匹配顺序改为先判 `0_150_` 再判 `0_150`；
- 测试 3b 从「50 图」改为「两页共 100 图 + 不回落 appcn（仍来自 `s1.bzcdn.net`）」——这是**行为变更的正确期望**，不是缩小基线；
- 新增 `clampMirrorPages` 注入开关 + 测试 5（钳制必须回落 appcn 拿全 86 图，而非静默 50）。

新基线 = 原 21 条中 3b 改判 1 条（改判不是删）+ 3b 新增 1 条 + 测试 5 新增 3 条 = **25 条**。

## 2. 拷贝源 `copy_manga(5).js` v1.9.0

### 2.1 审计结论（先读后改）

现有逻辑已相当完整：真实设备指纹池 + 被封指纹排除、`throttle()` 600–1200ms 抖动、API/网页双通道 + 域名故障转移、软封禁（`200 + results:null`）检测、`_app_dead_until` 12h。

**三个真缺口**（对应 P58 §2.2 与用户点的「拦截 / IP 封禁」）：
1. 退避是**固定阶梯** `10000 + attempt*5000`，只有 210 响应里 `Expected available in N seconds` 才解析；**429 + Retry-After 完全没处理**。
2. 退避**不上限、不跨请求记忆**——每次风控从 10s 重新爬起，"好了伤疤忘了痛"。
3. `throttle()` 固定 600–1200ms，被风控后**不提高基线节奏**，下一次批量请求又立刻撞墙。

P58 明确写了：Scrapling 的代理轮换「仅轮询、不拉黑坏节点，比我们现有逻辑弱，**不建议采用**」→ 本轮**不动 IP 池 / 指纹池**，只抄自适应退避。

### 2.2 落地：策略与业务分离

新增 3 个**纯函数**（`CopyManga` 静态方法，无引擎依赖，可离线单测）：

| 函数 | 语义（对齐 `spiders/throttle.py`） |
|---|---|
| `adaptiveBackoff(cur, {retryAfterMs,floor,maxDelay,factor})` | `clamp(max(cur×2, Retry-After, cur), 600, 60000)`；**封禁永不加速** |
| `adaptiveRelax(cur, opts)` | `clamp(cur×0.85, floor, max)`；成功后缓慢恢复（Scrapling 无衰减，我们补上避免永久惩罚） |
| `parseRetryAfter(message)` | 解析 `N seconds` / `N min` / `N 秒` / `N 分钟` → ms，无匹配返回 0 |

配套：`_getBackoffDelay` / `_setBackoffDelay`（`_adaptive_delay` 持久化，跨请求/跨会话保持）；`throttle()` 目标间隔改为 `delay × (0.75~1.25 抖动)`（保留抖动——这是 Scrapling 无 jitter 的短板，我们做得更好）；`_backoffOnBlock(progress, retryAfterMs, label)` 作为**唯一风控退避入口**（记被封指纹 → 重置 → 算 next → 等待）。

**接线（5 处全部收敛到同一入口，不再各写一套阶梯）**：
- 首页软风控、`loadInfo` 详情 210 / 软风控、`loadEp` 章节 210 / 软风控；
- 210 分支用 `parseRetryAfter(res.body.message)` 取 Retry-After，替代原先手写的 `Expected available in ... seconds` 特判；
- 成功取到数据后 `adaptiveRelax` 缓慢衰减。

`grep -c 'waitTime = 10000'` = **0**，旧固定阶梯已清零。

运行时 dataPath = `%LOCALAPPDATA%\.mangrove_datapath` → `D:\AI Coding Project Management\Mangrove\data`，**实际生效源是 `data/comic_source/`**。
