## 1 · 崩溃：日志实栈 → 根因 → 修复

### 1.1 实栈（`…\AppData\Roaming\io.github.maelshiyan02\mangrove\logs.txt`）

`init.dart` 的 `FlutterError.onError` 把未捕获异常写进 `Log.error`，error 级**立即
flush** 到该文件。用户复现的三次（18:40:52 / 18:41:09 / 18:41:18）内容一致：

```
error Unhandled Exception 2026-10-10 18:40:52.305017
Bad state: Too many elements
#0  List.single (dart:core-patch/growable_array.dart:363)
#1  ScrollController.position (package:flutter/src/widgets/scroll_controller.dart:173)
#2  ScrollController.offset  (package:flutter/src/widgets/scroll_controller.dart:179)
#3  StudioScrollCanvasState._spanOverlay.<anonymous closure> (…/studio_scroll_canvas.dart:559)
#4  ListenableBuilder.build (package:flutter/src/widgets/transitions.dart:1173)
…（Element.mount / _firstBuild / inflateWidget 链）
```

🔴 **关键**：release 构建下 `ScrollController` 里那句
`assert(_positions.length == 1, 'ScrollController attached to multiple scroll views.')`
被**剥离**，只剩 `_positions.single` 的原生报错 —— 所以屏幕上完全看不出是"滚动控制器"，
只有拿到实栈才能定性。

### 1.2 根因

P26 的 `build()` 是**条件式改变树形结构**：

```dart
if (!widget.spanMode) return listView;                       // 旧代码
return Stack(children: [listView, _spanOverlay(...)]);
```

切进 `spanMode` 时，`ListView` 从「`LayoutBuilder` 的直接子节点」被挪进**新建的 `Stack`**。
Flutter 对这种情况的处置是：旧 `Scrollable` **先失活（deactivate）**、**到帧末才
unmount**。于是同一帧里同一个 `ScrollController` 上挂着 **2 个 `ScrollPosition`**，
覆盖层此刻读 `_controller.offset` ⇒ `_positions.single` ⇒ `Bad state: Too many elements`。

顺带的两个副作用（同一原因，一并消失）：
- 整条 `ListView` 重挂 ⇒ **滚动位置被重置**；
- 每页重挂 ⇒ **已解码位图全部丢弃、重新解码**。

### 1.3 修复（三件套）

| # | 改动 | 作用 |
|---|---|---|
| ① | `Stack` **常驻**：`children: [listView, if (widget.spanMode) _spanOverlay(...)]` | **根除重挂**。`ListView` 永远是 `children[0]`，`Stack.updateChildren` 按位置就地复用同一 Element ⇒ 不重挂、`ScrollPosition` 不重建、滚动位置不重置。切模式只是**增删覆盖层这一个子节点**。 |
| ② | 新增 `_hasSolePosition` / `_scrollOffset` 兜底 | 读取一律先判"控制器是否唯一附着"：`.positions.length == 1` 才读，否则按 0 处理。覆盖 `scrollToPage` / `_currentPageIndex` / `_spanPointerSignal` / `_toStrip` / `_spanOverlay`。即使同类瞬态再出现，**只是读不到偏移，绝不抛**。 |
| ③ | 拖框实时状态改 `ValueNotifier`（`_spanRepaint`） | 拖框是高频手势，`setState` 会把整条 `ListView`（及每个可见页的块列表）重建一遍，只为让覆盖层上的框动起来。notifier 只唤醒订阅它的覆盖层。 |

## 2 · 卡顿：根因（重绘风暴，与页数无关、与"重建次数"成正比）

### 2.1 证据链

| 环节 | 事实 |
|---|---|
| `PageCanvasPainter.shouldRepaint` | 用 **`old.blocks != blocks`**（`List` 默认 `==` = **identity**）判断"块有没有变" |
| `studio_page._blocksFor(pageKey)` | **每次 build 都从 json 重新投影**一个**全新 `List<CanvasTextBlock>`**（元素也是新对象） |
| ⇒ 结论 | 任何 rebuild 都会被判成"块变了" ⇒ **整页重绘** |
| `PageCanvasPainter.paint` 的成本 | 每块走 `_paintText` → `_fitFontSize` **收缩循环**（每次迭代一次 `TextPainter.layout()`，最多 ~5~7 次）+ 描边 painter + 正文 painter ⇒ **每块数次文本排版** |
| 规模 | `_keepAlive = 7` 页在位 ⇒ 一次重绘 ≈ **数千次 `TextPainter.layout()`** |
| 触发频率 | 滚动时 `_loadAround` 每完成一次解码就 `setState({})`（翻一页边界即触发一批淘汰+解码）⇒ **滚动过程中持续触发** |

⇒ 这正是"**超过 10 页左右开始卡**"的形状：跨过 keep-alive 窗口后进入
"淘汰一页 / 解一页"的稳定节律，每次完成都重绘全部在位页。

### 2.2 修复

| 文件 | 改动 |
|---|---|
| `components/text_block_canvas.dart` | 给 `CanvasTextBlock` 加 **值相等**（`operator ==` + `hashCode`），**逐字段比较 `paint` 的全部依赖**（index/rect/translation/sourceText/fontFamily/fontSize/lineHeight/fontWeight/alignment/vertical/foreground/hasFormat/strokeColor/strokeWidth/letterSpacing/lineSpacing/opacity/gradient*/angle）；`PageCanvasPainter.shouldRepaint` 改用 `_sameBlocks`（先 `identical`，再逐元素 `==`） |

安全性论证（已写进代码注释）：`CanvasTextBlock` **全字段 `final`（不可变）**，且调用方
一律"投影出新表"而非原地改元素（实时拖拽的 `_preview` 也是 `List.of` + **替换元素**）
⇒ **"相等"确实等于"没有东西要重画"**，不存在"值相等掩盖了变化"的窗口。

效果：rebuild 之后若块内容没变 ⇒ `shouldRepaint == false` ⇒ **不重绘、不排版**；
真正的改动（拖拽、改字号、改译文、翻页换表）逐字段不等 ⇒ 照常重绘。

### 2.3 看过但**故意没改**的

| 项 | 结论 |
|---|---|
| `_onScroll` 被注册**两次**（`initState` 的 `_controller.addListener` + `build` 外层 `NotificationListener<ScrollNotification>`） | 每个滚动事件跑两遍，但内容是 O(页数) 的整数比较/指针扫描（≈ 数百次运算）⇒ 相对 §2.1 的**数千次文本排版**可忽略。**已尝试删除、评估后回退**：删掉要整段重排缩进（移除一层嵌套），收益与 diff 代价不成比例，本轮保持最小改动 |
| `_loadAround` 的淘汰扫描 O(页数) | 同上，可忽略 |
| `decodePageFile` 在 UI isolate 上 `readAsBytes` + `ImmutableBuffer` | 每页**一次**，不在每帧路径上 |
