## 0. 一句话结论

三项都落地了，且**U3 的"重方案"比预想的改动小**——因为查清了 `downloadedChapters` 存的是
**chapterKey（版本自己的 key）而不是话号/目录名**。同一个话号下每个翻译组的 key 本来就不同，
所以"键带组区分"是**天然成立**的，真正要补的只有"目录名带组"和"选章器能选中非首选版本"。

## 1. U3-① 先确认键语义（这一条决定了后面所有方案）

用户明确要求"别猜"。证据来自 `local.db` 实读：

```
id= gm28k//my-dragon-girlfriend-has-returned  (My Dragon Girlfriend Has Returned)
  downloadedChapters = ["https://comix.to/title/gm28k-my-dragon-girlfriend-has-returned/11413625-chapter-1"]
  磁盘目录            = https___comix.to_title_gm28k-my-dragon-girlfriend-has-returned_11413625-chapter-1
  chapters（版本化）  = {"7":[{group:Asura Scans, key:.../11422259-chapter-7}],
                        "6":[{Asura Scans, .../11416129-chapter-6},
                             {DivaScans,   .../11418401-chapter-6}, … 共 8 组],
                        "5":… 10 组, "4":… 10, "3":… 10, "2":… 10, "1":… 10}
```

**结论（U3-①）**

| 项 | 事实 | 出处 |
|---|---|---|
| `downloadedChapters` 存什么 | **chapterKey**（`ComicChapterVersion.key`），不是话号、不是目录名 | `download.dart:980` `downloadedChapters: chapters ?? comic?.chapters?.ids.toList()`；`ids` yield `versions.first.chapterKey` |
| 目录名怎么来 | `LocalManager.getChapterDirectoryName(key)` = 纯非法字符清洗（`/`→`_`, `:`→`_`） | 磁盘上的 `https___…` 就是这么来的 |
| 同话不同组的 key 是否相同 | **不同**。ch.6 的 8 个组各有自己的 `114xxxxx-chapter-6` | 见上方实读 |

**推论（U3-⑤）**：`downloadedChapters` 已经天然按组区分，**不需要改键格式**。
真正在"键"上出问题的是另一处——选章器返回的是**索引**，索引空间只有 7 个话号，
选了 DivaScans 也会被 `ids.elementAt(i)` 翻成 Asura Scans 的 key。所以 U3-⑤ 的实际工作是
**让选章器交出 chapterKey**（U3-⑥），而不是发明新的键格式。

顺带查清的另一个坑：`ImagesDownloadTask` 里 `chapterKeys = comic.chapters.allChapters.keys.where(...)`，
而 `allChapters` 在版本化下**只有首个版本**——即便把非首选 key 塞进 `chapters`，也一个都匹配不上，
任务会静默什么都不下。这条不改的话 U3-⑥ 等于白做。

## 2. 改动清单

### 新增 `lib/foundation/chapter_directory.dart`

| 函数 | 作用 |
|---|---|
| `sanitizePathSegment(String)` | 从 `LocalManager.getChapterDirectoryName` 搬出来的纯清洗器 |
| `chapterDirectoryName(ComicChapters?, String chapterKey)` | **章节目录名的唯一真相** |

规则：

```
版本化 && 该版本带组名  ->  "<话号> [组名]"      例：6 [Asura Scans]
其余（扁平 / 分组 / 版本化但没组名）-> 旧规则 parseChapterTitle(key).chapterNumber ?? key
```

- 话号取版本矩阵的**外层 key**（源给的话号），不是从 chapterKey 里正则抠——comix.to 的 key 是整条 URL，抠不出话号。
- 同名兜底：同话号 + 同组名出现多版本时从第二个起追加 ` (2)`、` (3)`；序号由 `(chapters, key)` 唯一决定，两侧算出来必然一致。
- `LocalManager.getChapterDirectoryName` 保留但降级为"纯清洗器"，注释写明**不要用它算章节目录名**。

**为什么必须抽成单一函数**：改动前这条规则被抄了 **4 份**
（`download.dart:295`、`chapters.dart:1113`、`scaffold.dart:178`、`scaffold.dart:222`），
其中 `LocalManager.getImagesForComic` 用的还是**第五种**（不 parse，直接清洗 key）。
只要下载侧改了而读取侧没跟上，就是"下完读不到"。现在四处 + 删除路径全部走同一个函数。

## 3. 两个"计划外但必须做"的修正

### 3.1 目录名要带组，就得让已下载的旧目录跟着搬

没有迁移的话，升级后所有旧下载（目录是 `https___…` 或纯话号）瞬间读不到。
迁移逻辑刻意保守：

- 只处理 `chapters.isVersioned` 的行；
- 旧名 = `sanitize(parseChapterTitle(key).chapterNumber ?? key)`，新名 = `chapterDirectoryName(chapters, key)`；
- **组信息取不到 → 两者相同 → 跳过**（不猜、不删）；
- 目标目录已存在 → 跳过（可能是用户自己放的）；
- 一次性，标记写 `implicitData.chapterDirGroupMigration`（设备本地，不进备份）；
- 顺带把 `missing_pages.json` 里的 `chapterId`（存的也是目录名）做 remap，否则 S2 的红色"缺页"标记会静默消失。

放在 `LocalManager.init()` 里、**恢复下载任务之前**跑。

### 3.2 `preferDownloaded`：否则"只下载了非首选组"会打开空白页

带组目录一上，出现一个新洞：

```
用户只下载 DivaScans 的 ch.6  ->  磁盘目录 "6 [DivaScans]"
阅读器按话号取 ids[?]          ->  versions.first = Asura Scans 的 key
                               ->  目录 "6 [Asura Scans]" 不存在  ->  空白
```

改动前这反而是"能用"的：所有组都写进同一个 `6/`，撞车但读得到。
所以这是**带组目录引入的回归**，必须补。

解法不是改 `ids` 语义（会波及阅读器和历史键），而是把"已下载的版本"提到每话
`versions` 的**首位**——一维投影自然落在有内容的那个版本上，话号顺序不变，历史下标依然有效。
新增 `ComicChapters.preferDownloaded()` + `LocalComic.effectiveChapters`，
在 `_localDetails()`、`getImagesForComic()`、`isDownloaded()`、`read()` 四处生效。

代价：该话的自定义章节顺序（`ChapterOrderPrefs` 按 id 存）在"已下载版本≠原首选版本"时会退化成源顺序。
可接受，且比空白页好得多。

## 4. 决策与理由

| # | 决策 | 理由 |
|---|---|---|
| 1 | 目录形态用 `<话号> [组名]/`，**不**编码进图片文件名 | 硬红线。组名进文件名意味着改组要重命名整章 97 个文件 |
| 2 | 话号用版本矩阵外层 key，不用 `parseChapterTitle(chapterKey)` | comix.to 的 key 是整条 URL，正则抠不出话号（实测 `chapterNumber` 为 null） |
| 3 | 非版本化 / 取不到组名 → 保持旧目录名规则 | 零迁移、零风险；绝大多数源不受影响 |
| 4 | "下载全部"仍只取每话首选版本；只有用户显式勾选才可能下非首选 | 否则 comix.to 上"下载全部"会从 7 话炸成 59 话 |
| 5 | 选章器**默认只展开第一组**，"下载全部"只作用于展开的组 | 同上；组名与 `(N)` 在一屏内仍全部可见，"显示不全"照样解决 |
| 6 | U1 复用 `showAddToCollectionDialog`（加 `lockedCollectionId`）而不是在编辑页另写一套 | 成员构造（本地封面解析、displayMode、tab 名）是真实逻辑，抄一份迟早漂移 |
| 7 | 迁移标记写 `implicitData` 而不是 `settings` | 设备本地的一次性动作，不该进备份/同步 |

## 6. 踩到的坑

1. **目录名规则被抄了 5 份**，其中读取侧（不 parse）和下载侧（parse）本来就**不一致**。
   只是 comix.to 的 key 恰好 parse 不出话号才一直没出事。抽成单一函数后，这个潜伏分歧自动消失。
2. **`allChapters.keys` 不等于"所有章节"**：版本化下它只有首个版本。
   下载任务的匹配、选章器的行、组名显示，全都栽在这一条上。
3. **`ComicChapters.versioned` 会重排**。`preferDownloaded` 如果把结果塞回 `versioned`，
   刚提到首位的已下载版本会被 uploadedAt/组名排序立刻推回去 → 必须走 `versionedOrdered`。
4. **`MissingPageEntry.chapterId` 是 `final`**，迁移时不能就地改，只能重建整个条目。
5. **`Comic.subtitle` 不是 `subTitle`**（`subTitle` 是 `LocalComic` 的 getter）。选择器里第一次写错了。
6. 分析器报 `unnecessary_non_null_assertion`：`_versionedChapters != null` 之后已经提升，
   循环里再写 `_versionedChapters!` 是多余的 `!`。
7. **`tools/run_build_task.py` 需要 pywin32**，换解释器才跑起来（见 §5.1 注）。

# 附录：S7U 实机反馈修复 —— comix.to 下载 "Null check operator" (2026-10-06 15:40)

## 现象
GUI 首次实跑 comix.to 下载（对**已有本地副本**的 *My Dragon Girlfriend Has Returned* 再下载），
任务卡报 `Error: Null check operator used on a null value`，自动重试 3 次全炸。
日志（logs.txt）三个特征：① 崩溃前后**零 JS / 零 webview 日志**；② `error Download` 行**无堆栈**；
③ 18s/33s 间隔 = LocalManager 错误自动重试退避。

## 根因（链条完整还原）
1. 漫画已有本地下载 → 详情页 `_loadDetails` 走 `_localDetails()`（comic_page.dart:593），
   `cover` 被置为**本地文件名** `"cover.jpg"`。
2. 用户在此页发起下载 → `ImagesDownloadTask.comic.cover = "cover.jpg"`。
3. `resume()` 封面步骤 → `ImageDownloader.loadThumbnail(comic.cover, source.key)`（**不传 cid**）。
4. `images.dart` 的 `startsWith("cover.")` 相对封面分支 → `comicSource.loadComicInfo!(cid!)` → **`cid` 为 null → 空指针**。
5. 异常在进入 loadComicInfo 前同步抛出 → `_runWithRetry` 捕获成 message，堆栈被丢弃 → 与日志证据完全吻合。
6. 为什么以前没炸：首次下载时无本地副本，详情页 cover 是网络 URL，不进该分支。
   这是"重下/补下"路径的**潜伏 bug**，与 U3 改动无关，但 U3 的验证场景（同话再下另一组）必踩。

## 修复
- `images.dart` 相对封面分支：`cid == null` 或源不可用 → 抛**可读错误**
  `"Cannot resolve relative cover '$url' (source=…, comicId=…)"`，不再空断言。
- `download.dart` 封面步骤：`loadThumbnail(comic!.cover, source.key, comicId)` —— 传 comicId，
  让相对封面能借源网络详情反查出真实 URL（下载目录里落的是网络封面，语义正确）。
- `download.dart` `_runWithRetry`：最终失败时 `Log.error("Download", …, stackTrace)` —— **堆栈必须落日志**，
  否则这类错误永远无法定位。
- `download.dart` 裸 `!` 清理：`source.loadComicInfo!` ×2 → 判空后抛可读错误；
  `_loadPagesForDownload` 的 `source.loadComicPages!` → 判空返回
  `Res.error("The source does not support loading pages")`；3 处 `res.errorMessage!` 日志 → `?? "unknown error"`。

## 关联核查（未改）
- `LocalManager.add()` 对 `downloadedChapters` 做并集（local.dart:574-579）→ 重下同话另一组不会丢旧记录。
- `loadEp` 接受完整章节 URL（任意版本 key）→ 与 U3 的按组选择兼容。
- `local_favorite_image.dart:42` 也无 cid 调 loadThumbnail，同样 URL 形态会走新抛的可读错误（收藏封面本就有占位降级，不修）。

# 附录 4：S12 第三轮——两任务被合并、卡第0页、副标题不显示（2026-10-06 17:05）

## 用户复测反馈（上一轮 BUILD 后）
① Diva ch.2 只下 3 张就跳到 ch.1（并行不成立）；② 下载页仍把两章堆在

直接卡在第 0 页不动。

## 🔍 三处根因（全部实锤）
1. **两个任务被合成一个**——`ImagesDownloadTask.==` / `hashCode` 只按
   `comicId + source.key` 判等。下载页 `_syncListeners` 用 `downloadingTasks
   .toSet()`（downloading_page.dart:57），且卡片 `ValueKey(task)`——两个同漫画
   不同章节的任务被判相等，`toSet()` 直接合并成一项、重复 ValueKey 让 UI 只
   渲染一张卡。这就是"任务堆一起、并行不成立、副标题看不全"的统一根因。
2. **卡第 0 页（头阻塞冻结）**——上一轮我把"图片池"改成了"5 张一批、等满
   整批才继续"。但 comix 图片通道是**全局 `_ComixImageWorker.laneCount = 3`**
   条 WebView lane（comix_client.dart:1394），所有任务共享这 3 条；叠加我
   当时额外加的 `_imageSlots=5` 全局槽位与 3-lane 池打架。**Diva 轮换域
   403 挂起图**在严格批里会撑满整批、整章停在 page 0 直到最慢那张超时——即
   "卡死"。且单张失败图最坏 = 3×3×3×90s ≈ 18 分钟才让位（重试预算失控）。
3. 副标题被"遮住/不显示"是现象 1 的连带：合并不了的第二张卡本来就该显示
   subtitle，但 `==` 合并后只剩一张、且 toSet 取第一个任务，副标题自然残缺。

## 修复（BUILD_OK + headless 14/14、5/5）
- **download.dart**：
  - `ImagesDownloadTask.==` / `hashCode` 纳入 `chapters`（内容比较）→ 同漫画
    不同章节任务判为不同项，`toSet()`/`ValueKey` 不再合并，下载页出现**多张
    独立卡**、各自可暂停/取消、队列并行度内并行。**这是并行与副标题显示的
    真正开关**。
  - 删除冗余的全局 `_imageSlots`（与 3-lane 池冲突、制造死锁风险）。
  - `_downloadChapterPool` 重写为**滚动窗口并发**：维持最多 `_maxInFlight=3`
    （== laneCount）张在途，任意一张到终态立刻补下一张，**绝不因某张慢图
    阻塞整批**；响应暂停。彻底消除"卡第0页"头阻塞。
  - 新增 `_launched` 指针（与 `_index` 前沿区分），支持断点续传从已完成数续起。
  - `_imageRetryLimit` 2→1（下载 wrapper 层）。
- **images.dart**：下载模式收紧——`webviewTimeout` 90→30s、重签 `retryLimit`
  下载模式 3→1（Diva 持久 403 重签无益）；配合上面的滚动窗口，单张失败图
  最坏 ≈ 30×(2+1)×1 = 90s 即让位记 missing，不再冻结整章。comix_client 的
  cache/reload 缓解仍需 30s 预算（足够）。
- 副标题 getter 本身正确，无需改；其"不显示"随任务拆分一并解决。

① 选 Diva ch.1+ch.2 → 下载页出现**两张独立卡**、副标题带"comix · DivaScans ·

# 附录 5：S12 第四轮——403 真因（导航落地 null/about:blank）、按组下载问题、整体强化（2026-10-06 18:10）

## 日志证据（用户复测 + 本轮抓取，17:5x~18:0x）
```
navigate landed on null
fetch status=403 error=http 403
navigate landed on about:blank
fetch status=0 error=TypeError: Failed to fetch
lane hard timeout, resetting: image timeout for https://447.hannahjournal.site/hi/bEqPbYfo...

```
🔴 **关键实锤**：DivaScans 章节图片走 `*.site` 轮换域（`447.hannahjournal.site`、`rxn.kaylablog.site`、`lov.softstyleboutique.site`…）——**WebView 导航本身就失败**（`getUrl()` 返回 `null` 或落到 `about:blank`），同源 fetch 一律 403。即：这些域有**比 `static.comix.to` 更强的反爬/TLS 指纹层**（comix_to.js 注释第 27-30 行已明示"轮换域有按 TLS 指纹拦截的 CF WAF"），**连无头 WebView2 都过不去**。Asura 章节走 `static.comix.to` → 导航 200、正常下载。**这不是软件 bug，是源侧封锁。**

## 用户问题 3 的答案：各翻译组是否都有类似问题
**取决于 comix.to 把该章图片分发到哪个宿主（服务器侧、代码不可枚举）**：
- 走 `static.comix.to`（如 Asura）→ WebView 可过，**能下载**。
- 走 `*.site` 轮换域（如 DivaScans）→ 导航失败 + fetch 403，**系统性不可下载**。
- 同一章内 URL 的 `/hi/<token>` 路径段完全一致，子域只是轮换；token 可作"按章封锁"的判定键。
- 结论：**所有组都"可能被封锁"，区分维度是宿主而非组名**；用 `*.site` 的组目前客户端无解，只能等待/绕过反爬（见末节）。

## S12 整体强化（BUILD_OK + headless 14/14、5/5）
1. **comix_client 主机封锁检测 + 快失败**（核心）：按 `/hi/<token>` 抽"章节 token"，
   连续 2 次 403/导航失败 → 判定该章整批"主机封锁"，后续同 token 图片降级为 **6s
   短超时、不再叠加重签/重试预算**。一个 20 图封锁章从"每张 30~90s"压到"2×30s + 18×6s
   ≈ 2.8 分钟"收尾为 N missing，而非把队列拖死。**正常宿主（static.comix.to）永不 403，
   不会被误判**。修复任务走同一 `fetchImageBytes` 自动受益。
2. **JS `downloadTimeoutSeconds` 90→30**：与用户"每图 30s 即证明无效"一致；单图
   最坏 30×(重签1+net1)×wrapper1 ≈ 90s 让位（配合快失败封锁章更快）。
3. **download.dart 续传跳过已存在页**：wrapper 启动时若 `$index.*` 已落盘 → 直接判完成，
   不重复拉取（重下/修复整章时不再重拉已好的页）。
4. **状态提示增强**：章节状态含"N missing"；累计 2 次封锁症状 → 追加"host blocked"，
   明确告知用户缺失是源侧封锁而非软件故障。
5. 修复页入口已存在（本地库/详情页"Repair missing" + missing_pages 弹窗），本轮
   强化后修复跑同样快失败，不会 30s×每张。
