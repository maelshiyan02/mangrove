# P5.1 工作日志 · S1 下载进度可视化

> 日期：2026-10-05　|　阶段：P5 分阶段计划 **S1**

## 1. 需求

- 之前只有"任务"页能看到下载进度；"本地 → 下载中"标签下的卡片是静态的，看不到任何进度，只能去文件夹里翻。
- 目标：在图书馆卡片上直接看到下载进度（百分比 / ETA），并能就地暂停、继续、取消。

## 2. 现状调研结论

| 事实 | 位置 |
| --- | --- |
| 进度数据其实**早已齐备**：`progress` / `speed` / `eta` / `message` 都在 `DownloadTask` 上 | `lib/network/download.dart:28-51` |
| "任务"页有完整的进度条+速度+ETA+暂停/取消渲染 | `lib/pages/downloading_page.dart`（`_DownloadTaskTile`） |
| 本地页的"下载中"标签只做状态过滤，卡片走通用 `SliverGridComics`，**没有进度通道** | `lib/pages/local_comics_page.dart:387`、`lib/components/comic.dart` |
| 本地页只监听 `LocalManager`（任务增删时刷新），**不监听任务本身** → 即使画了进度条也不会每秒更新 | `local_comics_page.dart:89` |

也就是说：**缺的不是数据，也不是渲染能力，缺的是"卡片 → 任务"这一条线**。

## 3. 方案选择

两个候选：

- **A（采用）卡片覆盖层**：给通用卡片加一个**可选**的进度覆盖层（底部细进度条 + 短标签），本地页按 comic 查到对应任务后传入。
  - 优点：所有标签（全部/已下载/下载中）都能看到进度，不只在"下载中"页；网格布局不变；不破坏其它 20+ 处调用方（新增参数可选，默认 null 即原样）。
- B（未采用）"下载中"标签整段替换为任务列表瓦片
  - 缺点：只有切到该标签才看得到进度；布局风格突变；任务瓦片与卡片两套交互。

**配色沿用 S3 已约定的语义**（本阶段先落在卡片上）：黄 = 下载中 / 灰 = 已暂停 / 红 = 出错。

| 未改动 | `download.dart`、`downloading_page.dart`（进度数据与任务页渲染本来就有，不动） |

### 两个实现细节（避免踩坑）

1. **进度通知只重绘，不重查库**：`LocalManager` 变更走 `update()`（重建列表），任务进度通知走 `_onTaskProgress()`（只 `setState`）。否则每秒一次的进度回调会触发整表查询。
2. **`LocalManager` 的监听函数换了**：原来直接挂 `update`，现在挂 `_onLocalChanged`（先同步任务监听，再重建列表），保证新任务一进队就有进度回调。

# 追补（2026-10-05 17:00）：S1 验收反馈修复 —— 下载按钮丢失 · 章节标签配色 · 下载卡死

> 用户 S1 验收时报告 4 个问题（截图 3 张）。前 3 个属于"下载入口/状态可见性"，第 4 个是**下载管线卡死的硬 bug**。全部当轮修复并重构建。
> 产物：**BUILD_OK，app.so 17:15，analyze 无 error**

## A. 问题 1：已下载漫画的详情页下载按钮消失

**根因**（`comic_page.dart:855`）：appbar 的下载按钮包在 `if (!isDownloaded)` 里，而 `loadData()`（comic_page.dart:544）对**任何在本地库里的漫画**（哪怕只下了 1 章）都置 `isDownloaded = true` → 只要下载过，按钮整个消失，用户无法再补下其余章节（"My Dragon Girlfriend Has Returned"截图场景）。

**修复**：显示条件改为 `comicSource != null`（有网络源就显示下载按钮）。纯本地导入（sourceKey=local）仍不显示——点了也只会得到 "Comic source not found"。`download()` 内部对"无章节且已下载"的提示逻辑保留；对有章节的漫画，对话框里已下载章节预勾选并禁用，其余章节可继续选（`LocalComic.chapters` 存的是源的**全部**章节，已核实 download.dart `toLocalComic()`）。

## B. 问题 2：章节标签状态配色（原 S3-a 提前落地）

按用户确认的四态语义实现（`chapters.dart`，普通视图 + 分组视图两个网格都生效）：

| 状态 | 底色（浅色主题 / 深色主题） | 文字 |
| --- | --- | --- |
| 基础 | 主题 surfaceContainerLow（白） | 默认，已读灰字保留 |
| **下载中** | #FFE082 / #4E4011 | #7A5900 / #FFD54F |
| **已下载** | #BBDEFB / #1D3A5F | #0D47A1 / #A6C8FF |
| 选中（批量选择） | primaryContainer | onPrimaryContainer |
| 缺页/失败（红） | **S2 落地后接入**（无可靠数据源，先留扩展位） | — |

实现：`_ChapterChipColors`（底色+文字色对）+ `_chapterChipColor(key, isSelected)`；数据源 `LocalManager().find(...).downloadedChapters`（已下载）与 `downloadingTasks` 的 `chapters` 字段（下载中，`null` 表示整部在下载）。优先级：选中 > 下载中 > 已下载 > 基础。

**已知限制**：详情页不监听 LocalManager，下载状态变化要等页面重建才刷新颜色（离开再进即可）；S2 时一并接通知。

## C. 问题 3：下载章节选择列表不显示翻译组

**根因**：`_SelectDownloadChapter` 只渲染 `eps[i]` 标题（截图里只有 "Ch.60..."）。

**修复**：新增 `chapterGroups` 参数（按章节下标对齐的组名，来自 `ComicChapters.scanlationGroupAt(i)`），列表行以 subtitle 显示（12号 outline 灰字）。comix.to 这类多组同章源的版本区分不再靠猜。

## D. 问题 4（硬 bug）：下载到第 3 张图永久卡死（0 B/s，2/111，约 19h）

**日志证据**：16:51:16 Lane0/Lane1 启动并各取 1 张（55KB/64KB），此后**再无任何输出**——第 3 张图轮到 Lane2 启动 WebView 时挂起。

**根因链**：
1. v0.6.4 的 3 条图片 Lane **各自** `WebViewEnvironment.create` **同一个** userDataFolder（`{data}\webview`）——第三条 Lane 的 environment 创建/`webview.run()` 并发执行时**永久挂起**（无日志、无异常）。
2. `_ensure()`（启动）**没有任何超时**；Lane 内部的 deadline 只覆盖导航后的回读段 → 挂起永不暴露。
3. 下载并发池（`downloadThreads=5`）等 `Future.any(pending)`，挂起的第 3 张既不完成也不失败 → 整个任务 0 B/s 冻结。

**修复**（`comix_client.dart`）：
1. **共享 Environment**：新增 `_getSharedWebViewEnvironment()`（全局单例 + 共享 future 去重），采集 Worker 与所有 Lane 共用同一实例。
2. **启动串行化**：`_withWebviewStartupLock` 全局启动互斥，WebView2 的 environment 创建 + headless run 不再并发。
3. **整体硬超时**：`fetchImageBytes` 外层 `.timeout(timeoutSeconds + 8s)` 兜底——任何一层挂起都会浮出水面。
4. **挂死后重建**：超时触发 `lane.reset()`（dispose WebView、清 `_starting`、**重置导航互斥链**——卡死的 fetch 永远走不到 finally，不重置链会拖死后续所有请求），下次取图自动重建。

**经验教训**：
8. **多 WebView 共用一个 userDataFolder 时，environment 必须共享、启动必须串行**。WebView2 对"并发创建同文件夹 environment"的行为是静默挂起而非报错——这类故障只能靠日志缺口发现。
9. **超时保护必须覆盖"取资源前的准备段"**。`_ensure()` 这种"应该很快"的调用恰恰是最可能永久挂起的地方；deadline 只护住主体流程等于没护住最脆弱的环节。
