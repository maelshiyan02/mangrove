## 二、实现

### 2.1 命令模型携带 `pageKey`

P9.0 §七.4 第 2 条点名的**隐藏前置**：`ProjectEditCommand` 原本不携带 `pageKey`，`captureBlockEdit`/`captureBlockListEdit` 也不接收 → **"哪些页脏了"这个信息根本拿不到**。

改动（`lib/foundation/translation_project/edit_command.dart`）：

- 基类 `ProjectEditCommand` 新增抽象成员 `String get pageKey`（本命令改动的页，即 `pages[pageKey]`）。
- `BlockEditCommand` / `BlockListEditCommand` 各实现它（`@override final String pageKey`）。
- 两个 `capture*` 辅助函数的 `pageKey` 声明为 **`required`**，而非可选。

> 🔴 **为什么是 `required` 而不是可选**：一个"忘记自己属于哪一页"的命令会**静默掉出脏页集合**，让 `result/` 在磁盘上保持陈旧而 JSON 说是新的——**正是本仓库反复踩到的静默分叉类 bug**（参见 `local.dart` 的 `add()`/`INSERT OR REPLACE`、以及 `page-reconcile` 之前恒返回空的那次）。宁可编译期报错。
>
> 📌 这个设计也顺带补上了一个**未来的漏登记风险**：P0-2/P1-5 批量建块若新写捕获路径，`required` 会让它们**编译期就暴露**出来，而不是悄悄漏登记。

### 2.2 `EditHistory.dirtyPages`：重算而非增量维护

```dart
Set<String> get dirtyPages {
  final dirty = <String>{};
  final savedStates = <String, Object?>{};
  // 保存点之后的 undo 栈 = 未保存的工作
  for (var i = _savedIndex; i < _undo.length; i++) {
    final c = _undo[i];
    dirty.add(c.pageKey);
    savedStates.putIfAbsent(c.pageKey, () => c.beforeState);
  }
  // redo 栈里的命令只在"该页仍有未保存改动"时才算脏
  for (final c in _redo) {
    if (!savedStates.containsKey(c.pageKey)) continue;
    dirty.add(c.pageKey);
  }
  return dirty;
}
```

**核心决策：重算，不做增量集合。**

| | 增量集合（push 加 / undo 减） | 本实现（重算） |
|---|---|---|
| 编辑一页 | ✅ | ✅ |
| 撤销回保存点 | ⚠️ 要在 `undo()` 里判断"这页是否回到保存态"，漏一条就是**假脏 → 白重渲** | ✅ 天然正确：`_savedIndex` 之后的栈为空且 redo 不含已保存态页 → **集合为空** |
| `limit` 截断（丢最老命令） | ⚠️ 丢掉的命令若恰是某页唯一的脏来源，该页会漏 | ✅ 无此路径 |
| 新增 undo/redo 路径 | 每次都要记得维护 | ✅ 无需维护 |

`dirtyPages` 的复杂度是 `O(命令数)`（`limit` 上限 200），远小于渲染成本。

**实现期的一次自我修正**：初版还给基类加了 `beforeState`/`afterState` 两个抽象成员，打算用"比较页内容"来判断是否回到保存态。写到一半发现**逻辑根本不需要比较内容**——只需要知道"这页在 undo 栈上还有没有未保存的命令"，是个纯集合成员问题。两个成员因此被删掉（留着就是无用 API 面 + 徒增实现类的负担），判定退化为 `unsavedPages` 集合的 `contains` 查询。**教训：动手前先问"我真的需要这个状态值吗"，比事后删干净更省。**

**已登记的已知取舍**：某页若在未保存期间"改了又改回"（净变化为 nil），仍会留在集合里 → 多渲一页。这是**刻意选择**：要在保存时精确判断净变化，得逐页比对整页 JSON，成本高于省下的那次渲染。

### 2.3 保存路径：先取快照，再 `markSaved`

```dart
// 🔴 必须先取快照：markSaved() 正是把页面变"干净"的那一步
final dirtyPages = _history.dirtyPages;
final report = await ProjectWriter.save(...);
_history.markSaved();
...
unawaited(_regenerateResults(dirtyPages: dirtyPages));
```

🔴 **这是本项最容易写错的一行**：若在 `markSaved()` **之后**取 `dirtyPages`，集合恒为空 → 传 `filter` 等于什么都不渲 → `result/` 永久陈旧，且**没有任何报错**。

`_regenerateResults` 的参数语义也已明确区分（避免"空集"被当成"不知道，全渲"）：

| `dirtyPages` | 含义 |
|---|---|
| `null` | **不知道** → 全量渲（无脏页信息调用者的默认） |
| 空集 | **确实没有脏页**（用户撤销回保存点）→ 一页都不渲 |
| 非空集 | 只渲这些页 |

日志同步加了 `dirty=${dirtyPages?.length ?? 'all'}`，便于实机核对。

## 四、`edit-check` 新增的 8 项断言

全部围绕"脏页追踪是否**精确**"，而不只是"有没有变脏"：

| 断言 | 验证什么 | 增量实现会不会挂 |
|---|---|---|
| `dirty.after_edits` | 三次编辑后集合**恰好**是那一页 | — |
| `dirty.two_pages` | 编辑第二页后集合**扩到两页** | ❌ 会挂（做成单一标志位） |
| `dirty.undo_shrinks` | 撤销第二页后集合**缩回一页** | ❌ 会挂 |
| `dirty.undo_keeps_own_page_out` | 被撤销的那页**不进**渲染集 | ❌ 会挂 |
| `dirty.empty_at_saved_boundary` | 全部撤销回保存点 → 集合**为空** | ❌ 会挂（最关键的一条） |
| `dirty.back_after_redo` | redo 后该页**重新变脏** | ❌ 会挂 |
| `dirty.filter_selects_one` | `planArtifacts(filter:)` 只选出 **1 个** artifact | — |
| `dirty.full_plan_is_larger` | 不带 filter 时计划数**更大**（`97 vs 1`），证明增量确实收窄 | — |

`dirty.empty_at_saved_boundary` 是本项的判别性用例：**一个刚打开的工程 `_savedIndex == 0`，撤销全部编辑就回到保存边界**，此时脏页必须归零。增量集合实现必然在此时留下"假脏"，导致用户每次撤销后保存都白渲一章。

|---|---|---|

> 📌 **教训**：断言"集合被收窄"时，**必须先证明未收窄的那侧非空**。否则"全部被跳过"和"过滤器正常工作"会给出同一个 `[]`，测试假绿。已把这条写进断言注释。
