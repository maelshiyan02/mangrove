## 1. 坑① 假缺页：12 页的 Ch.2 其实是 88 页

### 现象

Ch.2 目录里只有 12 个图，App 显示"已下载"，界面上看不出任何异常。

### 根因

comix 阅读器在视口内并发拉 80+ 张图，经本地代理时 Chrome 报
`net::ERR_HTTP2_PROTOCOL_ERROR`；**站点不重试**，节点永久停在
`is-errored`，`img.src` 被清空。旧版脚本把这些节点当"空节点"丢弃。

### 修法（已在 `SRC_PATCH_JS`）

`Page.addScriptToEvaluateOnNewDocument` 在页面脚本**之前**注入，拦
`HTMLImageElement.prototype.src` 的 setter，把真实地址存到 `el.__srcVal`。
加载失败也能回收 URL，python 侧自己下（独立连接 + 3 次重试 + 换域名回落）。

### 实测

Ch.2 一次会话**救回 68 个失败节点**，最终 88/88。没有这个补丁这章不可能下全。

> 详细判据见 **A17 §2**。本节只在提醒：**页数少 ≠ 源站缺页**，先怀疑 HTTP2。

## 2. 坑② 完整性判据把"没有记录"当成"完整"（Ch.2 长期不补的真凶）

### 有 bug 的代码

```python
complete = (
    bool(have)
    and not prev_rec.get("pending")
    and not prev_rec.get("failures")
    and (prev_nodes == 0 or len(have) >= prev_nodes)   # ← 这里
)
```

### 为什么致命

`prev_nodes == 0` 表示 **manifest 里没有这一章的记录**（旧版下载器产物）。
括号里那半边恒真 ⇒ 只要有图、没 pending、没 failures，就判定"完整"。

⇒ **所有旧版残章永远跳过，永远补不上。** Ch.2 的 12 页就是这样活了一个多月。

### 修法

```python
complete = (
    bool(have)
    and not prev_rec.get("pending")
    and not prev_rec.get("failures")
    and prev_nodes > 0                      # 没有记录 ≠ 完整，必须有依据
    and len(have) >= prev_nodes
)
```

无记录章节现在会被判"不完整"→ 走重下分支。**副作用**：其余 4 本 comix 单章
和 My Dragon Girlfriend 9 章下次跑会自动重下（这是期望行为，不是回归）。

## 3. 坑③ 安全删除守卫会**半路截断**整章重下（最阴的一个）

### 现象

```
[2/5] Ch.3 检测到残留（64/65 页）→ 重下本章
[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED] {"count":50,"threshold":50,"scope":"turn"}
[relay] 批次结束 rc=1
```

进程**无异常、无 traceback**，直接退出。看起来像被站封了。

### 根因

本机 `safe-delete` 守卫：**单回合删除 > 50 个文件必须人工确认**。
整章重下要先删掉旧页，65 页的章节删到第 50 个就被拦死。

### 二次伤害

它是**删到一半**才停：Ch.3 从 64 页变成 **15 页**，比不删更糟。

### 修法：移动替代删除

```python
stale_dir = ch_dir / ".stale" / datetime.now().strftime("%Y%m%d_%H%M%S")
for stale in have:
    shutil.move(str(stale), str(stale_dir / stale.name))
```

移动不是删除，**不受守卫限制**，而且可回滚。

```
[1/5] Ch.3 旧页 15 个已隔离到 .stale/20261024_172959/（不删，可回滚）
```

### 清理阶段的同一坑

`.stale` 累积到 **124 MB / 5 个目录 / 347 个文件**，逐个删又会被守卫拦。
解法：**整体移动目录**（`shutil.move` 一个目录 = 1 次操作），移到
`ComicLibrary/downloads/_trash_20261024/`，漫画目录内 `.stale` 归零。

> 通用规则见 **A01 §4**（删除配额）与 **A20 §3**。

## 4. 坑④ `--force` 反而**不会**清理旧页

### 有 bug 的结构

```python
if ch_dir.is_dir() and not args.force:      # ← 清理逻辑整个写在"非 force"分支里
    ...清理旧页...
```

`--force` 跳过整个块 ⇒ **带 `--force` 重下时旧页一个都不动**。

### 后果

新旧下载器的扩展名算法不同（旧 `.jpg` / 新 `.webp`），同一页出现两个文件：

| 阶段 | Ch.49 文件数 | 页数 |
|---|---|---|
| 旧版下载完 | 95 个 `.jpg` | 95 |
| `--force` 重下后 | 95 `.jpg` + 95 `.webp` | **190**（阅读器显示 190 页） |

### 修法

`--force` 也先走隔离流程，再开始下载。隔离后目录里只有本次写入的文件。

### 事后合并（不重下的补救）

先逐张比对 md5，确认内容完全相同（**95 对全部相同**），再用
`os.replace(jpg, webp)` **覆盖**而不是删除 ⇒ 190 → 95 页纯 `.webp`。
覆盖不触发守卫。

## 5. 坑⑤ 扩展名是从 URL 猜的 ⇒ 877 个 webp 被存成 `.jpg`

### 事实

comix 的图片 URL **一律带 `.jpg` 后缀**，实际响应是 **WEBP**。
旧代码：

```python
ext = "webp" if ".webp" in url else ("png" if ".png" in url else "jpg")
```

⇒ 全库 **877 个 `.jpg` 里装的是 WEBP 数据**（magic `RIFF…WEBP`，
`.jpg` 与 `.webp` 字节数完全相同）。

### 为什么之前没被发现

Flutter / Chrome 解码看 **magic** 不看扩展名，所以**阅读完全正常**。
唯一的爆发点是坑④ —— 换扩展名算法后新旧并存。

### 修法

新增按文件头判型（12 字节，零开销）：

| magic | 判定 |
|---|---|
| `RIFF` + `WEBP` @8 | webp |
| `FFD8` | jpg |
| `8950 4E47` | png |
| `GIF87a`/`GIF89a` | gif |

替换三处 URL 猜测点：`save_payload` 主路径、dataURL 兜底、`download_image` 落盘。

### 🔴 改名必须先分类，不能一把梭

全库 `.jpg` 分两类，**只有一类该改**：

| 类别 | 数量 | 处置 |
|---|---|---|
| 假 `.jpg`（内容是 WEBP） | **877** | 改名为 `.webp` |
| 真 JPEG（`cover/[cover]season(N).jpg` 8 张 + cos写真 1332 张） | **1,340** | **保持不动** |

一刀切会把 1,340 个真 JPEG 的名字改错，**比不改更糟**。

改名用 `os.rename`（不写盘、不删、不触发守卫），秒级完成。

## 6. 坑⑥ `ls -t` 判断下载进度是**错的**，害我误杀过进程

### 两次误判

| 场景 | 我的错误判断 | 实际 |
|---|---|---|
| 用户问"是否卡住了，磁盘没变化" | 以为没在写 | 正在写（Ch.7 最新页就是当前秒） |
| 我查 Ch.13 是否被拦截 | 看到最新文件是 `080.webp`，以为下到 80 页就断了 | Ch.12 实际 86 页全在，`080` 只是**最后写入**的 |

### 根因

并发下载（workers 8~28）**写入顺序是乱的**。`ls -t` 按 mtime 排序，
最后一个落盘的文件**根本不是页码最大的那个**。

### 正确判据

**只看 manifest**：`saved` / `nodes` / `pending` / `failures`。

```python
m = json.load(open('_manifest.json'))
(m['nodes'], m['saved'], len(m['pending']), len(m['failures']))
```

> 推论：**"最新文件时间"不能当心跳**。要判活看进程状态 + manifest 增量。

## 7. 坑⑦ "被拦截"的误判：三个信号一个都没有就不是拦截

真被反爬拦的判据（任一成立）：

- `pending` 或 `failures` **非空**
- 日志出现 `Third-party` / `Just a moment` / `Cloudflare` / `503`
- 进入 300s 熔断

Ch.13 三个信号**全零**，只是**上一批被中断、根本没启动**（manifest 无记录）。
重跑后 99/99、97s，站点完全正常。

⇒ **判断"是否被拦"要看 manifest 与日志关键字，不要看进度停在哪。**

## 9. 坑⑨ `--numbers` 的两个陷阱

1. **解析成 `set`**，遍历顺序由 `chapters.json` 决定 ⇒ **不能用它控制优先级**。
   要按顺序补，就一次一批、按批次调用。
2. **不带 `--group` 会命中该话所有组**：`--numbers 48` 曾命中 7 个翻译组，
   建了 7 个目录，事后要清理重跑。**永远带 `--group`。**

## 10. 坑⑩ 进程管理：`nohup &` 会被 shell 退出带走

- `nohup ... &` 在非交互会话里会被 shell 一起终止（`gap_fix_relay.sh` 试过）。
- 必须用**受任务托管的后台**，或本次最终采用的**前台逐章实时监控**。
- 杀进程要杀**真实 Windows PID**：Git Bash 的 `ps -ef` 显示的是 MSYS 虚拟 PID（如 594），
  对着它 `taskkill` 无效。要用：
  ```powershell
  Get-CimInstance Win32_Process -Filter "Name='py.exe' OR Name='python.exe'" |
    Where-Object { $_.CommandLine -like '*comix_browser_dl*' }
  ```

## 11. 坑⑪ 构建卡 INSTALL ≠ 构建失败

- 现象：`step_4_install` 卡住 / rc≠0，看起来像编译出错。
- 真因：`mangrove.exe` 正被运行中的 App 占用（PID 22160）。
- **先看 `app.so` 与源码 mtime**：`app.so` @17:03、Dart 源码最后改动 16:54
  ⇒ 编译其实早成功了，只是装不进去。重跑时 build 阶段显示 "up-to-date" 是**正常的**。
- 处置：让用户**关掉 App** 再跑，不要重复分析代码。

## 12. 核验铁律（这一节的结论比坑本身重要）

页数够 ≠ 下载完整。全本验收要**同时**过五项：

| # | 检查项 | 判据 | 本次结果 |
|---|---|---|---|
| 1 | 页数 | `落盘页数 == manifest.nodes`（逐章） | 50/50 相等 |
| 2 | 扩展名 | 章节内**零**非 `.webp` | 0 |
| 3 | 页号连续 | 排序后 == `1..N`，无跳号 | 全部连续 |
| 4 | 字节完整 | `RIFF` 声明长度 + 8 == 实际文件大小 | 29260/29260 通过 |
| 5 | 目录命名 | 匹配 `<话号> [组] [站]` | 50/50 合规 |

**只查页数会漏掉全部四类问题**：截断文件、重复文件、跳号、命名漂移。

### 一个必须会分辨的"假警报"

有 **487 个 webp 小于 1KB**，看着像坏图。实际全是 `扔掉的渣男`（baozimh）
的 **640 宽长图切片边缘**（`640x1`、`640x4`）—— 源站按 640 宽切长条图，
切点必然产生极窄片段。**这是源站特性，不是下载损坏。**

⇒ 小于 1KB 的文件**要解码看尺寸再判**，不能按体积一刀切。

## 13. 提速阶梯（实测数据）

`--restart-each`（每章独立浏览器 + 全新 profile）逐章跑：

| workers | 单章耗时 | 取链耗时 | 备注 |
|---|---|---|---|
| 8（默认） | 238–523s | 75–80s | 太慢 |
| 12 | 142s | 16s | |
| 20 | 90s | 43s | |
| **28** | **58–190s** | 17–49s | 全程零失败 |

### 反直觉结论

**130+ 页的大章节反而更快**（Ch.35 132 页 / 58s），
因为**瓶颈在取链（DOM 收集）不在下载**。取链 17s 时，132 页也是 58s 完事。

### 拦截风险实测

`workers=28` 全程 **39 章零失败、零 pending**，没有出现 Cloudflare / 503。
配合 `--gap 20,35`（章间随机冷却）+ `--restart-each`（不复用会话），没触发封禁。

> 但这不等于可以无脑提速：**每章一次文档导航**是反爬底线（A07c），
> 提速只能提**单章内并发**，不能提**章间频率**。
