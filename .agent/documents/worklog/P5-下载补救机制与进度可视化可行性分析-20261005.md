## 一、现状梳理：VeneraX 目前如何下载 comix.to 漫画

### 1.1 下载链路

```
ImagesDownloadTask (download.dart)
  ├─ loadComicInfo → 章节列表（comix_to.js loadInfo → WebView HTML 降级通道）
  ├─ 每章 _loadPagesForDownload → loadComicPageInfo(forDownload:true)
  │    （comix_to.js loadEp → 常驻 WebView 截获 /api/v1/chapters/{id}）
  └─ 每章 _downloadChapterPool（并发池，进度前沿推进，#2）
       └─ _ImageDownloadWrapper（每张图）
            ├─ loadComicImageUnwrapped(forDownload:true) → viaWebview
            │    → _ImageLane 池（3 通道导航优先，90s×3 次下载级预算）
            ├─ 魔数校验：detectFileType 必须 image/*，且 ≥100 字节（#14）
            └─ 落盘：{index}.{ext}（按字节魔数定扩展名）
```

### 1.2 关键事实（纠正一个记忆偏差）

**VeneraX 目前没有"跳过失败页"策略。** `download.dart:401-407`：
任何一张图耗尽 `_ImageDownloadWrapper` 的 3 次重试 → `t.error != null` →
**整个任务 `_setError` 失败，整章作废**（已下载的文件还在磁盘上，但任务标记错误）。

"失败页跳过 + 记录 + 补救"这套策略在 **BallonsTranslator** 里
（`ui/download_dialog.py`），VeneraX 尚未移植。这正好是本次要补的洞。

### 1.3 完整性现状：**没有任何缺失页记录**

- 落盘只有图片文件本身，**章节目录内没有清单文件**（无 FT 工程 `_source_urls.json` 的对应物）。
- 阅读时 `local.dart:getImagesForComic` 直接列目录排序，缺一页就是"总页数少一页"，
  **无任何提示**——读者根本不知道看了残本。
- 数据库 `LocalComic` 只有 `downloadedChapters`（章级），无页级信息。

### 1.4 下载进度可视化的现状（对应截图问题）

截图是 **本地 → 下载中** 标签：卡片只显示漫画信息（标题/作者/进度条无）。
而进度数据其实**已经存在**：`DownloadTask` 本身暴露 `progress / speed / eta / message`，
且任务页（`downloading_page.dart`）已经有完整的进度条 + 速度 + ETA + 状态行渲染。

缺的不是数据，是**本地页"下载中"标签的卡片没绑这些数据**，以及没有全局入口能
一键看到"当前在下载什么、到哪了"。

## 二、FT 工程的 comix.to 下载代码：哪些可参考、哪些不能照搬

参考源：`Ballonstranslator_win_minium/ballontranslator/ui/download_dialog.py`（698 行）、
`utils/scraper/comix_client.py`（339 行）。

### 2.1 可以直接借鉴的（框架级，与传输通道无关）

| FT 工程 机制 | 细节 | 移植价值 |
| --- | --- | --- |
| **失败页清单** | `failed_pages: [{page, url, error}]` 每章一份，**落盘**到 `_source_urls.json` | ★★★ 核心机制，直接对应 VeneraX 缺失的清单层 |
| **补救 Worker** | `RedownloadFailedWorker`：`scan_failed_pages()` 扫描所有清单 → 逐张重下 → 成功后从 `failed_pages` 移除并追加到 `pages`，**清单与磁盘状态保持一致** | ★★★ 补救闭环的完整参考实现 |
| **分组限速** | 5 张/组、组间歇 1.5s——CDN 连续 >10 张易 ReadTimeout/503 | ★★ VeneraX 现在是并发池无组间歇，加上可降失败率 |
| **部分成功语义** | 有失败页时整体仍算完成，但 `failed` 信号带前 20 条失败明细，主线程弹"部分成功"提示 | ★★ "跳过≠成功"的 UI 语义参考 |
| **原子落盘** | `.part` 临时文件 → `os.replace` 改名，防半成品被当已下载页 | ★★ VeneraX 直接 `writeAsBytes`，中断可留坏文件（虽有魔数校验兜底，但只在下载时校验） |
| **解码校验** | `download_image` 内 PIL 真解码（`validate=True`） | ★ VeneraX 现在只查魔数+大小，伪图（截断的 webp）能溜进来 |

### 2.2 不能照搬的（传输通道已根本不同）

FT 工程的 `comix_client.py` 是 **requests 直连 CDN**（timeout(10,90)、retries=5、
cache-bust、指数退避 `min(2^n,30)+jitter`）。**2026-10 起 comix.to 的 CDN 按
TLS 指纹拦截 dio/requests（1020），FT 工程的直连通道本身已失效**。

- VeneraX 的取图必须走 WebView 通道（`_ImageLane`，已实现），FT 工程的"直连+退避"
  参数只对补救 Worker 的**重试预算设计**有参考意义，具体数值要在 WebView 通道上重新标定。
- WebView 通道是导航互斥的（3 通道并行），"组间歇"在通道层实现（Lane 级节流）
  比在任务层实现更合理。

### 2.3 FT 工程独有、VeneraX 可选跟进的

- 章节分组信息（`[Group]` 前缀 → `group` 字段入清单）——翻译工作室按翻译组整理时有用；
  VeneraX 的 `ComicChapters` 已有分组概念，清单里带上即可。
- 清单镜像到翻译工作区（`translated/projects`）——若 VeneraX 翻译工程要和 FT 工程项目
  互通，清单格式尽量对齐 `_source_urls.json`。

## 三、补救机制设计方案（VeneraX 版）

### 3.1 数据模型：每章一份下载清单

**方案 A（推荐）：章节目录内 JSON 文件**
```
{comic_dir}/{chapter_dir}/_download_manifest.json
{
  "source": "comix_to",
  "comicId": "9lmnj-error-the-echo",
  "chapterId": "11429606-chapter-6",
  "expectedPages": 119,            // API 返回的 pages 数
  "failedPages": [                  // 与 FT 工程 failed_pages 同构
    {"index": 69, "url": "https://lov.joshuanotes.site/...", "error": "timeout"}
  ],
  "downloadedAt": "2026-10-05T14:40:00",
  "imageExtension": ".webp"        // 可选：辅助完整性推断
}
```
- 优点：与图片同生命周期（删章即删清单）；导出/同步目录时信息不丢；FT 工程格式可对齐。
- 缺点：文件系统扫描多一次 IO（可忽略，清单 <1KB）。

**方案 B：存 `LocalComic` 数据库（chapters JSON 里加字段）**
- 优点：查询快；缺点：导出目录后信息丢失、与 FT 工程目录不互通。

**结论：方案 A，另在 `LocalComic` 内存身派生"是否完整"布尔（扫描清单或缓存）。**

### 3.2 下载器改动（小）

1. `_ImageDownloadWrapper` 失败时不再让任务整体失败：把 `index + image URL + error`
   记入任务的 `failedPages` 映射，`_downloadChapterPool` 继续推进。
2. 章末写 `_download_manifest.json`（含 expectedPages——`_loadPagesForDownload`
   拿到的 URL 数就是它）。
3. 新增任务状态 `partialComplete`（部分成功）：`isError=false` 但 `hasMissingPages=true`，
   下载页消息显示 `"N 页缺失，可补救"`。
4. 取消/暂停恢复：恢复时先读清单，已成功的页跳过（现状已按文件存在性续传，保持）。

### 3.3 补救任务

```
RepairDownloadTask（新 DownloadTask 子类，或 ImagesDownloadTask 带初始 failedPages）
  输入：扫描 local 目录所有 _download_manifest.json 的 failedPages
  过程：逐页走与主下载完全相同的取图通道（loadComicImageUnwrapped forDownload）
  成功：写文件 + 从清单 failedPages 移除 → 清单空了则删除清单文件
  失败：保留清单记录，error 字段更新
  结束：汇报"补齐 N 页 / 仍缺 M 页"
```

- 复用现有队列/暂停/恢复/重试框架（DownloadTask 抽象已支持）。
- 阅读缺页章节时：`getImagesForComic` 读到清单 → 页数 < expectedPages 时
  在阅读器顶部提示"本章缺 N 页（已下载 X/Y）"，并提供"去修复"入口。

### 3.4 UI 呈现（不完整信息显示）

| 位置 | 展示 |
| --- | --- |
| 本地页卡片 | 缺页角标 ⚠️"缺 N 页"（清单派生） |
| 下载中/部分成功任务 | 状态行 + 黄色提示"N 页缺失" |
| 漫画详情页（本地） | 章节列表里缺页章节标黄 + "修复"按钮 |
| 阅读器 | 进入缺页章时顶部一次性提示 |

### 3.5 工作量评估

| 项 | 量级 | 说明 |
| --- | --- | --- |
| 清单写入 + 失败跳过策略 | 小（~100 行） | download.dart 改 2 处 + 1 个清单工具类 |
| RepairDownloadTask | 中（~200 行） | 复用框架，主要是扫描+回写清单 |
| UI（角标/提示/修复入口） | 中（~150 行） | 分散在 4 个页面 |
| 阅读器缺失提示 | 小（~40 行） | getImagesForComic 返回清单信息 |

总计约 1~2 个工作日的编码量，**无架构阻碍，纯增量**。

## 五、翻译工作室搭建的注意问题（结合本次下载链路）

### 5.1 页面完整性是翻译的生命线

翻译工程（FT 工程项目 / VeneraX 翻译页）按**页序对齐**组织工作。缺页或半成品图会导致：
- 翻译结果与页码错位（错一页，后面全错）；
- OCR/嵌字流程在坏图上崩溃。

**规范建议**：下载 → 清单校验（expectedPages == 实际页数）→ 补救 → 才进入翻译。
把"完整性校验"做成翻译工程创建前的**强制闸门**，而不是靠人眼发现。

### 5.2 comix.to 特有的注意事项

| 问题 | 影响 | 对策 |
| --- | --- | --- |
| CDN WAF 日变（轮换域 + 指纹拦截） | 直连通道随时失效（FT 工程已中招） | 只用 WebView 通道取图；补救机制必备（失败页必然发生） |
| CDN 连续请求易限流（>10 张 503） | 批量下载失败率上升 | 组间歇/Lane 级节流；并发别贪高（当前 3 合适） |
| 章节带翻译组署名（`[Group]`） | 同一话可能有多组版本 | 下载时保留翻译组信息入清单；工作室选源时明确要哪一组 |
| 30s 单图超时是合理值 | 更长预算只会在 WAF 拦截时浪费等待 | 保持阅读 30s / 下载 90s 的双预算 |
| 站点登录后有广告弹层 | 不影响 API/取图（已验证），影响 SPA 交互 | 已加 `_adSweepJs` 防护；工作室流程无需人工点广告 |

### 5.3 工程化建议（工作室规模运转时）

1. **清单即档案**：`_download_manifest.json` 记录 source/comicId/chapterId/URL/
   downloadedAt——翻译成品出问题时可溯源到源站页面。
2. **目录结构与 FT 工程对齐**（Venera 布局 `{comic}/{chapter}/{index}.{ext}`），FT 工程的
   翻译项目可直接消费 VeneraX 下载的目录，反之亦然。
3. **失败页清单跨工具互通**：若沿用 FT 工程的 `failed_pages` 字段名与结构，两边任何
   一方下载、另一方补救都成立。
4. **批量任务的资源隔离**：下载（WebView 通道）与阅读（同一通道池）共享 3 条
   Lane——大批量下载时阅读会排队。后续可考虑下载任务用独立 Lane 池（隔离开关）。

## 六、章节标签四态配色（2026-10-05 新增需求 · 可行性分析）

### 6.1 需求
详情页章节网格的章节标签（"第 1 话"这类 chip）按下载状态着色：
**白色**＝基础（未下载）／**黄色**＝下载中／**蓝色**＝已下载／**红色**＝缺页或下载失败。

### 6.2 渲染点（唯一）
`lib/pages/comic_details_page/chapters.dart:447` —— 章节网格每个 chip 的底色来自

```dart
Material(
  color: isSelected
      ? context.colorScheme.primaryContainer   // 选中
      : context.colorScheme.surfaceContainerLow, // 基础
  ...
)
```

目前只有两态，"已读"只影响文字颜色（`outline`）。加一个
`_chapterChipColor(state, isSelected)` 即可，**不动网格结构、不动翻译组 chips 行**（Asura Scans 等过滤行维持现状）。

### 6.3 四态数据源逐项评估

| 状态 | 颜色 | 数据源 | 就绪度 / 缺口 |
| --- | --- | --- | --- |
| 基础 | 白（surface） | 现状默认 | ✅ 已有 |
| 下载中 | 黄 | ⚠️ `LocalManager.isDownloading(id, type)` 目前是**漫画级布尔**（local.dart:112），没有"哪一章在下载"。需新增：从 DownloadQueue 活动任务的 chapterId 聚合出 `downloadingChapterIds` 集合，随任务进度通知刷新 | 需新增 ~30 行，纯增量 |
| 已下载 | 蓝 | `LocalComic.downloadedChapters`（章节 id 列表，local.dart:69）已存在且持久化；**章节 chip 的 key 恰好就是章节 id**（`_displayChapters.ids`），映射零成本 | ✅ 数据现成 |
| 缺页/失败 | 红 | 依赖 S2 的 `missing_pages.json`（章节→缺失页清单）。S2 落地前可临时用**会话内失败任务**的记录显示，重启后丢失 | ⛔ 硬依赖 S2 |

### 6.4 结论与排期建议

- **可行，且改动集中**（单文件为主 + 一个数据源聚合函数）。
- **蓝色（已下载）与黄色（下载中）不依赖 S2**，可以随 S1/S2 一并交付或提前单独做——对"已下载第一话"的漫画（用户截图场景），S2 之前就能看到蓝标签。
- **红色（缺页）必须在 S2 之后**才有可靠数据源——已合并进 S3 的交付物（S3-a）。
- 配色优先级建议：**红 > 黄 > 蓝 > 选中 > 白**；选择模式（多选下载）时状态色作底、选中用描边，避免覆盖。已读灰字逻辑保留。
- UI 细节：黄/蓝/红建议用低饱和容器色（类似 `primaryContainer` 的做法）保证文字可读；色弱场景下叠加图标（✓/↓/⚠）作为冗余编码——S3 一起做，代价极小。
