## 一、本轮事故与修复

### 1. comix_to 源整个消失（"Comic source not found"）— 已修复 ✅

**现象**：漫画源列表里没有 comix.to；历史记录打开详情页报"章节加载失败：Comic source not found"。

**根因**：`comix_to.js` v0.3.0 在 **class 体内用 `var` 声明字段**（`var _chaptersCache = {};`）。
这在 JS 里是语法错误，QuickJS 解析整个类失败 → 源注册失败 → 所有引用该源的地方报 not found。
日志铁证（logs.txt 19:55:23）：

```
SyntaxError: expecting ';'  at ComixTo:16:1
  at ComicSourceParser.parse / ComicSourceManager.doInit
```

**修复**：改为 class field 语法 `_chaptersCache = {};`（v0.3.1）。

**教训（重要）**：
- **JS 漫画源改动后必须 `node --check` 验证语法再同步**。已固化为流程：
  `node --check assets/comix_to.js && cp 到 %APPDATA%\io.github.kyosee\venera\comic_source\`
- class 体内只能写 `field = value;`，不能写 `var/let/const`。
- 源加载失败的影响面是"整个源消失"，不只是功能异常——排查时先查 logs.txt 里 `ComicSource` 前缀的 SyntaxError。

### 2. 发现页 CERTIFICATE_VERIFY_FAILED — 已修复 ✅

**现象**：发现页包子漫画报 `HandshakeException: CERTIFICATE_VERIFY_FAILED: unable to get local issuer certificate`，目标 `https://cn.baozimhcn.com`。

**根因**：与本次改动无关的存量问题。rhttp 依赖被注释后所有 HTTP 走 dart:io，
而 **dart:io 的 BoringSSL 只信 Flutter 内置根证书列表，不认 Windows 系统证书库**
（`app_dio_io.dart` 注释里本就写了这个坑）。`*.baozimhcn.com` 是 ZeroSSL 签发，
其根/中间证书不在内置列表（curl/openssl 用系统库所以正常）。走 Clash 代理时
代理软件的根证书同样只装在系统库。

**修复**：`createIOHttpClient` 原来只在 `ignoreBadCertificate` 设置开启时才挂
`badCertificateCallback`；现在**只要走代理（proxy != null）就挂**，与原 rhttp
路径行为对齐（commit 见 lib/network/app_dio_io.dart）。用户侧也可以直接在
设置里开"忽略证书校验"临时绕过。

### 3. 收藏页 "Not login" — 非 bug，无需修复

网络收藏夹需要登录对应网站账号（包子漫画等）。comix_to 的 `favorites.login`
目前是占位返回 false，属未实现功能（P4-3 范围外）。

### 4. 上一轮的构建/运行时发现（回顾固化）

- **exe 不重新构建 = 改动不生效**。`builds\venera\venera.exe` 是 0.2MB runner 壳，

- **漫画源 JS 不进安装包**：运行时从 `%APPDATA%\io.github.kyosee\venera\comic_source\*.js`
  加载，改 JS 必须手动同步该目录（v0.3.0 事故的另一诱因：同步了坏文件）。
- **WorkBuddy 会话内 flutter 必失败**（嵌套进程 CreateFile 231），唯一验证可行：
  `tools\build_venera_release.bat` + 计划任务（schtasks）独立进程树执行。
  analyze 必须加 `--no-fatal-infos`（13 条存量 info lint 会让 errorlevel=1 误判失败）。

## 二、新功能：comix.to 搜索（v0.3.2）✅

**逆向结论**（从前端 bundle main.js/env chunk 确认）：
- 搜索框调用 `mangaApi.list({keyword, limit})` → `GET /api/v1/manga?keyword=<kw>&page=N&limit=28&__=token`
- 响应 `{status:"ok", result:{items:[...], meta:{last_page}}}`（axios 拦截器解包，原始带包装层）
- comix.to 搜索/分类页**没有 SSR**（只有详情页有 initial-data），纯 HTTP 拿不到搜索结果；
  API 又要 `__=` token（VMP 混淆 secure.js 生成、绑浏览器指纹，Node/Dart 无法复现）

**实现**（复用 headless 采集架构，无窗口）：
1. `ComixClient.searchManga(keyword, page)`：从已截获的 `/api/v1/manga` 列表请求里
   提取 `__=` token（worker 启动时主页会自发请求，通常有现成 token；没有就导航主页截一次），
   然后在页面上下文内 fetch `/api/v1/manga?keyword=...&__=<token>`，直读 JSON。
2. `js_engine.dart` 新增 `comix_search` 桥接。
3. `comix_to.js` 的 `search.load/loadNext` 实现：item → `{id: "hid//slug", title, cover}`，
   id 格式与 loadInfo 对齐；cover 兼容 poster 对象/字符串两种形态。

**待实测验证**：搜索结果条目的确切字段名（hid/slug/poster 是从详情 API 推断的），
若映射不上，看 logs.txt 里 `ComixClient search` 日志后调整 comix_to.js 的字段提取。

## 三、comick.js 配置分析 与 comix.to 对比

### comick.js（v1.2.0，官方源）为什么写得"轻松"

| 能力 | comick（comick.art） | comix.to |
|---|---|---|
| 网站架构 | SvelteKit，**关键页全有 SSR** | Laravel+Vue SPA，**只有详情页有 SSR** |
| 搜索 | `/search?q=` 是 SSR 页，解析 `#sv-data` JSON 即可 | 搜索页空壳，必须 `/api/v1/manga?keyword=` + token |
| 章节列表 | **无鉴权 JSON API** `/api/comics/{slug}/chapter-list?page=N` | API 要 `__=` 指纹 token |
| 图片 | 章节页 SSR 的 `#sv-data` 里有 images，纯 HTTP 跟"下一页"链 | 必须截获 `/api/v1/chapters/{id}` |
| 反爬 | 图床仅 Referer 防盗链 | Cloudflare + 指纹 token + VMP 混淆 |

结论：**comick 的纯 HTTP 写法是它家网站善良，不是通用方案**。comix.to 的 headless
webview + API 截获架构是对抗其反爬的必要复杂度，不能照搬 comick。

### comick.js 值得借鉴的写法（已采纳/建议）

1. ✅ **id 编码复合信息**：`slug//title`、epId 用 `hid//chapter//{chap}//{lang}`，
   把 loadEp 需要的全部参数编码进 key，避免查表。comix_to 已用同思路
   （章节 key = 完整章节页 URL）。
2. ✅ **versioned 按语言/汉化组分桶**：`Map<语言, Map<章节key, 标题>>` ——
   comix_to 的 versioned map（章节号 → 多翻译组）同构，方向正确。
3. ✅ **onImageLoad/onThumbnailLoad 带 onLoadFailed 重试构造器**：图床防盗链
   站的标配。**建议后续给 comix_to 也加上**（图片域若验 Referer 会 403）。
4. ✅ **静态字典 + 双向映射**做标签中文化（category_param_dict / reversed）。
   comix.to 做分类功能时可照搬。
5. ⚠️ comick.js 的反模式不要学：`transReformBookList` 与 `transformBookList`
   功能重复；`Network.get(url=url, headers=headers)` 这种 Python 风格命名参数
   在 JS 里其实是赋值表达式，能跑纯属巧合。

# 第二轮修复（20:28-20:40，v0.4.0）

## 用户新报的问题与根因

### 1. 章节栏空白 → `_chaptersCache is not defined`（我的 v0.3.1 修复不彻底）
v0.3.0 是 class 体内写 `var`（语法错误）；v0.3.1 改成了 class field `_chaptersCache = {}`，
**语法过了，但方法里裸引用 `_chaptersCache` 是全局查找而不是 `this._chaptersCache`** →
运行时 ReferenceError → loadInfo 在章节段抛异常。
**修复**：缓存挪到模块级 `var _chaptersCache = {}`（class 外），方法通过闭包访问。
**教训**：JS class 实例字段 ≠ 闭包变量。跨方法共享的可变状态放模块级 var 最稳。

### 2. 搜索空白 → 主页截获不到 token（设计缺陷）
日志链：headless 启动 OK → 导航主页 → 只截获到 `/api/v1/user` → 30s 无 manga 列表请求 → 无 token → 0 结果。
**主页根本不会自发请求 manga 列表**（内容走 SSR/initial-data），"等截获"思路错误。
**修复**：改成**直接导航到 `https://comix.to/browse?q=<关键词>&page=N`**，
SPA 自己带 token 发 `/api/v1/manga` 请求，截获即得。搜索/发现/分类统一走新桥接 `comix_browse`。
**教训**：能借站方 SPA 自己发的请求就不要自己拼 API 参数（数组序列化 types[] vs types= 无法静态确认）。

### 3. 发现页"Sleepless Death 占位卡片、封面失败" → 那是 v0.2 时代的硬编码占位
explore[0].load 硬编码返回一条 `{id:"9l3kj", cover:""}`。已改为真实数据：
explore = /browse 最新更新列表（真实封面、可翻页）。

### 4. 收藏页 Not login（所有源）+ 分类页没有 comix.to
- Not login：网络收藏夹需要登录各网站账号，属正常 venera 行为；comix_to 侧**移除了 favorites 占位**
  （parser 检测不到 favorites 就不显示收藏入口，避免误导）。
- 分类页：comix_to 之前没定义 `category`。已新增 types/statuses 两组枚举分类
  （Manga/Manhwa/Manhua/Other + 连载中/已完结/休刊/已断更），走 comix_browse。
  genres_in 需要数字 id（/api/v1/manga/genres 动态接口），暂未接入。

### 5. 用户疑问解答（已回复）
- VPN：app 网络走设置里的代理（默认 system = Windows 系统代理），Clash 挂了系统代理就会走它；headless WebView2 也用系统代理。无需手动开全局。
- 详情页信息/封面是**真实从 comix.to 解析的**（纯 HTTP，走 Clash 成功），不是写死。写死的只有旧发现页占位卡片（已移除）。
- 详情页信息显示但章节空白：loadInfo 在章节段抛异常前已返回数据？不——UI 显示的是历史记录缓存 + loadInfo 抛错后 UI 用已有数据渲染，章节自然为空。

## 逆向补充（本轮新增）

# 第三轮修复（20:50-21:00，v0.4.1：章节采集根因 + (Invalid) 残留）

## 问题 1：章节慢（~20s）且不全（只到 22 话）

### 日志复盘（logs.txt 20:48:05-08）
```
captured chapters API (URL 正常，带 __= token)
chapters API page1: 0 items, lastPage=1   ← 解码后没有 items/meta
API path empty — falling back to DOM scraping
DOM: page 2..8，每页 ~1.2s，累计 160 行
Built versioned(DOM): 22 chapter numbers
```

### 根因（两个叠加）
1. **API 路径误判失败**：SPA 页面刚加载时第一个章节 API 请求可能吃到 WAF
   挑战的 403 JSON（`{"error":"challenge_required"}` 形态，与 baozimh 同款
   gatekeeper）。钩子不记 status，Dart 拿到 body 解码成无 items 的 Map →
   按 0 items 处理 → 降级 DOM。**截获 URL 一直有效，body 不可信。**
2. **DOM 兜底天然不全**：`pages=8` 取的是分页按钮上的最大数字（按钮只有
   1-8），不是总页数；且只点数字按钮不点 Next → 最多 160 行 ≈ 22 个章节号。
   慢（8×1.2s≈10s）+ 不全双重缺陷。

### 修复（comix_client.dart v0.4.1）
- 钩子 record() 增加 status 字段（fetch 的 res.status / XHR 的 xhr.status）。
- 新通用方法 `_inPageFetchJson(template, {overrides, attempts=3})`：页面上下文
  内按模板 fetch（同源同 cookie，token 有效），非 200 等 700ms 重试。
- 章节流程重写：截获只用来拿 URL 模板；page1 优先用截获 body（校验含
  items 才用），否则页面内 fetch；按 meta.lastPage 翻完全部分页（不再受
  按钮数量限制）。60 章 = 3-4 个请求 ≈ 1s 内完成。
- browse（搜索/发现/分类）与 pages（章节图片）同样加"body 不可用 → 页面内
  fetch 重试"兜底。

## 问题 2：网络收藏页显示 "(Invalid) comix_to"

### 根因
- 显示处：`setting_components.dart:743` `widget.pages[key] ?? "(Invalid) $key"`。
- 设置 `favorites` 列表里残留 `comix_to` key（v0.3.x 有 favorites 占位时
  写入的）；v0.4.0 移除 favorites 后 `favoriteData == null` → title 查不到。
- 存量清理函数 `_validatePages()` 只在**删除漫画源时**调用，启动不跑 →
  残留永不消失。

### 修复
`ComicSourceManager.doInit()` 末尾新增 `_validateSavedPageKeys()`：启动/重载
时把 favorites/categories/explore_pages/searchSources 里没有对应源数据的
key 清掉并保存。自愈式，无需手动改 settings.json。

## 经验教训
1. **截获的响应体 ≠ 可信数据**：拦截/截获架构必须记录并校验 HTTP status，
   "URL 对"不等于"body 对"。WAF 挑战响应也会走钩子。
2. **UI 上的数值不一定是全集**：DOM 分页按钮显示 8 个 ≠ 总共 8 页。
   能拿 API meta（lastPage/hasNext）就不要用 UI 线索推断范围。
3. **设置残留要自愈**：源功能增删后，引用它的持久化配置应在启动时校验
   清理，不能只挂在删除源的路径上。
4. "Not login" 对所有网络源是正常行为（未登录站内账号），不是 bug；
   但源侧不提供收藏功能时就不该注册 favorites，避免误导。

# 第四轮修复（21:05-21:15：baozimh 挑战验证自动化）

## 现象
阅读包子漫画报"需要Cloudflare验证"，需手动点"验证"；且每次换章节/镜像可能反复出现。

## 链路复盘（logs.txt + baozi.js）
1. baozi.js loadEp 主路径走镜像网页（www.baozimh.com → cn.bzmgcn.com）；
2. 这些站 403 + JSON `{"challenge_url":"/__gatekeeper_challenge/start?return=...","error":"challenge_required"}`
   —— **这不是 Cloudflare**，是站方自建 gatekeeper WAF（JS PoW 挑战，自动完成、无需人工）；
3. `CloudflareInterceptor._check` 只认 `cf-mitigated: challenge` 头 → gatekeeper 403 被当成普通
   "Invalid status code: 403" → 全部镜像失败 → 兜底 appcn.baozimh.com（这个域才是真 Cloudflare）；
4. appcn 的 CF 异常抛给阅读器 → 显示"需要Cloudflare验证"+验证按钮（手动、弹窗）。

## 根因
- gatekeeper 挑战在 Dart 网络层不可见（只认 CF 头），无法进入验证流程 → 主路径永远 403；
- 已有验证流程必须手动点按钮 + 弹窗，而两种挑战其实都是**非交互 JS 挑战**，
  完全可以在离屏 webview 里自动通过。

## 修复（cloudflare.dart + loading.dart）
1. `_check` 增加 gatekeeper 检测：403 JSON 含 `error=challenge_required` + `challenge_url`
   → 抛 CloudflareException，URL = realUri.origin + challenge_url（挑战入口）。
2. `_isCloudflareChallengePage` 增加 gatekeeper 标记（`__gatekeeper_challenge`、
   `正在验证浏览器`、`data-state="checking"`）——防止把挑战中页面误判为"已通过"
   （否则会把挑战页 HTML 缓存成"已验证页面"，污染后续请求）。
3. 新增 `tryHeadlessVerification()`：HeadlessInAppWebView（复用 AppWebview 的
   WebViewEnvironment profile）离屏打开挑战 URL，轮询页面标记，通过后收集全部
   cookie（含 gatekeeper 的 `__Host-gk_browser_*` 与 CF 的 cf_clearance）存入
   SingleInstanceCookieJar、标记 host 已验证、缓存已验证 HTML。45s 超时兜底。
4. `NetworkError`（loading.dart）检测到 CloudflareException 时**自动**触发一次
   无窗口验证（每 URL 仅一次，防循环），成功自动 retry；失败保留手动"验证"按钮
   （此时才弹可见 webview，应对交互式验证码）。

## 效果
- 阅读包子漫画：报错一闪而过（或根本看不到）→ 无窗口自动过挑战 → 自动重试出图。
- 主路径（镜像网页）恢复后不再依赖 appcn 兜底。
- 所有源的 CF 挑战（经典 "Just a moment"）同样自动通过，无需手动。

## 其他网站排查结论
- copy_manga / dm5 / komiic / comick 等：无 gatekeeper 式自建 WAF；走真 CF 的
  场景现在也享受自动验证，无需逐源修改。
- comix_to：自有 headless worker + WAF token 机制，不经过此路径。

## 经验教训
1. **"Cloudflare 验证"不一定是 Cloudflare**：403 + JSON challenge 指令是常见自建 WAF
   模式（challenge_url 字段是解题入口）。验证层要按"协议"识别挑战，不能只认 CF 头。
2. **非交互挑战不需要弹窗**：JS PoW 挑战在 headless webview 里可全自动通过；
   可见 webview 只应留给交互式验证码兜底。
3. **误判"已通过"比不验证更糟**：把挑战页缓存成正常页面会污染请求结果；
   挑战页标记列表必须覆盖所有遇到的 WAF。
4. cookie 域注意 `__Host-` 前缀（host-only，不可设 domain）——逐镜像分别通过是
   预期行为，好域名记忆机制（_rememberGoodDomain）会减少重复验证。
