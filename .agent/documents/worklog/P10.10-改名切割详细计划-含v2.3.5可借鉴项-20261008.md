# 第一部分 · 上游 v2.3.5 可借鉴项

## 1.1 ✅ 值得抄的三个功能

### ① 自定义翻译脚本（**最值得抄的一条**）

| 项 | 内容 |
|---|---|
| 落点 | 上游 `lib/foundation/image_translation/script_translator.dart` |
| 机制 | `flutter_qjs` **QuickJS 沙箱**跑用户 JS；`Network.sendRequest` 注入 HTTP；**1s 超时 + 64MB 内存上限** |
| 契约 | `translate({texts, sourceLang, targetLang, glossary, provider}) → {texts, glossary}`；**一次传整批 texts，要求等长同序返回** |

**为什么对 Mangrove 特别有价值**：

- `glossary` 字段直接对上漫画专名一致性 —— 我们刚做完术语表（`A08 §1`），这给了它第二条通路。
- **"等长同序"正是本项目 `studio_pipeline._translate` 已有的契约** ⇒ 接入成本主要是沙箱与 HTTP 注入，不是数据模型改造。
- 沙箱有超时与内存上限 ⇒ 用户脚本跑飞不会拖垮管线。这是"可扩展翻译后端"的正确形态。

⚠️ 移植代价：新增 `flutter_qjs` 依赖（**本仓库当前没有**）；需设计脚本的持久化与 UI 编辑入口（上游有，我们没有）。

### ② 大文件导出修复

| 项 | 内容 |
|---|---|
| 落点 | 上游 `lib/utils/epub.dart`（重写） |
| 改动 | 弃用 `zip_flutter`，改 `archive` 的 `ZipEncoder().startEncode()` **流式**写出；SAF 批量读做**空字节检测**并抛错 |

**为什么重要**："批量读静默返回空"在 Windows 上表现为**导出成功但图片空白** ——
这是隐蔽数据损坏，比崩溃难查一百倍。汉化工程的产物动辄几十 MB，走的就是这条路。

⚠️ 我们已有 `utils/cbz.dart` / `pdf.dart` / `epub.dart` ⇒ 需逐个核对是否已含空字节检测，**只补缺的那几处**。

### ③ 缓存"冻结路径 + 启动扫描先于写入"

| 项 | 内容 |
|---|---|
| 落点 | 上游 `lib/foundation/image_translation/cache_manager.dart` |
| 改动 | 路径在实例化时冻结为 `final _cachePath`；**启动扫描完成前不写** |

**为什么重要**：汉化会产大量中间产物（`inpainted/` / `result/` / `mask/` / 缩略图）。
清理与写入竞争 ⇒ 丢数据。而且这类丢失是**静默**的：文件少了，没人知道是哪一步丢的。

配套还有 `perf(cache): index startup file lookups`（启动索引）—— 漫画库大时启动扫描是卡顿主因。

## 1.2 ⚠️ 可以按点摘取（需改造）

| 项 | 改造点 |
|---|---|
| **取消加载要真取消** | `fix(images): track active local cover reads`。点取消后 CPU 仍满载 ⇒ 对应我们的 OCR/擦字任务也应能真取消 |
| PDF 导入为本地漫画 | 需新增 `pdfrx_engine` + `pdfium_flutter`（**本地无**）。上游只给"PDF → 本地漫画"，**不含**检测/OCR/汉化 |
| 自选缓存目录 | 模式可借鉴（子目录、拒绝软链接、拒绝非绝对路径、保留恢复默认），但子目录名要改 |
| 设置作用域/继承（global / device / per-comic 三级） | 若汉化参数（OCR 引擎、翻译模型、擦字强度）需按漫画覆写，可直接借用 |
| 任务页搜索/筛选、长操作按钮换行 | 下载 + 翻译任务卡片布局可借鉴 |
| WebDAV 同步白名单（v2.3.4） | 多机同步时 API key 类敏感项必须走这条 |

## 1.3 ❌ 与本项目无关

阅读器动效与模式、追更、探索/分类页、合集、漫画卡片、阅读统计、WebDAV 上传本身、
空状态引导页、AltStore 清单。

## 1.4 上游趋势判读

v2.3.0–v2.3.4 主要是阅读器/收藏/追更，AI 翻译只有 v2.3.3 的"可编辑提示词"。
**v2.3.5 是首个把翻译接入方式开放给用户的版本** ⇒ 上游正从"内置 AI 翻译"走向
"可扩展翻译后端"。这条趋势与 Mangrove 的路线**同向**。

⚠️ v2.2.10 改了 `comic.onImageLoad` 插件 API（async + 类型校验 + 传 `comicId`）——
若将来要兼容上游插件，这是破坏性变更。

## 1.5 结论

**整体 cherry-pick 性价比低** —— 65 文件里 21 个是测试，真实生产改动约 30 文件，
分散在设置/任务/缓存三块。**按上面 1.1 / 1.2 的清单摘取更合适。**

## 2.2 更新检测在哪（上游已收敛成单点，设计很好）

> 🔴 上游注释本身就写了 "Single edit point for a fork" —— 明确是给 fork 用的设计。

| 环节 | 位置 |

   切割前必须读完整份 LICENSE（不止前 5 行）并确认。
