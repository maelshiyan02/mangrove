### 2.3 🔴 踩到的坑：Python 生成的 JSON 必须与 `PyJson` 逐字节一致

首次生成用了 `json.dumps(..., indent=4)`，`project-check` 的 `roundtrip` 立刻失败：

```
FAIL roundtrip -> differs at byte 1: {
    "directory": "D vs {"directory": "D:/Bal (len 1496 vs 899)
```

`PyJson` 就是 Python `json.dumps(value, ensure_ascii=False)` 的**默认紧凑格式**：分隔符 `", "` / `": "`，**无缩进、无末尾换行**。

> 📌 **这就是为什么 `Error the Echo` 能过 roundtrip 而新建的不能** —— 它本来就是 FT 用 Python 写的。**用 Python 生成或手改载体 JSON 必须传 `separators=(', ', ': ')`。** 修正后 `roundtrip -> identical (899 B)`。

这条恰好补上了记忆里"零字节 diff 三坑"中"`PyJson` 分隔符"那条的**实际踩坑场景** —— 之前只在跨语言测试里遇到，这次是在**自己造载体**时遇到。

### 2.4 `edit-check` 原本在空工程上直接 FAIL（本轮顺手修掉）

## 三、P2-6-c Create 块

### 3.1 唯一默认块来源（P9.0 §七.4 隐藏前置 ②）

P9.0 点名的第二个隐藏前置：**`TextBlock(this.raw)` 没有空白块模板**，且 **P0-2 的 `fromOcr` 必须复用它**，否则人工块与自动块字段规格不一致，会在零字节 diff 上炸。

落地：

- **`TextBlock.createDefault({required IntRect rect})`** —— 写出 FT 的**全部 23 个块键**（顺序与真实工程一致）。
- **`FontFormat.createDefault()`** —— 写出 **全部 32 个 `fontformat` 键**。

> 🔴 **为什么必须写全**：FT 读 `fontformat` 是**逐字段**读的，只写 `font_family` + `font_size` 的块在 FT 里打开时**其余样式全部静默重置**。部分 `fontformat` 比没有更糟。

实现期定下的三个具体取值：

| 字段 | 取值 | 理由 |
|---|---|---|
| `alignment` | `center`(1) | 🔴 **FT 自己的默认是居中**，而 `FontFormat.defaultAlignment` 常量是 `left`(0)。新建块跟 FT —— 否则工作室看到的和 FT 打开时看到的不一致 |
| `_detected_font_size` | `defaultFontSize`(24.0) | 🔴 **不能写 0**：它是渲染器折算行高的依据，0 会退到渲染器的兜底值，与面板显示的字号脱节 |
| `text_effects.effects[0]` | `stroke` **enabled**、width 0 | 与真实工程一致：效果存在但不绘制，面板的描边滑块有东西可抓，改宽度即真正开启 |
| `det_model` | `''`（空串） | 🔴 不能写 `'ctd'` —— 那是**检测器**的名字，声称一个手工块来自检测器是撒谎；P1-3 读它时会误判 |

### 3.2 工作室入口

- AppBar actions 最左侧新增「新建文本块」（`Icons.add_comment_outlined`）→ `_createBlock()`。
- 落点：**页内水平居中、垂直 1/3 处**，尺寸为页面 `image_info` 的 **42% 宽 × 9% 高**（下限 48×24 px）。
- 建完**自动选中**并刷新面板。

> **为什么落点是固定位置而不是"拖出来"**：画布上已有的拖拽是**移动**手势，再加一个绘制矩形的手势会与之冲突，且 `StudioScrollCanvas` 自己也有手势。在真正的"框选新建"手势做出来之前，按钮落一个可读的框、让用户**拖到想要的位置**（拖拽已实现且只算 1 个撤销步）是更诚实的交付。**这是已知限制，不是"拖拽新建已完成"。**

> **为什么尺寸取页面的比例**：块的 `xyxy` 单位是**原图像素**，而画布可能缩放（`limitImageWidth`）。按页面比例算，900px 宽和 2400px 宽的页上创建的块**视觉大小一致**；写死像素会在高分辨率页上变成一枚读不清的小邮票。

### 3.3 三个实现期决策

1. 🔴 **Create 与 Delete 走同一条命令路径**（`captureBlockListEdit`）—— 一个撤销步，与删除对称，两者不可能各自漂移。
2. 🔴 **选索引用 `identical(b.raw, block.raw)` 身份比对，不能用 `blocks.length - 1`**：`ProjectPage.blocks` 会**跳过非 JSON 对象的条目**（模型容忍手改文件里混入这种东西），所以类型化视图可能比原始列表短，"最后一个类型化索引"未必是刚追加的那个。按长度取会**选错成邻居**。
3. **`clamp` 在 `double` 上返回 `num`**，且退化页（`image_info` 只有 1px）会把框塌成不可排版的细条 → 先对下限 clamp 再对页面 clamp，显式 `.toInt()`。

## 四、🔴 本轮最贵的坑：本仓库有自己的 `IntRect`，不是 `dart:ui` 的

在 `headless.dart` 里写 `IntRect.fromLTWH` 报 `undefined_identifier`，第一反应是"缺 `dart:ui` 导入" → 加上 → 变成：

```
error - The method 'IntRect' isn't defined for the type '_TranslationStudioPageState'.
```

**真相**：`lib/foundation/image_translation/translation_types.dart:13` 声明了**自己的 `IntRect`**（`left/top/right/bottom`，**没有** `fromLTWH`，构造器**不是** `const`）。这是为了让翻译模型**不依赖 Flutter**、能在 headless 下测。

于是连锁踩了 4 刀：

| # | 错误 | 真相 |
|---|---|---|
| 1 | `undefined_identifier: IntRect` | 缺的是**本仓库**的 `translation_types.dart`，不是 `dart:ui` |
| 2 | 加 `dart:ui` 后变成 `isn't defined for the type` | 引入了**同名不同类型**的第二个 `IntRect` |
| 3 | `IntRect.fromLTWH` 不存在 | 本地类只有 `IntRect(l, t, r, b)` |
| 4 | `const IntRect(...)` 报 `const_with_non_const` | 本地构造器**非 const** |

> 📌 **教训**：在 `translation_project/` / `image_translation/` 这两个目录里，`IntRect` / `IntSize` / `RgbaImage` 一律来自 `translation_types.dart`。看到 Flutter 没有的"缺失"标识符，先 `grep "^class <名字>" lib/` 确认是不是本仓库的影子类型，**别急着 import `dart:ui`** —— 同名引入会换来更迷惑的报错。

顺带：`_hypot` 我一开始手写了牛顿迭代来算 `norm`，纯属过度设计 —— `dart:math` 已经在导入列表里。改回 `math.sqrt`。

## 八、🐛 P9.3-bugfix · 长画布连续滚动"缺少页面图片"

> 用户报告（截图）：工作室长画布模式下满屏"缺少页面图片"，但切到单页模式**同一页又能正常显示**。
> 判断：连续画布（`StudioScrollCanvas`）的解码缓存被打断。

### 8.1 根因：不是尺寸适配，是解码缓存挂在每帧新建的对象上

用户的猜测是"长画布没适配图片的灵活尺寸变化"。**尺寸问题确实存在（见 8.3），但它不是这个 bug 的根因** —— 根因是生命周期。

`StudioStripPage` 持有解码结果（`decoded`），而 `studio_page._buildCanvas()` 里写的是：

```dart
StudioScrollCanvas(pages: _stripPages(), ...)   // ← 在 build() 内部调用
```

`_stripPages()` **每次 build 都 new 一批 `StudioStripPage`**，于是完整链路是：

1. `initState` → `_loadAround(0)` → 给 build#1 的对象设 `loading=true` 并解码
2. 解码成功 → 画布 `setState` → **显示正常**（所以首屏看着没问题）
3. 用户滚动 → `onPageChanged` → `studio_page.setState(_pageIndex)`
4. `_stripPages()` 生成**全新对象**，`decoded` 全是 null
5. `didUpdateWidget` 只比较 `pages.length`（还是 5）→ **判定"没变"** → 不触发 `_loadAround`
6. → 满屏"缺少页面图片"，且**永久不自愈**

第 5 步是关键：原本唯一的恢复入口靠"页数变化"识别项目切换，而滚动导致的重建页数不变，所以**永远进不去恢复逻辑**。截图里"第 1/5 页却满屏缺图"正是滚回来之后缓存已被清空的状态。

**单页模式为什么正常**：`_base` 挂在 `_TranslationStudioPageState` 上，不是每次 build 的临时对象。

### 8.2 修复：画布自己拥有页列表，按 key 复用

| 改动 | 文件 | 说明 |
|---|---|---|
| `_syncPages()` | `studio_scroll_canvas.dart` | 新增。画布持有 `_pages`，按 **`key`** 与 `widget.pages` 对账：命中就**复用旧实例**（连同它的 bitmap），从而父组件重建不影响解码缓存 |
| `_stripPages()` 缓存 | `studio_page.dart` | 加 `({project, pages})?` 记忆化。顺带干掉每帧最多 **97×3 次 `existsSync()`**（`_resolvePageFile` 要 stat original/inpainted/mask） |
| `_invalidateStripCache()` | `studio_page.dart` | 项目重载 / 分辨率顺序可能翻转时（检测落盘 `inpainted/`）显式失效 |
| `index`/`file`/`fromInpainted` 转可变 | `studio_scroll_canvas.dart` | 复用实例时要能纠正 index；磁盘上文件变了要能换源重解码 |
| `dispose()` 推进 `token` | `studio_scroll_canvas.dart` | 🔴 见 8.4 |

### 8.3 顺带修的三个真 bug（都在同一条链路上）

**① `_pageHeight` 把「视口高度」当成了「页面宽度」**

```dart
_controller.position.viewportDimension   // 纵向滚动 = 视口**高**度
```

原代码拿它当页宽去算页高。766px 宽的视口算出 1185px 页高，实际应为 1513px → **`scrollToPage` 必然跳错页**。现改为从 `LayoutBuilder` 的 `constraints.maxWidth` 取真正的页宽。

**② 占位高度与滚动数学互相撒谎**：`_StripItem` 占位写死 `420`，而 `_pageHeight()` 对未解码页返回 `1100`。布局和滚动数学各说各话，`_onScroll` 算出的当前页必然漂移。现统一由 `_pageHeight()` 一个来源出值。

**③ `fit` 缺 `min(…, 1.0)` 夹取**：`_pageHeight` 算 `w * sh/sw`，但画布用的是 contain 适配 `min(w/sw, 1.0)`。**比视口窄的页**（小图、封面）按原始尺寸渲染，实际高度小于估算值 → 再次失步。

**④ 🔴 我自己引入又修掉的一个**：`becameReady` 标志写在**异步回调内**，却在 `_loadAround` 同步返回前就读它 → 解码完成的页**不触发重建**。这是我第一版改动的错误，改成在回调内部直接 `setState`。

### 8.4 内存：`dispose()` 必须推进 token

`StudioStripPage.dispose()` 原先只释放 bitmap，**不推进 `token`**。若该页正在解码，回调回来时 `page.token == token` 成立 → 把结果挂到一个已经不可达的页上 → **逐出窗口的页会永久持有 bitmap**（项目开着多久泄漏多久）。现在 `dispose()` 递增 token，让在途解码自己 `dispose` 掉结果。

另外给解码失败加 `failed` 标志：损坏文件原本会在**每次滚动通知**时被重读一次（每秒几十次），现在只试一次并写 `Log.warning`。

### 8.6 教训（值得写进 MEMORY）

> 🔴 **把缓存挂在"每次 build 都新建的对象"上 = 缓存不存在。**
> 本项目的三次同类踩坑：`_stripPages()`（本轮）、S7 的 `_base`（当初靠 state 侥幸躲过）、以及"列表长度不变就认为数据没变"这个**只比长度的失效判断**。

## 九、Create 块交互优化：框选新建 + 8 控制点缩放

> 用户需求（原话要点）：除了按钮在固定位置生成，还要能**手动选择图片上的位置**创建块；块要能**自由增大缩小** —— 四条边有拉大缩小的点，四个角也有整体拉大缩小的点（附示意图：8 个方形控制点）。

### 9.1 手势消解：小画布上三种拖拽如何共存

一块屏幕上要回答"这次拖拽是**移动**、**缩放**还是**画新框**"，且答案必须在 `onPanStart` **一次定死**：

| 优先级 | 命中条件 | 结果 |
|---|---|---|
| 1 | 框选模式开启 | `marquee` —— 任何拖拽都画新框 |
| 2 | 落在选中块的**控制点**上 | `resize` |
| 3 | 落在**任意块**内 | `move` |
| 4 | 空白处 | 无（普通 tap 取消选择） |

🔴 **两条关键顺序**：

- **控制点必须先于块命中测试**。控制点位于块内部，若先测块，小块的四角控制点就永远命中不到 —— 这正是"看得见却拖不动"的经典成因。断言 `resize.handle_self_hit` 专门锁这条：8 个控制点在自己的中心处必须命中自己。
- **判定只做一次**。若在 `onPanUpdate` 里重新判定，拖拽一旦越过块边界就会从"移动"翻成"画框"，块会跳走。

🔴 **框选做成显式模式，而非"空白处拖拽即画框"**：从选中块内部起手的拖拽，**绝大多数是移动**而不是"要替换掉当前选择"。猜错的代价是用户刚摆好的块自己跳走了。模式只需点一下就彻底消除歧义，且**画完自动退出**（常见流程是"画框 → 打字"，不退出的话下一次拖拽又会画一个框）。

### 9.2 新增文件 `block_resize_geometry.dart`（纯几何，可 headless 测）

`ResizeHandle` 枚举（8 个）+ `resizeHandleBox` / `hitTestResizeHandle` / `applyResize` / `normalizeMarquee`。**绘制与命中测试共用 `resizeHandleBox`**，避免"点画在A 处、拖拽却响应B 处"。

三条硬规则：

| 规则 | 原因 |
|---|---|
| **四角等比、双轴；对角钉住** | 从抓住的角向对角生长 |
| **四边中点只动单轴** | 另一边不动 |
| **永不翻转、永不塌缩**（下限 16px） | 🔴 翻转的 `Rect` 会把文字上下颠倒渲染，更糟的是**把负宽度写进 FT 的 `xyxy`** |

**命中区（12px）比绘制尺寸（8px）大**：手指/鼠标很难精确落在 8px 上，"看得见却抓不住"是手写缩放 UI 最常见的抱怨。视觉不可见的余量把可用命中面积翻倍。

**角点优先于边**：小块上角与边的命中区重叠时，若按固定顺序测，会有一方永远抢不到 —— 故角点单独记录、边用 `??=`，最后角点优先返回。

### 9.3 缩放的 delta 累积基准（一个真实的棘手问题）

`applyResize` 含防止翻转的 clamp，而 **clamp 不可逆**。若每帧从**上一帧结果**继续累加，一旦被 clamp，后续位移就从已 clamp 的边开始度量 → **边缘每收到一个事件就再往内收一点**，指针停住时框仍在蠕动。故 `_dragDelta` 始终相对**手势起点**累积，`applyResize(start: 原框, delta: 总位移)` 每帧从原框重算。

### 9.4 顺手修掉的既有缺陷

- 🔴 **旧的"四角圆点"标记画在 `_paintText` 内**，而该方法对**空文本提前 return** —— 所以**新建的空块一个控制点都没有**，而那恰恰是最需要调大小的块。已移到 `paint` 层。
- `_StripItem` 的占位高度与滚动数学的失配（§八.3②）已统一到 `_pageHeight()`。
- 控制点加**白色描边**：主色方块压在深色气泡/黑边上会消失。

### 9.5 🔴 签名分层：我在这上面错了 4 次

`_StripItem` 的回调一度反复报"argument type not assignable"，根源是**两层 widget 的 pageKey 约定不一致**：

- 顶层 `StudioScrollCanvas` 的回调**带 `pageKey`**（P8.1 既有的对外 API，不宜改）
- `_StripItem` 是**每页一个**的内部 widget，本就闭包捕获了 `page.key` → 它的回调**不该再带 pageKey**

我中途在两个方向上反复横跳。**定案：`_StripItem` 全部回调 pageKey-free，由顶层 build 统一包装回 `page.key`** —— 单一地点贴 key，而不是让每个 widget 都记得贴。

> **教训**：跨 widget 传回调时，**先决定"谁负责补上下文参数"，再动手写**。两层都"顺手"加一次是最容易出错的形态。

### 9.6 🔴 一个我自己写错又修掉的注释

我给 `block_resize_geometry.dart` 写注释称"不 import `dart:ui`，保持零 Flutter 依赖"。**分析器直接打脸** —— `Rect`/`Offset` 就在 `dart:ui` 里。该注释已改为说明真相：**需要 `dart:ui` 的几何类型，但不需要 widget 代码和 live binding**，这才是能 headless 测的真实原因。

**判据纠正**：MEMORY 里"`IntRect` 自制是为了零 Flutter 依赖"的教训方向没错，但不能外推成"`dart:ui` 的 `Rect`/`Offset` 也要自制"。

## 十、工具栏图标"乱码"与 tooltip 英文：一次误诊两次的记录

> 用户反馈：① crop 图标显示成奇怪的中文；② 框选按钮的取消状态显示空白，且功能说明是全英文。

### 10.1 真实结论先说

| 反馈 | 真实原因 | 状态 |
|---|---|---|
| 图标是"奇怪的中文字" | **不是代码问题** —— 截图整行（连顶部 FPS/GPU 文字）被**非等比水平压扁**，`crop_outlined` 被压成了看不出形状的窄条 | 需重新截图确认 |
| tooltip 全英文 | **真bug**：`Draw box for new block` / `Cancel box draw` **未登记进 `translation.json`** | ✅ 已修 |
| 取消状态"显示空白" | **真问题**：活动态只靠 `Icons.crop` 填充字形区分，在 8 个同形按钮里看不出来 | ✅ 已修 |

产物字体**实测**：`crop`(0xe1a3) 与 `crop_outlined`(0xef9a) **都在** `MaterialIcons-Regular.otf` 子集里（子集 283 字形 / SDK 8668）。字形从来没丢过。

### 10.2 🔴 我误诊了两次，两次都是"方法错了却当成结论"

**第一次**——我用纯 Python 解析 `format 4` cmap 表，得出"`crop` 0xe1a3 与 `crop_outlined` 0xef9a **不在**产物子集里"，并据此断定根因是 Flutter 的 icon tree-shaking 不收录运行时三元里的 `IconData`，于是把 `studio_page.dart` 等 5 个文件的按钮全部改写成 `if/else` + `const`。

这个结论**不成立**。两个错误叠在一起：

1. **解析器有 bug**：我按`start..end` 区间展开codepoint，**漏算了 `idRangeOffset` 指向的 glyph id数组**，因此漏掉了大量用偏移映射的码位。
2. **推理链本身是错的**：即使某个字形真不在子集，也**不能推出"运行时三元"是原因** —— Flutter 的 `IconTreeShaker` 是扫 **kernel 常量池**里的 `IconData`，而 `Icons.crop` 是 `static const`字段，**无论出现在运行时三元还是 if/else 里都是常量**，都会被收录。我把"两个现象同时出现"当成了因果。

**第二次**——修完解析器（加上 `format 12` 子表）后重扫，得出"**35 种图标缺字形**"，包括大量已经写成 `const Icon(...)` 的（`deselect`、`hub_outlined`、`remove_done_rounded`）。这个"35"同样是我第一次解析 bug的残留（`format 12` 才是那些新版码位所在的地方）。补上`format 12` 后：**全部存在**。

> **教训（比修复本身重要）**：我连续两次用**没验证过的自制解析器**去读二进制结构，把输出当成了事实。正确顺序是**先验证工具**：拿一个已知答案去测它。我第一次就该发现"连 `undo` 0xe68c 这种渲染正常的都报 MISS"，那时就该停下 —— **一个检测工具在同一批数据上大量误报，本身就是工具坏了的证据，不是有 35 个 bug。**

### 10.3 为什么"截图被压扁"不该被读成"图标乱码"

关键线索是**顶部那行 `FPS 45 | GPU 16% | CPU 9%` 文字也被同样压扁**。如果只有图标变形，尚可怀疑是图标资源问题；但**同一行的普通文字以相同比例变形**，说明变换发生在**整行控件之上**（缩放/截图环节），与图标无关。

第二张截图（同一行、未压扁）里 `crop_outlined` 形状完全正常，直接证伪了"图标资源损坏"。

### 10.4 真正修掉的两处

**① tooltip 中文** —— `String.tl` **以英文原文为 key**，未登记就原样返回英文。新增两条：

| key | zh_CN | zh_TW |

| `Draw box for new block` | 框选新建块 | 框選新增區塊 |
