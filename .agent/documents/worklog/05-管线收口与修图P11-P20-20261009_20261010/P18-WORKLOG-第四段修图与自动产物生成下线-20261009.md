## 1 · 第四段「修图」的语义（这是本轮的核心设计）

```text
检测（划气泡 → 建空块） → 识别（块内 OCR → 填原文）
  → 翻译（原文 → 译文） → 修图（抹除原文 → 在同一块里填译文）
```

前三段是**文本层**（产物 = 工程 json 里的块），第四段是**位图层**
（产物 = `mask/` + `inpainted/` + `result/`）。

### 🔴 为什么必须分段而不是「翻译完自动做」

**抹字不可逆**：`inpainted/` 一旦写出，原图上的字已经被算法抹掉。用户想
"框歪了，重画一下"必须重新下载原图。而**框歪不歪只有人能判断** —— AI 不自知。

所以正确顺序是：AI 跑完前三段 → 用户在工作室里**亲眼看块、拖块、改完** →
再跑第四段。原实现把这两件事绑在一起，等于剥夺了这个机会。

### 三处纪律

1. **`repair` 默认 `false`**（`StudioRunStages` 构造与 `fromJson` 都是）。
2. 🔴 **旧记录（无 `repair` 键）读出 `false`，不是「跟着 `translate` 开」**——
   那是"迁移时最容易犯的向后兼容"，会把用户刚取消的自动出图**又悄悄恢复**。
3. **只勾修图时短路整个文本段循环**（`repairOnly`）：否则每页都被记一次
   "没有块可识别"跳过，最后报成"整章 N 页失败"，而用户只是选了第四段。

### 新的阻断原因码

`nothingToRepairCode` = `'nothing-to-repair'`，**刻意不复用**
`nothing-to-translate`：那一条的提示是"没有块有原文"（正确动作：去跑翻译），
而这里的真实情况是"有块、也翻了，但没打开修图"（正确动作：回弹窗勾修图，
或去工作室核对块）。两句话指向完全不同的下一步。

### `repairPages` 按**页**不按块

`inpainted/` 是按页落的文件，一页 8 个块也只画 1 张。报 24 会让用户以为要等
8 倍时间。`StudioRunCounts` 因此新增第 4 个字段 `translatedPages`。

## 2 · 🔴 顺手抓出的第二个真缺口：`fullArtifacts` 是死参数

`StudioChapterRunner.run(...)` 的签名里早就有 `bool fullArtifacts = true`，
但**全文件搜下来从未被读过** —— 一次都没用。

⇒ 后果：阅读页「入队跑整章」时**每一次都无条件**重画 `inpainted/` + `result/`，
而用户**看不到也关不掉**这个行为。这正是他说的"莫名其妙生成一次产物"的
另一半来源（P17 那轮我只切了工作室的 `_save`，漏了这条）。

**修法**：默认改 `false`，并把出图代码抽成 `_writeAllArtifacts`。工作室那条路
显式传 `true`（用户在那里看过块了）。

🔴 不出图时**不写**对账表的产物段：盘上确实没有产物，写上会让
"78 页有 inpainted 没有 mask"这类缺口凭空多出一批**假条目**。

## 3 · 「产物只能由显式选择触发」的三条路

| 触发 | 范围 | 说明 |
|---|---|---|
| Ctrl+S | **只写 JSON** | 不碰任何图片文件 |
| 「保存并修图」工具栏按钮 | 本轮改动过的页 | 不可逆，带确认框 |
| 运行弹窗勾「修图」 | 选中区间内**已有译文**的页 | 可只勾这一段 |

第三条里 `filter` 用"本页集里 `hasTranslation` 为真的页"：一页都没有译文的页
画出来是一张**去字的白页**，比原图更糟（用户会以为"翻译把字弄没了"）。

`_regenerateResults` 的返回值从 `void` 改成 `(int, int)`（底图数, 成品数）——
否则"跑了���次修图"事后无法区分"画了 0 张"与"根本没跑"。

## 4 · 旧管线：开关，不是删除

```dart
static const bool legacyPipelineEnabled = false;
```

用户明确说过"暂时不要清理老的管线的功能，只需要在软件中暂时让老的管线失效，
后续再按需求改进"⇒ 做成**开关**而非删分支：

- 开关在 `_run` 的**唯一分叉点**读 ⇒ 不存在"某个角落还按旧的跑"；
- 关掉时任务立刻 `failed` + 写日志，**不静默 no-op**（静默会让"我点了预翻译
  但什么都没发生"变成查不到的事）；
- 恢复只需改一行常量。那条路的重试/暂停/断点逻辑调了几个版本
  （`_retryFailedPasses` / `_waitWhilePaused`），将来要复用一半时能省一轮返工。

🔴 **不给 UI 开关**：用户要的是"在软件中失效"，不是"能自己打开又关上"。给开关
就得配文案、配设置项、配"改回 true 之后旧数据的读侧判据对不对"—— 而这些正是
他现在不要的。

### 5.1 🔴 本轮又被门禁抓到一次「判据写错 ≠ 行为没改」

`wiring.save_does_not_spawn_artifact_generation` 第一版判 FALSE。真因**在判据**：

```dart
rest.indexOf(RegExp(r'\n  (Future|void|Widget|String|bool) '))   // ❌
```

而下一行是 `  Future<void> _saveAndRepair()` —— `Future` 后面紧跟 `<` 而**不是
空格**，正则匹配不到 ⇒ 边界退化成"整个文件末尾" ⇒ `_saveAndRepair` 里那一句被
算进了 `_save`。

⇒ 教训已写进断言注释与文件头的 `_memberStart`：`Future<` 必须显式列出。
这条断言把"判据写错了"和"行为没改"报成**同一个失败**，第一反应会去改代码 ——
而真因在判据。**这是本项目特有的坑**：静态扫描类断言的失败必须先确认
"扫描器本身对不对"，再动被扫的代码。
