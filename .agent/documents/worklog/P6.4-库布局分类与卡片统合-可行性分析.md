## 0. 结论（TL;DR）

1. **完全可行，而且你的方案与代码库中三处既有设计"暗合"**——尤其是 `translated/` 这个路径**已经是代码里写死的默认导出根**（`local_comics_page.dart:734-746`，注释原文："to keep all translation/export artefacts out of the pristine download folders"）。
2. **"artifacts 必须外置"不是偏好，是硬约束**：本地扫描器对"章节目录里出现子目录"的做法是**整本拒绝**（`local_comic_scanner.dart:49-58`）。而 FT 产物天生是 `<kind>/<章节>/<页>.png` 两层结构 → 只要留在 `downloads/<漫画>/` 里，该漫画就**永远进不了本地库**。实测 `Error the Echo` 正是如此。
3. **`translated/<漫画>/<章节>/*.png` 的形状恰好就是扫描器想要的**——纯图片、无子目录。所以成品**可以走普通导入流程变成一个完全正常的本地漫画**，零特判、零新机制。这是本方案最大的收益。
4. **"一张卡片统合两版"不需要任何新机制**：`ComicCollection` 已支持 `local` 成员（`collection_source.dart:140-184`）且 `displayMode: tabs` 就是"每成员一个 tab"（`:281-300`）。要做的是**自动建集合**，不是造新轮子。
5. **"翻译组视图"与"两版统合"长得像，但存储/路由是两回事**（你的直觉正确）：前者是**同一话的多个来源**（章节号对齐、路由到不同 chapter id），后者是**整本的两种载体**（不同目录、不同图片文件）。两者在现有模型里**各有原生支持**，建议分而治之（§4）。
6. **"本地库不该重新联网刷章节"成立且可安全落地**：现状是「本地先渲染 → 后台仍联网覆盖」（`comic_page.dart:539-556` + `:744-758`）。而"关注更新"有**完全独立的定时服务**（`FollowUpdatesService` / `FollowUpdateTaskManager`），所以关掉打开时刷新**不会**影响更新检测。
7. **组名目前完全不落盘**：章节目录名只取章节号的数字部分，取不到就整条 chapterKey 消毒（`download.dart:295-300`）→ comix.to 的目录名直接成了 URL 串。要"离线显示翻译组"，得**新增一层落盘**（§5.4）。

## 3. 目标布局定案

### 3.1 为什么 mask/inpainted/result **必须**外置（硬证据）

`lib/utils/local_comic_scanner.dart:47-64`：

```dart
await for (final entry in directory.list()) {
  if (entry is Directory) {
    await for (final child in entry.list()) {
      if (child is Directory) {
        Log.info('Import Comic', 'Invalid Chapter: ${entry.name}\n'
            'A directory is found in the chapter directory.');
        return null;                       // ← 整本拒绝，不是跳过该章节
      }
    }
    chapterDirectories.add(entry);
  } else if (entry is File && _isLocalComicImage(entry)) {
    rootImages.add(entry);
  }
}
```

规则读出来的完整语义：

| 条目类型 | 扫描器行为 |
|---|---|
| 根下**非图片文件**（json / txt / docx） | **静默忽略**（无害）← json 可以放在漫画根 |
| 根下**子目录** | 当作"一个章节" |
| 章节里再出现**子目录** | 🚫 **`return null` —— 整本漫画被拒绝导入** |

FT 产物是天生的两层结构（`mask/0/1.png`、`inpainted/0/1.png`、`result/0/1.png`），所以：

- 根下 `mask/`、`inpainted/`、`result/` 会被当成 3 个"章节"，且它们内部还有 `0/` 子目录 → **拒绝**；
- 章节 `0/` 里若也塞了 `mask/`（S5 实测的双层布局）→ **再拒一次**。

**磁盘实测（S5）**：

```
'Error the Echo'                     -> REJECT   违规: ('0','inpainted') ('inpainted','0') ('mask','0') ('result','0')
'My Dragon Girlfriend Has Returned'  -> OK       chapters=1  cover=cover.jpg
```

`Error the Echo` 之所以"看得见"，纯粹靠 `BtProjectManager` 用 `bt_` 前缀单独注册，**跟本地库扫描器无关**。

> 结论：**你的方案（外置）不是可选项，是唯一让原版漫画能被本地库正常识别的途径。**

### 3.2 三棵树

```
D:/Ballonstranslator_Windows/ComicLibrary/
├── downloads/                     ← 素材库：纯图片章节，只读、不可变
│   └── Error the Echo/
│       ├── cover.webp             ← 可选
│       ├── chapters.json          ← 新增：章节边车（组/语言/状态），见 §5.4
│       └── 0/1.webp 2.webp ...    ← ★ 纯图片，无子目录 → 扫描器 OK
│
├── projects/                      ← 工程库：VeneraX/FT 的工作区（★ 库外，不被扫描）
│   └── Error the Echo/
│       ├── imgtrans_Error the Echo.json   ← ★ 工程身份文档
│       ├── mask/0/1.png ...
│       └── inpainted/0/1.png ...
│
└── translated/                    ← 成品库：定稿位图（★ 扫描器友好，可直接当普通漫画）
    └── Error the Echo/
        ├── cover.png              ← 成品封面（从成品页生成）
        └── 0/1.png 2.png ...      ← ★ 纯图片，无子目录
```

**用户给的实例路径 `ComicLibrary\translated\error the echo\0` 正是这个形状。** ✅

### 3.3 FT json 安放（你问的第 5 点）

**放 `projects/<漫画>/imgtrans_<名>.json`**，理由三条：

1. **json 是"工程"的身份文档**，而工程的工作产物（mask/inpainted）同在一处 → 一个目录 = 一个完整工程，搬迁/备份/删除都是**整目录操作**，不会出现"json 还在、产物没了"的半残状态。
2. **json 放漫画根会污染素材**：虽然非图片文件被扫描器忽略（技术上无害），但它会让 `downloads/<漫画>/` 不再是"纯净的素材快照"，与 §2.1 的既有设计意图冲突。
3. `directory` 字段**继续指向 `downloads/<漫画>`**（原始页所在），`workspace` 字段暂不写（S6 已定案：本版 FT 不读 `workspace`，凭空加键会产生 diff）。

FT 兼容性后果（**必须记入 S11**）：

- FT 打开 `projects/<漫画>/imgtrans_*.json` → `directory` 指向 `downloads/<漫画>` → **原始页找得到** ✅
- 但 FT 找 `mask`/`inpainted`/`result` 一律用 `osp.join(self.directory, ...)`（`proj_imgtrans.py:216-223`，S6 已实测）→ **全找不到** ❌

→ 所以 **"导回 FT" 必须真实搬迁产物，不能只改路径**（S6 结论不变，本方案只是把它坐实了）。**规范存储 = 三棵树；FT 兼容 = 一次显式导出。**

### 3.4 `translated/` 的天生优势

`translated/<漫画>/<章节>/*.png` 满足扫描器的**全部**要求：
纯图片 + 无子目录 + 根/首章能取到封面（`:69-95` 的 cover 兜底逻辑可命中 `0/1.png`）。

**收益**：成品不需要新存储语义、不需要 `bt_` 式特殊注册、不需要改读图链路——**直接复用普通导入流程**（`scanLocalComicDirectory` + `LocalManager().add`）就是一个正常的本地漫画。它自动获得：网格卡片、封面、历史、收藏、导出、删除。

> 建议：工作室保存成品时同时落一个 `cover.png`（取成品第 1 页或工程封面），避免"封面回落到章节首图"导致的额外 IO。

## 4. "一张卡片统合两版"——两条路线

### 4.1 路线 A：集合（`collection` + `tabs`）　← **推荐**

```
卡片: Error the Echo
 ├─ tab「原版」   → downloads/Error the Echo  （LocalComic，普通导入）
 └─ tab「翻译版」 → translated/Error the Echo （LocalComic，成品）
```

- **机制现成**：`CollectionDisplayMode.tabs` = 每成员一 tab（`collection_source.dart:281-300`），tab 名来自 `member.displayName`（用户可命名）→ 直接填「原版」/「翻译版」。
- **本地成员已支持**：章节合并走 `local.chapters.allChapters`，出图走磁盘（§2.3）。
- **代价**：需要"**自动建集合**"这一步（工作室保存成品时，若无对应集合则创建并塞入两成员）。
- **颗粒度**：整本对齐（原版 vs 翻译版），天然符合"两种语言版本"的语义。

### 4.2 路线 B：同卡 `versioned`（把"译文"当成一个组）

```
卡片: Error the Echo
 └─ 第1话 [原版] [译文]   ← 同一话的两个版本，切换即换页
```

- **机制现成**：`ComicChapters.versioned` + `ComicChapterVersion(group, lang, title, key)` + `filterForScanlationGroup` + `preferredVersionKey`（`models.dart:416-453, 583-632`），UI 侧 chips 已实现（`chapters.dart:445-446, 560`）。
- **优点**：颗粒度细，阅读时"读原文对照译文"极自然。
- **🚫 硬障碍**：出图路径绑定 `baseDir`——`local.dart:740-751`：

  ```dart
  var directory = Directory(comic.baseDir);
  ...
  directory = Directory(FilePath.join(directory.path, cid));
  ```

  一个 `LocalComic` 只有**一个 `baseDir`**，而路线 B 需要"同一话的不同版本落在不同根"（原版在 `downloads/`，译文在 `translated/`）→ 必须**给版本加"根"的概念并改路由**。

### 4.3 对比与建议

| | A 集合(tabs) | B 同卡 versioned |
|---|---|---|
| 新增机制 | 仅"自动建集合" | 需给 `LocalComic` 加"多变体根" + 改 `getImagesForComic` 路由 |
| 阅读体验 | 整本切换（tab） | 逐话切换（chip），可对照 |
| 与"翻译组"心智 | 分得开（两版=两本） | 与组混在同一层 |
| 对 reader/history/收藏 影响 | 0（已是 comic source） | 需验证 history 的 (cid, ep, group) 语义 |
| 风险 | 低 | 中 |

**建议：A 为 S7–S8 落地路径；B 可作为 S10 之后的增强（"对照阅读"）单独排期。**
理由：A 只增加"自动建集合"这一件事，且它复用的路径对阅读器/历史/收藏**完全透明**；B 要动出图路由，是本方案里唯一会碰到 reader 内核的地方，不该和布局改造捆在一起。

### 4.4 与"翻译组"的准确区分（你的直觉）

| 维度 | 翻译组（scanlation group） | 翻译版 / 原版 |
|---|---|---|
| 对齐粒度 | **同一话** | **整本** |
| 差异本质 | 同一章的**不同来源版本**（章节号相同、chapterId 不同） | 两种**载体**（不同目录、不同图片文件） |
| 现有载体 | `ComicChapterVersion.group/lang` | 无（需 collection 或版本根） |
| 章节号 | 相同 | 相同 |
| 存储位置 | 同一棵树内 | **不同树**（downloads vs translated） |
| 视图形态 | 章节行上的 chip | 详情页 tab（或版本 chip） |

**结论：视图可以"看起来像"，但绝不能共用同一层存储**——组是"树内的元数据维度"，两版是"树之间的对象关系"。你判断的"存储逻辑可能不一样"是准确的。

### 5.3 为什么关掉"打开即刷新"是安全的

"关注更新"是**独立服务**，不依赖详情页的这次刷新：

- `lib/init.dart:220-223`：`checkUpdates()` → `FollowUpdatesService.initChecker()`
- `lib/foundation/appdata.dart:482-487`：`followUpdatesIntervalHours` / `followUpdatesCheckOnStart` / `followUpdatesFixedTime`
- UI 独立：`lib/pages/follow_updates_page.dart` + `FollowUpdateTaskManager`

→ 关掉打开时刷新，**下载来的漫画仍会被"关注更新"服务照常检测新章节**。风险仅在：少了一次"顺手把在线吐槽/推荐拉进来"的机会（而注释说这次刷新的目的恰恰就是 comments/recommendations）。**建议保留"在线元数据"刷新、但不让它覆盖本地章节表**——即把 `:753-755` 的 `data = res.data` 改成"只合并 comments/recommend/tags，不动 chapters"。

### 5.4 存储介质：章节边车 `chapters.json`

**放漫画根**（非图片文件，扫描器静默忽略，已验证安全）。建议结构：

```json
{
  "version": 1,
  "chapters": {
    "https___comix.to_..._chapter-1": {
      "number": 1, "group": "Luna Toons", "lang": "en",
      "title": "Ch.1", "state": "raw", "dir": "1"
    }
  }
}
```

**为什么不改目录名**：现有已下载的目录名（URL 串）是**已落盘事实**，改名会破坏 `downloadedChapters` 与历史记录的对齐；边车是**纯增量、向后兼容**，旧漫画无此文件时行为与今天一致。

字段设计正好承接你之前定案的 `language` + `translationState: raw|in-progress|released`（P6 §6 决策 4）：**边车是它天然的落点**。

## 6. 风险与红线

| # | 风险 / 红线 | 说明 | 对策 |
|---|---|---|---|
| R1 | 🔴 **四件套不得写进被扫描的树** | 任何 `mask/`、`inpainted/`、`result/` 目录一旦出现在 `downloads/<漫画>/` 内（根或章节里），该漫画**整本被拒** | 落盘前走统一 `ProjectWriter`，路径规则里**硬禁**写入 `downloads/` |

| R4 | 🟠 **FT 打不开 VeneraX 工程的产物** | FT 不读 `workspace`，一律用 `directory` 找 mask/inpainted/result | S11「导回 FT」= **真实搬迁**（复制产物到 `downloads/<漫画>/` 下的临时/导出目录），非改路径 |
| R5 | 🟡 **老工程迁移是"一次性、且对 FT 有损"的** | 把 `downloads/<漫画>/` 内的四件套搬去 `projects/` 后，FT 就地打开该目录会缺产物 | 迁移需**用户确认**；迁移前提示"FT 需用导出功能重新获得产物"；保留回滚（移动而非删除） |

| R7 | 🟡 **两套 collection/grouped 语义混淆** | 同一详情页既有组 tab（collection）又有组 chip（versioned） | 文案区分：collection tab 用「原版/翻译版」；versioned chip 用「组名」 |
