## 2. 三个开门问题是怎么收的（对应 P6.1 §10）

### 2.1 「先写 Dart 分隔符/浮点探针」→ `json_codec.dart`

用探针把 Dart 与 Python 的输出逐条对照（`tools/spike/out/s6_p1_dart.txt` vs `s6_p1_py.txt`），结论：

| 维度 | 结论 |
| --- | --- |
| **字符串转义** | ✅ **完全一致**（18 个用例逐字节相同：`\u0001`/`\u007f`/`\u2028`/U+1F600/组合字符…） |
| **整数 / 布尔 / null / 键序** | ✅ 一致（Dart Map 与 Python dict 同为插入序） |
| **分隔符** | 🔴 **不一致**：Python `", "` / `": "`，Dart `jsonEncode` 无空格 → **必须自实现** |
| **浮点整数值** | ✅ 一致（`20.0` / `0.0` / `-0.0` 都保留 `.0`；**Dart 不是 JS**，JS 会给 `20`） |
| **浮点指数** | 🔴 **不一致两处**（见下） |

浮点指数的两条差异（这是本次最容易踩空的地方）：

1. **切换阈值不同**：Python 在指数 `[-4, 16)` 之外用科学计数法；Dart 的切换点是 21 / -6。
   `1e16` → Python `1e+16`，Dart `10000000000000000.0`；`1e-5` → Python `1e-05`，Dart `0.00001`。
2. **指数补零不同**：Python 指数**至少两位带符号**（`1e-07` / `1e+16` / `5e-324`），Dart 不补零（`1e-7`）。

**实现方式**：不走 Dart 的 `toString()` 排版，而是**从 Dart 的最短往返数字串里重新提取有效数字**，再按 Python 规则重新排版（固定/科学、指数补零、整数补 `.0`）。
这样即使 Dart 与 Python 在"用不用科学计数法"上判断不同，输出仍然一致——因为格式完全由我们按 Python 规则重建。

> 关键收获：**"浮点能不能原样写回"是这次唯一的真技术门槛，不是 JSON 结构。** 探针先行把这个问题一次性钉死，后面 2000 多行模型代码才没有踩坑。

### 2.2 「模型走有序 DOM 透传」→ `text_block.dart` / `project.dart`

**没有**采用"结构化模型 + 只写已知字段"，而是**原始有序 Map 为唯一真源，typed 访问器只做视图**：

- 真实工程有 **23 个 TextBlock 键 + 32 个 FontFormat 键**，FT 还在演进；只写已知字段会把不认识的字段删掉。
- 更硬的理由：样本工程里 **194 个页键中有 97 个是磁盘上不存在的"幻影键"**（`0/001.jpg` 之类，只有键、没有对应文件，62 个真 `.webp` 才有内容）。任何"只保留有效页"的策略都会让往返 diff 非零。
- 因此两条铁律写进了代码注释与实现：
  1. **读取永不物化键**：`fontFormat` 在缺键时返回 `null`（而不是造一个默认对象塞回去）；要编辑才用 `ensureFontFormat()` / `ensureTextEffects()`。
  2. **写入走原 Map**：setter 修改既有键（保留位置），新键才追加。
- 复合字段双写：FT 的 `text_effects` 是 `opacity` / `stroke_width` / `srgb` 三个扁平字段的**真源**，`setOpacity` / `setStrokeWidth` / `setStrokeColor` 会**同时**更新两侧，避免工作室和 FT 对同一文件的理解分叉。

### 2.3 「写契约 `ProjectWriter.save(root, project)`」→ `project_writer.dart`

```dart
ProjectWriter.save({required root, required project, workspace, directory, ...})
```

- **`root` 只是入参**：老工程 `root = ComicLibrary/downloads/<manga>/`，新工程 `root = ComicLibrary/projects/<manga>/`，**同一份实现**。
- 产物命名规则（两套真实样本互相印证）：`<root>/{mask,inpainted,result}/<页键去扩展名>.png`
  （`0/1.webp` → `inpainted/0/1.png`；章节级工程 `1.webp` → `inpainted/1.png`）。
- `workspace` / `directory` **只在显式传入时才写进 json**。
  这条很关键：本版 FT **根本不写 `workspace` 键**（见 §4.3），凭空加一个键就会让"没人编辑过的文件"出现 diff。
- 原子写与 FT 对齐：`<json>.tmp` → replace（`File.rename` 在 Windows 走 `MoveFileEx` 覆盖，失败再退化 copy+delete）。

## 4. 问题与经验教训

### 4.1 🔧 会话内 `dart run` 被 native-assets 钩子挡死 → 用"无 pubspec 目录 + 相对导入"

- **现象**：`cd VeneraX && dart run tool/...` 报
  `CreateFile failed 231 (所有的管道范例都在使用中)` + `ProcessException`，卡在
  `dart compile kernel .../objective_c-9.5.0/hook/build.dart`。
- **原因**：包依赖里有 native-assets build hook（`objective_c`），`dart run` 在包内会先 spawn `cmd.exe` 去编译 hook，而本会话安全策略禁止创建这类子进程。
- **解法**：把驱动放到**没有 `pubspec.yaml` 祖先目录**的位置（`tools/s6_harness/`），用**相对路径**直接 import `VeneraX/lib/...`。
  Dart 不再做包解析，自然不跑 hook；而模型层文件只依赖 `dart:*` 与彼此，所以能直接编译。
- **前提条件**：`translation_project/*` 与 `bt_project/bt_project.dart` **必须保持零 Flutter 依赖**（这也是为什么回退日志被搬到 `bt_project_manager.dart`，而不是在 `bt_project.dart` 里 `Log.warning`）。
- **教训**：把"纯逻辑层不 import Flutter"当成一条硬约束，收益不只是可测试——在受限环境里它是**唯一能快速迭代的通道**（一次 release 构建 ~5 分钟，纯 Dart 通道 <3 秒）。

### 4.2 🐞 `headless` 命令全线卡死（既有缺陷；修了一半，另一半已定位）

- **现象**：`venera.exe --headless <任意命令>` 只打印 Impeller 一行后**永久挂起**；连 `--headless bogus` 也不报 "Unknown command"。
- **第一层原因（已修）**：`main.dart` 里 `runHeadlessMode(args)` **没有被 await**，`main` 立刻返回。
  无命令分支在第一个 `await` 之前就 `exit(1)`，所以这个缺陷一直没暴露；任何真命令都会在第一个插件调用处停住。
  修复：`Future<void> main(...) async { ... await runHeadlessMode(args); ... }`。
- **第二层原因（已定位，未修）**：修复后启动埋点显示卡点前移到了 `App.initComponents()`：
  ```
  [headless] init: App/data/translation
  [headless] init: done
  [headless] init: cookie jar
  [headless] init: components      ← 到此为止（60s 超时）
  ```
  即 `data/history/readLater/favorites/domain/local/TranslationStore` 其中之一（或 `DownloadNetworkGuard.start()`）在无窗口运行下不返回。
- **对 S6 的影响**：**无**。`project-check` 被安排在任何 app 启动之前执行（它只需要文件系统），13/13 正常退出。
- **留给后续**：这是"headless 其它命令（webdav / updatescript / updatesubscribe）"的既有问题，与翻译工作室无关；建议按 7 个 store 逐个加埋点定位，或给 headless 走一条最小化的 `initComponents`（只初始化命令真正需要的 store）。
- **教训**：`main()` 里不 await 异步入口，是一个**只有"同步早退路径"才会掩盖**的 bug；新增异步 CLI 命令时必须先确认入口被 await、并把启动步骤打点。

### 4.3 🔴 **FT 的 `workspace` 字段与 P6 §2.8(b) 的前提不符**（对 S11 有直接影响的发现）

查 FT 源码得到三条事实：

1. `proj_imgtrans.py:216-223`：`mask_dir()` / `inpainted_dir()` / `result_dir()` 是
   **`osp.join(self.directory, 'mask'|'inpainted'|'result')`** —— 产物根取自 **`directory`**，**不读 json 里的 `workspace`**。
2. `proj_imgtrans.py:193-195`：工程 json 路径 = **`<directory>/imgtrans_<basename(directory)>.json`**。
3. `proj_imgtrans.py:1020-1033` 的 `to_dict()` 只写
   **`directory` / `pages` / `current_img` / `image_info`**（外加可选的 `llm_compact_memory`）——
   **不写 `workspace`，也不写 `page_order` / `chapters`**。

而实测样本 json 里**有** `page_order` / `chapters`、**没有** `workspace` —— 与 (3) 一致。

> ⚠️ **因此 P6 §2.8(b) 里这句话需要加注**：
> "新工程的产物天然就是 FT 形态，`workspace` 已指向 `projects/`——FT 打开只需认这个路径。"
> **本版 FT 不会去读 json 的 `workspace`。** A 方案（产物进 `ComicLibrary/projects/`）在**工作室侧**完全成立（VeneraX 的 `bt_project.dart` 是认 `workspace` 的），但要在**本版 FT 里打开**一个 workspace-分离的工程，不能只改 json 的 `workspace`：
> 要么把产物放回 `directory` 下（就地），要么让 FT 用工程目录当 `directory` 打开（此时原图路径就需要另想办法），要么等 FT 侧把 workspace 映射接上。
>
> **对 S11 的影响**："导出为 FT 工程"不能简化为"改 `workspace` 指向"，需要**至少提供一次真实的产物搬迁/复制**（或改为在 `directory` 下单写一份）。建议 S11 开工前先做一次 FT 实测：用 FT 打开一个 workspace-分离的工程，确认它到底读哪个路径。

### 4.4 📌 FT 自己已经有 A 方案（`utils/workspace.py`），但**当前未启用**

- `Ballonstranslator_win_minium/ballontranslator/utils/workspace.py` 实现了
  `manga_source_root`（图片源，只读）→ `translation_workspace_root`（工程产物区，嵌套镜像）→ `translation_export_root`（成品导出区）的三区映射，并**明确写下了动机**：
  > "Venera 的本地库扫描器要求章节目录内只能出现图片文件（任何子目录都会让整本漫画失效）。历史版本 BallonsTranslator 把工程产物（json / mask / inpainted / result / assets）以及 `_source_urls.json` 全部写在图片目录内，会直接破坏 Venera 布局。"
- 但该模块目前**未接入**：全仓库只有 `ui/download_dialog.py` 用了 `workspace.manifest_path_for`；
  `ProjImgTrans` 仍完全走 `directory`；且 `translation_workspace_root` 这个配置项**只存在于 `.btrans_cache/last_version/` 的旧配置副本里**，现有 `utils/config.py` 没有它 → `workspace.is_enabled()` 恒为 false。
- **价值**：① 我们的 A 方案与 FT 自己的演进方向**完全一致**，不是自创；② **"本地库扫描器不能容忍章节目录里有子目录"这条约束，正是 FT 写下 workspace.py 的原因**——这直接解释了 S5 里"为什么会有两套并存工程"，也提示我们：**工作室把产物放到 `projects/` 之外的地方必须谨慎，因为 Venera 的本地库扫描对目录形状很敏感。**

### 4.5 其它值得记的细节

- **`text` 恒为 list、`translation` 恒为 string**：110/110 块都是这个形状（`text` 是 OCR 行列表，`translation` 是译文串）。`TextBlock.sourceLines` / `sourceText` 已按此建模。
- **`image_info` 条目**是 `{finish_code, width, height, translation_target}`，与 `page_order` 一样只覆盖 97 个真页。
- **章节级工程没有 `page_order` / `chapters`**：新模型按"缺失即回落 pages 键序"处理（与旧解析器一致），所以两种工程共用一份代码。
- **旧字段迁移只读不写**：FT 的 `deprecated_attributes`（`size`→pt2px、`weight`/`bold`、`family`、`glyph_slant_angle`）在模型里以 `effectiveFontSize` / `effectiveFontFamily` 等**读取视图**形式复刻，**绝不回写**——否则一个未被编辑的旧工程会被"升级"成新版字节。
- **LDPI=96**：`pt2px = pt*96/72`（`shared.LDPI`），迁移旧 `size` 时会用到。
