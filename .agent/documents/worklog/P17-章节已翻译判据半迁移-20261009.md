## 0 · 缺口从哪来

S9.5-b 把**产出**搬进了工作室管线：成品落工程 `result/`，绑定落 `studioReaderBindings`。
但详情页**读**那一侧有四处没跟着搬，仍在读旧引擎的 `TranslationStore`
（`image_translation.db`）：

| # | 位置 | 作用 | 修复前读什么 |
|---|---|---|---|
| 1 | `comic_page.dart::_buildChapterStatus` | 章节右侧「已翻译 ✓ N 页」 | `storedPageCount` |
| 2 | `comic_page.dart::_chapterHasIdleTranslation` | 「重译 / 删除译文」菜单的出现条件 | `storedPageCount` |
| 3 | `comic_page.dart::_translatedChapterIds` | 「已翻译 / 未翻译」两个状态页签的分组 | `TranslationStore.chaptersFor` |
| 4 | `comic_page.dart::_deleteChapterTranslation` / `_reTranslateChapter` | 实际清理的对象 | `ImageTranslationService.retranslate` |

而 `studio_chapter_runner.dart`（整章跑管线的唯一实现）**一行都不写**
`TranslationStore` —— 只写工程 json 与 `result/`。

### 用户会看到什么

用工作室翻完一整章之后：

- 章节列表**看不到**已翻译标记；
- 长按菜单里**没有**「重译 / 删除译文」；
- 「已翻译」页签**筛不出**这一章。

**症状与「翻译没生效」几乎一样**，但译文其实就在 `result/` 里躺着。

### 🔴 第 4 项是最阴的一处：菜单出现了也是空的

判据修好之后，菜单会**开始出现** —— 而 `_deleteChapterTranslation` 调的
`retranslate` 只清 `TranslationStore` + 渲染缓存，**一行都不碰工程**。
所以「删除译文」会**点了没反应**、提示照样弹、翻开漫画仍是译文（成品位图还在
`result/` 里）。

`_reTranslateChapter` 更糟：它清完旧缓存就把任务丢进队列，而
`studio_chapter_runner` 的去重**只读既有块**（`overlapsExistingBlock`，
防覆盖用户校对过的块）⇒ 工程里旧译文块还在 ⇒ **新译文整章被当成重复丢弃**，
用户看到"重译了但译文一个字没变"。

⇒ 所以第 4 项不是"顺手补一下"，是判据修复的**必要配套**。只修 1~3 会把一个
"看不见"的问题换成一个"点了没反应"的问题。

## 1 · 修法

### 1.1 纯逻辑层：`chapter_translation_state.dart`（新建）

三支判据，全部走注入（`studioProductPages` / `legacyStoredPages`），不碰
implicitData、不碰磁盘 ⇒ 可在 headless 里被注入故障打红：

- `chapterTranslationSource(...)` → `none` / `legacyOnly` / `studioOnly` / `both`；
- `chapterHasTranslation(...)` → 是否已翻译；
- `isTranslatedTab(...)` → 页签归属；
- `translatedPageCountForBadge(...)` → 徽标页数。

三条纪律钉在注释里：

1. 🔴 **并集而非替换**。旧库里躺着 S9.5-b 之前翻的、WebDAV 同步来的章；
   改成只认工程 ⇒ 那些章的标记/菜单/页签**全部消失** —— 从"能看见"变成
   "看不见"，是更糟的回归。
2. 🔴 **判据是「> 0」而不是「绑定存在」**。绑了工程但一页没跑（建完就走）
   不该显示成已翻译。
3. 🔴 **徽标取两侧之和而不是 max**。工作室的 `result/` 与旧缓存是**不同的页
   集合**（工程页键 vs `cacheKey`），相加不重复计数；取 max 会让"工作室翻了
   90 页、旧缓存 3 页"显示成 90 —— 用户以为只翻了 90，实际 93 页有成品。

### 1.2 app 侧：`studio_reader_app.dart`

- `StudioChapterProductCount.forComic/forChapter` —— 数一章在工程里有几页成品。
  判据是 `hasTranslation` **或** `result/` 位图的并集：只数前者会把"只填了块
  没出图"的中间态算丢；只数后者会让"填了块还没出图"闪一下未翻译。
  🔴 走**同一个** `bindingFor`（内部已校验 json 在盘上）⇒ "绑定在但工程被删"
  的章不进结果集。
- `StudioChapterProductCount.clearChapter` —— 清一章的**工作室侧**成品。
  🔴 落地必须走 `captureBlockListEdit` + `ProjectWriter.save`（硬规矩 3）：
  直接 `rawBlocks.clear()` 会绕过脏页登记，`result/` 增量重渲漏页，而且**下一次
  工作室打开会把内存里的旧块写回去**（用户以为删除失败）。

### 1.3 接线（`comic_page.dart`）

- 新增 `_studioProductPages` / `_legacyStoredPages` 两个映射，
  `_loadTranslationState()` 在 `initState` 里加载（`await` 后复查 `mounted`
  —— 几十页工程的读盘足以让用户瞬间关掉弹窗，那时 `setState` 会抛
  `setState() called after dispose()`，症状是"点开章节选择器偶发闪退"）。
- 四处判据改走并集；`_onStoreUpdate` 改为**只更新 legacy 页数再重算**。
  🔴 原因：旧做法 `addAll(current)` 会把集合**收窄** —— 工作室刚翻完的那一章
  被旧库**反向清掉**。
- `_deleteChapterTranslation` / `_reTranslateChapter` 补上 `clearChapter`，
  删完再 `_loadTranslationState()`（否则标记还挂着，菜单还在，可以无限次点）。

### 2.1 🔴 顺手订正：P15/P16 日志里的 edit-check 计数是错的

实测本轮 `199`、新增 `3` ⇒ **基线是 196**。而 P15 记「198」、P16 记「199」
（各称"198→199"）—— 两轮都比实测多 2~3 条。

原因不是断言在减少，而是**当时把 `edit_check.json` 里的条目数当成了断言数**：
报告的顶层 `checks` 数组长度 199 与"断言条数"恰好相等只在纯 1:1 时成立；
实际每条断言在报告里还会带 `passed`/异常字段。⇒ 结论不变（那两轮门禁确实
PASS），但**数字不可再引用**。后续轮次一律以"本轮实测 − 本轮新增"反推基线。

### 2.2 新增 3 条断言（均 绿路径=true / 故障路径=变红）

| 断言 | 钉的是什么 | 故障路径 |
|---|---|---|
| `chapter_state.the_union_survives_both_sides` | 并集判据的**四个场景**一次比完：工作室侧 90 页 ⇒ 已翻译（修复前**判不出来**）；两侧都有 ⇒ `both`；旧库 12 页 ⇒ 仍已翻译（"只认工程"会**弄丢**）；两侧 0 ⇒ 未翻译且不显示徽标；负数夹到 0 | **只读旧库**（S9.5-b 之前那一版）：工作室侧整个被丢掉 |
| `chapter_state.the_other_two_faults_are_caught_too` | 另两个故障副本（只认工程 / 有绑定就算）**都**判出与产品版不同的结论 | 判据不再区分两侧 ⇒ 本条与上一条一起失效 |
| `chapter_state.the_badge_counts_both_sides` | 徽标 = 两侧之和（90+3=93）；徽标与页签归属**同源** | 取 max 时 3 页被吞 |

### 2.3 🔴 本轮自己踩了 A02 的坑，被门禁当场抓住

第一版写了 4 条断言，其中**两条是装饰品**：红路径写成了"换一个**也成立**的输入"
—— 例如断言「只有旧库 12 页 ⇒ 已翻译」，却拿它当「只读旧库」那个故障的反例
（可那本来就该成立）。门禁如实报：

```
"passed":false, "detail":"… | 绿路径=true 故障路径=仍绿(装饰品)"
```

改法（可复用）：**同一个 `typedef` 判据签名**下放**产品版 + 三个故障版**
（只读旧库 / 只认工程 / 有绑定就算），喂**同一组**输入，断言只比"结论字符串"。
这样绿红两版可直接对照，**不必**在探针里做函数同一性比较（第一版试过，
既脆弱又会在真失败时给出误导结论）。

⚠️ 「工作室侧算数」与「旧库侧仍然算数」是**成对**的两条：只钉前者的话，一个
"恒返回 true"的实现也能通过 —— 而那会让**每一章**都显示成已翻译。
