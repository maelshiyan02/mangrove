## 一、BT 为什么把产物写进原漫画文件夹（问题 2）

### 1.1 根因：BT 的工程根 = 图片文件夹本身

`utils/proj_imgtrans.py`：

```python
def load(self, directory, json_path=None):            # :189
    self.directory = directory                        # ★ 传入的就是图片文件夹
    if json_path is None:
        self.proj_path = osp.join(self.directory,
                                  self.proj_name() + '.json')   # :193-195
def proj_name(self) -> str:
    return self.type + '_' + osp.basename(self.directory)        # :186-187
def mask_dir(self):      return osp.join(self.directory, 'mask')       # :216
def inpainted_dir(self): return osp.join(self.directory, 'inpainted')  # :219
def result_dir(self):    return osp.join(self.directory, 'result')     # :222
def assets_dir(self):    return osp.join(self.directory, 'assets')     # :225
```

打开工程 = 打开一个图片目录（`ui/mainwindow.py:792-798 openDir` → `imgtrans_proj.load(directory)`）。
工程 json 里 `to_dict`（`:1020-1033`）只存 `directory` 这一条根路径，`mask/` / `inpainted/` / `result/`
**不单独存**，全靠 `directory` + 固定子目录名实时拼出来。

### 1.2 结果目录树

```
<原漫画图片文件夹>/
├── imgtrans_<文件夹名>.json   # 工程文件（TextBlock 列表 + image_info）
├── mask/<页>.png              # 文字掩膜（inpaint 的输入）
├── inpainted/<页>.png         # 去字后的底图（嵌字的底）
├── result/<页>.png            # 最终嵌字结果
├── assets/                    # 可复用图片资产
└── bubcuts/ , *.docx          # 可选导出
```

保存动作 `ui/mainwindow.py:1618 saveCurrentPage`：先 `imgtrans_proj.save()` 写 json（`:1658`），
再写 `mask`（`:1664`）、`inpainted`（`:1674`），最后 `canvas.render_result_img()`（`:1680`）
渲染并写 `result`（`:1682`）。

### 1.3 这与我们**根本上不同**

| 项 | BT | Mangrove（我们） |
|---|---|---|
| 工程根 | **图片文件夹本身** | 独立目录 `ComicLibrary/projects/<工程名>/` |
| 原图 | 就在工程根里（同目录） | **不复制**，json 的 `directory` 指向 `downloads/<漫画>` |
| 产物与原图 | 同级 | 兄弟目录，**硬禁产物进 `downloads/`** |
| mask | **必须落盘**的中间产物（用户还能手绘改） | 空目录占位（见 §四.4） |

🔴 **可迁移性判定**：BT 的「工程 = 文件夹」模型**不能搬**。原因见 §六 矛盾 1 ——
我们的 `downloads/` 是共享的漫画库根，章节目录里出现任何子目录都会被
`local_comic_scanner` 判为「不是漫画」并把整本拒绝。所以「产物写在原图旁边」这条
在我们的架构里是**红线级禁止**，不是风格选择。

## 二、Mangrove 的嵌字产物落盘在哪（问题 3）

### 2.1 实际落盘位置

`ComicLibrary/projects/MDGH-ch1/`：


- 全部产物**真实存在**（`inpainted` 80 张、`result` 80 张），与 BT 一样是**PNG**。

用 `create(recursive: true)` **建出来的空目录**，没有任何代码往里写（详见 §四.4）。
BT 的 mask 是**真产物**（检测器 → `save_mask` → 去字器读 → `save_inpainted`）。

## 三、BT 的字体、取色与嵌字渲染全景（问题 2 前半）

> 这一节是**移植参考**，不是缺口。列出来是因为问题 4~8 的每一项都要落到这张图上。

### 3.1 字体资产

| 项 | BT 事实 | 位置 |
|---|---|---|
| 内置字体 | **只有一个** `assets/font_refresh/Abel-Regular.ttf`，且**只用于强刷 Qt 字体库**，不参与渲染 | `ui/font_refresh.py:52-54` |
| 默认渲染字体 | `Microsoft YaHei UI`（**系统字体，不打包**） | `utils/shared.py:84-85` |
| 用户字体目录 | `<app>/fonts/`（当前只有 `put fonts here.txt`） | `launch.py:15,75-76` |
| 注册方式 | Qt `QFontDatabase.addApplicationFont` | `utils/font_registry.py:1017` |
| 全局字体配置键 | `global_fontformat.font_family` → `config/config.json` | `utils/config.py:409` |

> `NotoSansSC` 一类打包字体的理由（S9.5-a 验收第 7 步：「字形是打包字体（不是雅黑）」
> 就是为堵这个坑）。

### 3.2 文字颜色与描边：**自动取色为主，用户可覆盖**

- **自动取色**（默认）：OCR 模型自带 **fg/bg 颜色预测头**（`modules/ocr/mit48px.py:578-582`
  两个 `nn.Linear(64,3)`）；逐字累加、逐行取均值、再按区域平均
  （`mit48px.py:190-220` → `utils/textblock.py:654-679` → `utils/textlines_merge.py:537-543`）。
  **fg → 文字填充色，bg → 描边色**。
- **自动描边宽度**：前景/背景色差 < 15 就不加描边，否则 0.2（相对字号）
  —— `utils/textblock.py:711-719 recalulate_stroke_width`。
- **用户覆盖**：`let_fntcolor_flag` / `let_fnt_scolor_flag` / `let_fntstroke_flag` 等 8 个开关
  （`utils/config.py:435-442`），UI 上是 `decide by program` / `use global setting` 二选一
  （`ui/configpanel.py:972-1018`），执行在 `ui/mainwindow.py:1958-2053`。

> ⚠️ 关键点：BT 的取色**不是对区域采主色**，而是**模型预测**。我们要做到等价效果，
> 又不带那个模型，就得自己在前景/背景上做一轮主色聚类（我们 `studio_pipeline.dart:136-141`
> 的注释已经指出：颜色住在 `OcrBlock` 上、聚类输入是逐行的 `TextLine`）。

## 四、能力缺口逐条（问题 4 ~ 8）

### 4.1 【问题 4】抹字复原 —— **没有**

**定义**：对一个已被文本块覆盖、被 inpainting 擦除的区域，把**原图像素**恢复回来
（因为重新划区识别需要原图信息）。

**代码事实**：

- 全库 `grep "restore|恢复|复原|revertOriginal|originalRegion"` 在 `lib/` 只命中
  无关项（`canvas.restore()` 图形栈、窗口还原图标、`PageStorage` 滚动还原、`appdata` 导入还原）。
- 工作室的 undo 栈（`studio_page.dart:124 EditHistory`）回退的是**块模型**（JSON），
  不是**像素**。`captureBlockListEdit` 快照的是 `rawBlocks`。
- 去字产物 `inpainted/` 是**整页覆盖写**的：`renderInpaintedPage`（`result_renderer.dart:151`）
  调 `TextInpainter.erase(image, eraseRects)`，出去就是一个新的整页 PNG ——
  **没有「只恢复某个矩形」的入口**。

**为什么 BT 天然有**：BT 的 mask 是**独立落盘**的中间产物（§一.2），
「复原」= 把该块从 mask 里抹掉再重跑 inpaint；原图始终在工程根里可读。
我们因为没有 mask 产物、且 `inpainted/` 是派生整页图，**缺少"回到原图"的那一跳**。

**结论**：这是一个**真缺口**，且**依赖问题 3 的 mask 生产**（`A08 §4.10.2` 待拍板 18）。

### 4.2 【问题 5】新建文字块后的自动识别 —— **不会发生**

**代码事实**（`studio_page.dart:889-926 _createBlockAt`）：

```dart
final block = TextBlock.createDefault(rect: IntRect(...));   // 只有几何
final command = captureBlockListEdit(page.rawBlocks,
    () => page.addBlock(block), pageKey: pageKey, label: 'Create block');
```

- 建的是**空块**：`TextBlock.createDefault` 不填 `sourceText`，不填 `translation`。
- **没有任何 OCR 调用**：`lib/pages/` 与 `lib/components/` 全库搜 `runOcr|TranslationPipeline|ocrPage`
  **零命中** ⇒ UI 侧根本没有触发识别/翻译的入口。
- 结果：新建块后 `sourceText` 恒为空，块面板显示 `Source: (empty)`（`studio_block_panel.dart:123`）。

**用户期望**：块 = 原文 + 译文两部分；建块后应自动识别框内文字并填充原文
（BT 的行为：画完框 → `run_blktrans(1)` 一步出原文+译文）。

## 六、BT 与我们的「适用场景矛盾」清单

| # | 矛盾点 | BT | 我们 | 处置 |
|---|---|---|---|---|
| 1 | 🔴 **工程根模型** | 图片文件夹本身就是工程根，产物写原图旁 | 三棵树 + **硬禁产物进 `downloads/`**（会触发 `local_comic_scanner` 拒绝整本） | **不能搬**。保留我们的分层 |
| 2 | 🔴 **算法可插拔** | `custom_modules/` 热插拔 + 缺依赖自动 pip 装 + 任意 torch 模型；4 检测器 / 12 OCR / 14 翻译器 | Flutter + ORT FFI + **6 个预置组件**，**运行时装不了包** | 只能做「预置 N 个 + 按需下载」，不能做「任意换算法」 |
| 3 | 🟡 **mask 语义** | 独立落盘的**整页单通道灰度**，用户可手绘改 | 内存里的 `TextMask` 是**逐 region 局部窗口**（`computeMask(image, region)`） | 补 mask 生产必须按 FT 语义**拼整页**，不能 dump 内存那份（待拍板 18） |
| 4 | 🟡 **术语表作用域** | **全局单文件**（`pcfg.module.llm_glossary_path`），不按工程/语言对 | **per-comic**（`cid@sourceKey` / 工作室用 `comicId`） | **保持我们的**（更细），别倒退 |
| 5 | 🟡 **源/目标语言作用域** | 全局，且**切换翻译器会覆盖语言** | per-comic（`TranslationConfig.of(cid, sourceKey)`） | 保持我们的；问题 8 的弹窗是**本次运行**级覆盖，不落盘 |
| 6 | ⚠️ **离线引擎吃不吃术语表** | 只有 `LLMTranslator` / `Sakura` 吃；其余不吃 | 只有真 LLM 吃；已补 **D 桥接**（哨兵替换）覆盖免 Key / NMT | 我们的桥接**比 BT 更进一步** |
| 7 | ⚠️ **VLM 能力** | 魔改分支有 VLM OCR / VLM 上下文 / VLM 页摘要 / LLM 图像去字 | **全库无 vision**（无 image part） | 这是与 BT 最大的能力差；短期不追 |
| 8 | ⚠️ **单块 vs 整页 OCR** | `run_ocr(img, blk_list=[选中块])` 可按块 | `ocrPage(bytes, {sourceLang, targetLang})` 只吃**整页** | 问题 5/6 需补「按块/按区域」识别入口 |

## 八、本节新增的可迁移经验

1. **「BT 的工程 = 图片文件夹」是一条架构红线，不是风格**：跨工程搬能力时，
   先判「对方的根模型我们能不能有」——不能有的那些（工程根、算法热插拔）会**静默**
   把搬过来的代码变成不可用。
2. **「能力存在」≠「入口存在」**：我们的 `StudioRunOptions` 早就有 `sourceLang`/`targetLang`/`glossary`，
   `PageTranslationPipeline.ocrPage` 早就 public —— 问题 5~8 里有 **3 项是纯接线**，
   不是从零造。定位缺口的第一步永远是 `grep` 现有 API，不是设计新类。
3. **验收数字先于结论**：MDGH-ch1 的 `80/94` 是"有产出但不足额"，
   与"恒为 0"是完全不同的故障 —— 别把两者混成一句"产物有问题"。
