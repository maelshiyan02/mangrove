## 3. 🔴 写代码期间遇到的问题（供后续决策）

### 3.1 会话内 `dart analyze` 不可用 → 反馈周期被拉到 ~2 分钟

`dart analyze` 需要拉起 `analysis_server_aot.dart`，同样被 **CreateFile 231** 拦掉。于是静态检查只能靠"计划任务里跑 `flutter analyze`"，一次往返 ≈ 2 分钟。

**代价**：首轮构建一次性暴露 9 个错误。**经验**：进构建前必须手工做一遍类型自检，重点是 Dart 的这几条"不报错但会炸"的规则：

| 规则 | 踩中的次数 |
| --- | --- |
| `num.clamp()` / `int.clamp()` 返回 **`num`**，赋给 `double`/`int` 要 `.toDouble()` / `.toInt()` | 4 |
| `Directory.createSync()` 返回 **`void`**，不能链式取 `.path` | 1 |
| 可空字段（`data`）一旦没判空，后续十几处一起报 `unchecked_use_of_nullable_value` | 8（1 个根因） |
| 局部变量名遮蔽同名静态方法（`final plan = plan(...)`）→ `referenced_before_declaration` | 1 |
| `Future` 返回值未 `await` 赋给同步变量 | 1 |
| API 记错：`ui.Codec` 是 `getNextFrame()` 不是 `getNextImage()` | 1 |

### 3.2 校验项自身有 bug —— 教训：**校验不能假设样本形态**

第一版 `assembly.workspace` 断言"显式设 workspace 后 `isInPlaceLayout` 应为 false"。但唯一样本 `Error the Echo` 是**就地布局**（`json 父目录 == directory`），设了等于没设 → 断言必然失败，套件报 FAIL。

**修法**：重写成三段自洽测试（就地读 / 合成 split 布局 / 显式 workspace 优先），并在 scratch 目录里真建两棵目录树（getter 只接受**存在的**目录）。
**教训**：写校验时先问"这个断言依赖样本的哪个属性"——若是样本的偶然形态，就自己造样本。

### 3.3 实机 `export-check` 第一次跑出 `available=2/291`，暴露三个真设计缺陷

这是本次最有价值的发现，**纯 Dart 套件完全测不到**（它们只测模型，不测"落到磁盘的形状"）：

1. **幻影页键没被过滤。** `result/<页键去扩展名>.png` 会把 `0/1.jpg` 和 `0/1.webp` **映射到同一个文件**。不去重 → 章节页数虚增、编号错乱。判定规则改为：**既无原图、又无成品**的键直接丢弃；"有原图但还没渲染"的页保留并计入 `missing`。
2. **文件夹模式按路径排序选错了工程。** 选中了 `0/imgtrans_0.json`（章节级：`pages` 291 键、`page_order` 为空、`directory` 指向章节目录、**自己根下没有产物**）。改为**取路径最浅的 json**（漫画级）。
3. **目标目录名退化成 `"0"`。** 原来用 `basename(project.directory)`；章节级工程的 `directory` 就是章节目录。新增 `FinishedExport.comicNameFor()`：**父目录里若还有 `imgtrans_*.json`，说明这是章节级工程 → 取父目录名**。

> 顺带确认：阅读器之所以一直正常，是因为 `BtProject.pageKeysForChapter` 早就用"文件存在"过滤了同一批幻影键。**工作室必须用同一把尺子**——这是 S7 里最容易漏掉的一致性约束。

### 3.4 `ComicCollectionStore._write` 是 fire-and-forget → 集合丢落盘而"看起来成功"

第一次 `--publish`：`LocalComic` 注册成功（SQLite 同步写，DB 里查得到），`create()` 也返回了 collectionId，但 **`appdata.json` 里没有 `comicCollections`**。原因：`ComicCollectionStore._write()` 调 `appdata.saveData()` **不 await**，而 headless 紧接着 `exit(0)` → 写入还没落盘就被杀。

**修法**：headless 发布路径在退出前显式 `await appdata.saveData()`。
**教训**：**任何走 `appdata.saveData()` 的持久化在进程退出前必须显式 flush**。更general的教训：一个功能里"一半同步写（DB）、一半异步写（appdata）"时，短命的 CLI/headless 验证最容易只看到成功的一半。

### 3.5 语义错误：「原版」成员抓到了 `bt_` 工程卡

`Error the Echo` 在库里**只有** `bt_` 工程卡（它被扫描器拒绝，见 P6.3），而它的 `directory` 恰好等于源目录 → 按目录匹配的查找把工程卡当成了"原版"。tab 标签写着「原版」，点进去却是重绘版。

**修法**：查找时**排除 `bt_` 前缀**；且标签按实际内容给（`bt_` → 「工程（重绘）」）。集合因此只剩「翻译版」一个成员——这是**正确**的，因为这部漫画确实没有普通原版卡。**集合在下次发布时自愈**（复用同一 id 更新成员表）。

### 3.6 `btProjectRoot` 仍是 `downloads`（未改）

`appdata.json` 里 `btProjectRoot = …\ComicLibrary\downloads`，与本地库根同值。要让工作室扫 `projects/`，需用户在设置里改（或我下一步加一个"迁移默认值"的引导）。**S7 未动用户设置**——这属于配置变更，应由用户拍板时机。

## A.3 🔴 迁移暴露的 3 个设计缺陷（本轮修）

### A.3.1 `save.in-place` 校验把"就地"当成了样本属性

迁移后工程变成**分离布局**（`workspace`=json 父目录 ≠ `directory`=downloads），校验项 `save.in-place` 立刻 FAIL——但它断言的是"保存后必须 `workspace==directory`"，而真正该保证的是"**保存不能改变布局**"。

改为布局感知：`oldReport.isInPlaceLayout == (project.directory == project.jsonDirectory)`。json 字节仍然 identical（没有凭空写 `workspace` 键），这才是契约本体。

### A.3.2 成品库是成品的**长期住所**，而 `result/` 只是 FT 的工作产物

按计划删掉 `downloads/…/result/` 后，`export-check` 立刻报 `available=0/97 missing=97`——因为发布器只认工程自己的 `result/`。

这与实际工作流冲突：FT 渲染完 → 发布到 `translated/` → `result/` 就没用了。改成**幂等发布**：`available = 工程 result 存在 || 目标文件已存在`；`needsCopy = 源在且目标不在`。于是重复发布是 no-op，且成品库天然是成品的唯一真源。

### A.3.3 🔴 off-by-one：`targetPath` 在 `ordinal++` 之前算

改 A.3.2 时新引入的：报告里首项 target 是 `0/0.png`（磁盘上是 `1.png`…`97.png`），`96/97`。**页号与文件名脱钩，单看计数器是发现不了的**（item 的 ordinal 仍是 1,2,3…）。

修正顺序，并把 `plan.numbering` 强化为**同时校验路径**：每项必须满足 `target.endsWith('/<chapter>/<ordinal>.png')`。这类"改一个字段、动到另一处顺序"的 bug 靠纯 Dart 套件测不出来，只有实机跑才暴露。

## A.4 其他实现要点

- **`btProjectRoot` 支持多根**（`;` 分隔）。单根必然二选一：指向 `projects/` 就看不见老的就地工程，指向 `downloads/` 就看不见新工程——这正是这次配置尴尬的根源。老值仍是合法的单根，行为不变。
- **`_ensureCollection` 排除 `bt_` 工程卡**作为「原版」成员（S7 首轮的语义 bug 修复）；`bt_` 若确实被选中，标签按内容给「工程（重绘）」而不是谎称「原版」。
- **工作流交接**：① 你在「本地 → 导入文件夹」选 `ComicLibrary\downloads\Error the Echo`（现在能通过了）② 主页「翻译工作室」→ 进画布 → 点「发布成品」③ 合集自动补上「原版」tab（发布器会找到刚导入的原版漫画并复用同一个集合 id，不会产生第二张卡）。
- ⚠️ **副作用**：工程卡 id 从 `bt_e12050d7` 变成 `bt_5be94984`（id 由 json 路径哈希而来）。旧 id 的**历史/收藏记录会变成孤儿**。这是"用路径哈希当稳定 id"的固有代价，换来的是同一工程无论放在哪都能被认出来。
- ⚠️ **`appdata.json` 已被我用脚本重写**（紧凑格式，与 Dart `jsonEncode` 一致）。原文件备份在同目录 `appdata.json.bak-s7r`。
