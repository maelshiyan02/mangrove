## 0. 八句话结论（TL;DR）

1. **可行，而且比预期更可行**——VeneraX 已经具备翻译工作室 ~80% 的地基：推理管线、任务队列、限流、缓存、渲染器、术语表、离线 NMT 全部现成。
2. **正确形态是"重写"而不是"嵌入"**：用 Flutter 复刻 FT 的**工程模型 + 编辑画布**，复用 VeneraX 的**推理后端**。把 PyQt 程序嵌进来在 Flutter/Windows 上是死路（进程/窗口/字体三重不可控）。
3. **兼容性问题要分三层回答**：**契约层 100% 兼容**（json 是纯数据）、**代码层 0% 可复用**（Python+Qt vs Dart+Flutter）、**推理层可复用**（VeneraX 已把 ONNX 走 FFI 接进来了）。所以"整合"= **复刻契约 + 重写交互 + 共用推理**。
4. **库分类要不按"语言"分，按"角色"分**：`素材库 / 工程库 / 成品库`。外文漫画和中文漫画都是素材，区别只是"是否需要翻译"这个**标签**，不是目录。（注意：**库分"存储层"与"视图层"两层**，见 §2.3(b)。）
5. **跨页气泡方案可行**，但实现不该是"两图拼接"，而是**连续画布 + 联合框 + 坐标回切**（§2.2）；且定位为**自动流水线之后的人工复查工具**（手动触发）。
6. **最大难点不是算法，是 FT 工程 json 的"双向写入兼容"**——它的字段迁移规则（`deprecated_attributes`）相当密集，读漏一个字段，用户回 FT 打开工程就会丢样式。
7. **阅读器天然适配"重绘路线"**——它现在的 BT 工程路径本来就是重绘（`inpainted` + json）；"本地库读成品"只需加一个小分支。预览（连续长画布）可复用现有连续阅读的滚动地基（§2.7）。
8. **老 / 新工程要共用同一套"保存契约"**——同样的四件套（`imgtrans_*.json` + `mask/` + `inpainted/` + `result/`）落在**各自的漫画目录**下，写入器只差一个 `root` 变量（§2.8）。这样"本地库读成品"从 S7/S8 起就有数据，**不必等 S11 导出**；"导出为 FT 工程"也随之退化为"改 workspace 指向"。

### 1.1 三条链路的真实归属

先看磁盘（这是我自己扫出来的，不是推测）：

```
D:/Ballonstranslator_Windows/ComicLibrary/
├── downloads/                      ← 下载库（VeneraX 自己的本地库）
│   └── Error the Echo/
│       ├── 0/                      ← 章节目录（章节目录名 = 章节号）1.webp, 2.webp ...
│       ├── cover.jpg               ← Venera 封面约定
│       ├── imgtrans_Error the Echo.json   ← ★ FT 工程文件就长在这里
│       ├── mask/0/…                ← FT 文字掩膜
│       ├── inpainted/0/…           ← FT 去字底图
│       └── result/0/…              ← FT 嵌字成品
└── translated/                     ← 空目录（导出镜像的目标位，TranslatedExport.buildMirror 用）
```

而应用设置里：

```json
"btProjectRoot": "D:\\Ballonstranslator_Windows\\ComicLibrary\\downloads"
```

**结论（这解释了你截图里的现象）**：FT 工程没有被"收进"什么特殊位置，它就是**直接长在下载漫画的目录上**。VeneraX 用 `btProjectRoot` 去扫，扫到就打上 `bt_` 前缀 id 塞进本地库，所以它出现在「本地 → 翻译工程」tab。它不是"另一套库"，是**同一个漫画目录的另一种解读方式**。

### 1.2 实测 FT 工程 json 的真实 schema

我打开了真实的 `imgtrans_Error the Echo.json`（194 页）：

### 1.4 VeneraX 的 BT 工程接入（`lib/foundation/bt_project/`，2 文件）

- 识别：文件名 `imgtrans_*.json` + JSON 可解析 + 有封面（`bt_project_manager.dart:298`）
- id：`bt_` + 路径哈希（`bt_project_manager.dart:35`）
- 归属：本地页第 5 个 tab（index 4），过滤条件 `id.startsWith('bt_')`（`local_comics_page.dart:144`）
- 渲染：读 `inpainted/<stem>.png` 底图 + 译文区域重绘（`bt_project_manager.dart:196-223`）
- **只读**：无任何 serialize/save；`result/`、`mask/`、`lines`、`text`(原文)、`image_info` **全部不用**
- ✅ **关键发现**：`bt_project.dart:26-30` 已解析 **`workspace` 字段**——注释原文明确它是"BT 生成产物(inpainted/mask/result)的根目录，**可与原图根 `directory` 不同**，就地布局时二者相等"。这说明 **A 方案（原图与产物分家）是 FT 原生支持的形态**，不是我们额外发明的。
- ⚠️ **S5 实测修正**（见 `P6.1-现状探查报告.md` §2）：`workspace` 是**可选字段**，本机真实样本工程（`Error the Echo`）**顶层只有 6 键、没有 `workspace`**，走的是**就地布局**（`root = directory`）。代码在缺失/目录不存在时回落到 `directory`（`bt_project.dart:63-66`）。→ 结论不变，但"工程都用 workspace"这个印象要改成"**workspace 可缺省，缺省即就地**"。

### 1.5 阅读器的真实读取结构（本轮新增，供 §2.7 用）

- **阅读模式**：`ReaderMode`（`reader.dart:1104`）= `gallery`(翻页) + `continuous`(连续：上到下 / 左到右 / 右到左)；且支持**跨章无缝连续**（`_isSeamlessContinuous`、`enableContinuousChapterReading`，`reader.dart:553-565`）。
- **连续模式实现**：`_ContinuousModeState`（`images.dart:840`）= `CustomScrollView` + **章节滑动窗口**（`_ContinuousReaderEntry` image/separator）+ 预加载计数（`preloadImageCount`）+ 每章错误跟踪。→ **这就是"长画布"现成的地基**。
- **统一的图片解析层**：`ReaderImageProvider`（`foundation/image_provider/reader_image.dart`）对每页**分层解析**：
  1. 取原始字节（本地 `file://` 或网络）
  2. **BT 分支**：`btProjectDir != null` → `renderBtPage`（`inpainted` + json **重绘**，`:130-142`）
  3. **翻译分支**：`translationKey != null` → **`findTranslated` 先读已存位图**（`translation_service.dart:416`），未命中才 `renderStoredPage` 重绘（`:143-195`）
  4. 自定义图像处理 → 原始字节兜底
- **缓存失效已接线**：provider key 含 `@bt:<jsonMtimeMs>`（`reader_image.dart:268`）→ **改 json 即自动重画**。

### 2.2 Q2：跨页气泡（截图分割）怎么办？

**先纠正一个前提**：FT **自己也没有**跨页气泡处理。我搜遍了 `merge/split/cross_page/stitch/concat`，只有两个地方涉及跨页，且都与检测无关：

- `utils/page_concat.py:28-84` —— 纯 numpy 垂直拼接工具（本来用于"长条导出"）
- `utils/chapter_export.py:92-115` —— 整章拼成长条导出

FT 处理跨页气泡的唯一手段是**文本层上下文**（把前几页的译文喂给 LLM），**像素层完全没有**。所以这块是**你要新增的能力**，FT 帮不上忙，但它的 `page_layout.compute_vertical_layout`（连续页几何）正好是地基。

**你的方案（拼接→翻译→切回）方向对，但"两张图拼接"这个表述会踩三个坑**：

| 坑    | 说明                                                         |
| ---- | ---------------------------------------------------------- |
| 坐标污染 | 拼出来的临时图上检测到的框，y 坐标是"缝合带坐标系"的，切回单页要减去页高偏移，`lines` 四边形还要逐点平移 |
| 回切腰斩 | 如果译文框横跨缝线，切回后文字会被页边界**劈成两半**（上半页半行、下半页半行）                  |
| 渲染顺序 | 译文要按"每页各自渲染"还是"整条渲染再切"？两种结果不同，前者会重复描边                      |

**建议的算法（连续画布方案，代替物理拼接）**：

```
① 建临时条带：只有"接缝带"（第 N 页底部 K px + 第 N+1 页顶部 K px），K ≈ 0.35 × 页宽
② 只对条带跑检测（复用现有 DBNet），成本极低
③ 若某框同时跨越缝线上/下：判定为"跨页气泡"
   → 把两页对应区域一起裁出来（完整气泡），走 OCR + 翻译
   → 按缝线把译文分成上下两段（按行高整数分配，不切断行）
④ 回写：上半段作为第 N 页的独立 TextBlock，下半段作为第 N+1 页的独立 TextBlock
   → 两页各自渲染，缝线处按基线对齐
⑤ 在工程 json 里给这两个块加互指标记（自定义扩展字段，FT 读到时忽略）
```

**关键设计决策**（你的第 5 条）：这个能力**应该是"可选的修复工具"，不是自动流水线的一部分**。理由：接缝检测本身有误判率，自动合并会污染正常页面。做成**画布上的手动入口**，定位为**自动流水线跑完后的复查工具**。

### 2.3 Q3：保存逻辑差异 + 本地库/翻译库该怎么分？

#### (a) 三套存储的真实差异（这是你截图里"归入本地库 vs 翻译库"的根因）

| 维度     | 本地库（下载的漫画）             | FT 工程                                              | VeneraX 翻译库                         |
| ------ | ---------------------- | -------------------------------------------------- | ----------------------------------- |
| 物理形态   | 目录 + 章节子目录 + 图片        | **同一目录上叠 json + mask/inpainted/result**            | SQLite 行 + 缓存位图                     |
| 注册表    | `LocalManager`（本地库 DB） | `bt_` 前缀塞进 `LocalManager`                          | 无独立注册表，来自 `TranslationStore.comics` |
| 元数据来源  | 源站 API                 | **目录名当标题、祖父目录名当作者**（`bt_project_manager.dart:352`） | `translated_chapter_index` 表        |
| 粒度     | 章                      | **页 × 文字块 × 45 字段**                                | 页 × 气泡（`regions` json）              |
| 可编辑    | ❌                      | ✅（FT 侧）                                            | ❌（只读展示）                             |
| 与图片的关系 | 图就是图                   | 图 + 掩膜 + 底图 + 成品，**四份**                            | 只有渲染后的成品位图                          |

**看到问题了吗**：FT 工程的元数据是"从目录名猜的"（标题=目录名、作者=祖父目录名），而 VeneraX 下载库有完整的源站元数据。同一个漫画，**两边记的是两套信息，且互不知道对方**。

#### (b) 库模型：**先分清"存储层"与"视图层"**（这是你困惑"素材库会不会重复"的根因）

你的担忧是："如果唐突地再设一个素材库，就和原本的生肉文件地址重复了。" —— **不会重复，因为你把"存储的位置"和"显示的视图"当成一回事了。** 它们是两层：

**① 存储层（真实存在于磁盘的目录，三个）**

```
D:/Ballonstranslator_Windows/ComicLibrary/
├── downloads/      ← ★ 素材库 = 下载来的生肉（外文/中文同构），只读、不可变
│                        = 你现在这个目录本身，一个字节都不动、不搬家
│                        （老 FT 工程就地长在这里：json + mask/ + inpainted/ + result/）
├── projects/       ← 工程库（A 方案新建）：可编辑工作区，一漫画可有多份工程
│                        共用统一保存契约（§2.8）：json + mask/ + inpainted/ + result/
└── translated/     ← 成品库：定稿分发产物（result 位图 / CBZ / PDF），只读
```

**② 视图层（tab，只是对存储的筛选器，不是一个位置）**

| 视图（tab）   | 数据来源      | 说明                                      |
| --------- | --------- | --------------------------------------- |
| **本地库**   | 素材库 + 成品库 | **阅读入口**。你说的"本地库直接打开阅读"，读的就是这里的图        |
| **翻译工作室** | 工程库       | **编辑入口**。原"翻译库"改名而来（显示名改，section id 不动） |
| 素材库       | ——        | **不是 tab**，是 downloads/ 这个目录的"角色名"      |
| 成品库       | ——        | **不是 tab**，是 translated/ 这个目录的"角色名"     |

> **所以**：`素材库` ≠ 新建的东西。它**就是现有的 `ComicLibrary/downloads/`**，只是给它一个"角色名"。三库是**角色的划分**，不是三份拷贝——**没有任何地址重复**。你原来的"本地库"这个 tab 是**视图**（阅读用），"素材库"是**存储**（角色），两者不在一个层级，不冲突。

**为什么按角色分、不按语言分**：

1. **素材与工程解耦** = 一个生肉可以出"简中/繁中/英化"三份工程，而不用把生肉复制三遍。
2. **成品独立** = 现在 VeneraX 的翻译库（SQLite + 位图缓存）本质是"成品库"的轻量形态，应把它**归位到成品层**，而不是跟"翻译开关"这种状态混在一起。
3. **FT 工程天然落进中间层**——而且它的 `directory` 字段本来就指向素材，说明 FT 自己也是"工程引用素材"的思路（只是它把 `mask/inpainted/result` 直接写进了素材目录，是个历史设计缺陷，工作室应该把产物挪到独立工程目录）。

> ✅ **A 方案是 FT 原生支持的，不是我们凭空造的**：`bt_project.dart:28` 里 **`workspace` 字段的设计含义就是"产物根目录，可与 `directory`（原图根）不同"**（注释原文：*"Absolute root of BT's generated artifacts (inpainted/mask/result). Equals directory when the project uses BT's in-place layout."*）。也就是说 FT 早就预留了"原图与产物分家"的能力，只是默认用了就地布局。**所以走 A 方案的兼容风险，比上一版评估的低得多。**

> ⚠️ **仍需一个显式操作**：若工作室把工程产物写到 `projects/`，则**FT 直接打开 `downloads/` 会看不到这些产物**（FT 只认自己 json 里 `workspace`/`directory` 指的位置）。解决：提供"**导出为 FT 工程**"——把 json + 产物镜像回一个 FT 能识别的位置（显式按钮，不是自动）。因为有了 `workspace` 字段，这个镜像甚至可以只改 json 里的 `workspace` 路径指向 `projects/`，**连产物文件都不用复制**。

#### (c) 外文漫画 vs 中文漫画，要不要区分？

**不该按语言分目录**，理由：

- 语言是**属性**不是**角色**。"日文生肉"和"中文漫画"在存储上完全同构，硬分目录会导致：同一部漫画出了官方中文版后要搬家；中译英需求无法归档。
- 你提到"外文漫画属于翻译工程的生肉原件"——这个判断是对的，但结论应该是：**所有下载漫画都默认是"素材"，其中"是否需要翻译"用标签表达**。

**建议**（你的第 4 条，已定案）：在 `LocalComic` 上加两个字段（或复用 tags）：

| 字段                 | 取值                                              | 用途                 |
| ------------------ | ----------------------------------------------- | ------------------ |
| `language`         | `ja / ko / en / zh-Hans / zh-Hant / …`          | 决定默认 OCR 引擎与默认翻译方向 |
| `translationState` | `raw`（未处理）/ `in-progress`（有工程）/ `released`（有成片） | 决定它出现在哪个库视图        |

这样：

- 「本地」tab 显示 `raw` + 全部语言
- 「翻译工作室」tab 显示 `in-progress`
- 「成品」视图显示 `released`
- **中文漫画默认 `language=zh`、`translationState=raw`** → 不参与外译中流水线，但可以参与中译外

#### (d) 你的第 3 条追问：译文 / 字体 / 颜色到底存在哪？

**答案：全部存在 `imgtrans_*.json` 一个文件里，没有单独的"样式文件"。** FT 把"文字的视觉样式"直接挂在每个文字块上：

```
imgtrans_<title>.json
└── pages["0/1.webp"] : [ TextBlock, TextBlock, ... ]
      └── 每个 TextBlock
            ├── xyxy                ← 位置
            ├── translation         ← ★ 译文文本（就存在这）
            ├── text / lines        ← 原文 + 文字行四边形
            └── fontformat          ← ★ 字体/字号/颜色/描边/对齐/行距/字距/竖排/特效（32 字段）
                    ├── font_family / font_size / font_weight
                    ├── frgb（填充色） / srgb（描边色） / stroke_width
                    ├── alignment / vertical / italic / underline
                    ├── line_spacing / letter_spacing
                    └── text_effects / text_transform（描边/阴影/发光/渐变…栈式结构）
```

**所以工程库的完整构成是**：

| 组件                | 角色                                            | 你原来的理解                                        |
| ----------------- | --------------------------------------------- | --------------------------------------------- |
| `imgtrans_*.json` | **元数据 + 译文 + 全部样式**（译文文本、字体、颜色、字号、对齐、竖排…都在这里） | ❓ 你不清楚存哪 → **就是这里**                           |
| `mask/`           | 文字掩膜（扣下来的文字区域，用于去字）                           | ✅ 你理解对                                        |
| `inpainted/`      | 去字底图（挖空白的气泡底图）                                | ✅ 你理解对                                        |
| `result/`         | **嵌字成品位图**                                    | → **统一保存契约下它也是工程目录的产物之一**（§2.8）；对外作为"成品库"的读取源 |

> 🔴 **必须纠正一处事实**：你说"我们在本地库里面直接打开阅读的是 `result/` 文件夹里面的成品"——**目前不是**。VeneraX 现在阅读 FT 工程时，走的是"**用 `inpainted/` 底图 + json 里的译文区域，实时重绘**"（`bt_project_manager.dart:183-224`），**根本不读 `result/`**。视觉结果与 `result/` 等价（都是"去字 + 嵌字"），但机制是"重绘"而非"读位图"。
>

### 2.4 Q4：开发计划怎么推进？

**编号冲突已定案**（你的第 1 条）：原《P5 计划》的 `S5=下载稳定性增强 / S6=翻译工作室配套` 作废，改为**工作室独占 S5–S11、下载增强顺延为 S12**。下面是重排后的顺序（详见 §4）。

**推进原则**（沿用你已验证有效的方式）：

- 一阶段一交付 → 你人工验收 → 再进下一阶段
- 每阶段只碰少数文件，可单独回退
- 每阶段末构建 + 给验收清单

**顺序逻辑**（这条很重要）：

```
现状探查小样（S5）   ── 零风险只读探针，把 json 往返/四件套目录/渲染/依赖面钉死
      ↓

      ↓
只读画布（S7）      ── 看得见；同时完成「翻译库→翻译工作室」改名 + 旧只读网格下线
                        + 本地库「成品优先读取」+ 工作室「连续长画布预览」
      ↓
可编辑画布（S8）    ── 改得动；★保存即产四件套（result 后台异步）；旧即时翻译退出
      ↓
检测/OCR 升级（S9） ── 自动流程达到 FT 水准
      ↓
跨页气泡（S10）     ── 手动复查工具（FT 没有）
      ↓
术语/记忆 + 导出回流（S11）
      ↓
下载功能增强（S12） ── 工作室全部完成后再做
```

**为什么"可编辑画布"必须排在"检测升级"前面**：因为检测算法的调优需要**可视化验证工具**。没有画布，你没法判断"这个框合并得对不对"。先把"看得见、改得动"做出来，后面每一步调优才有肉眼反馈。

### 2.5 Q5：难点清单（按难度排序）

| # | 难点                   | 为什么难                                                                                                                                   | 应对                                                                                                      |
| - | -------------------- | -------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |

#### (a) 阅读器适配性（逐条核对 §1.5 的事实）

| ---------------- | --------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |

| 场景               | 读取来源                                                | 机制   | 可编辑         | 定位                    |
| ---------------- | --------------------------------------------------- | ---- | ----------- | --------------------- |
| **本地库 · 打开翻译工程** | **成品 `result/`**（有则直读位图，无则重绘兜底）                     | 位图优先 | 否（阅读）       | **成品视图**——定稿的、要分发的样子  |

> **关键点**：两条路线**代码上是同一个 `ReaderImageProvider` 的小分支差异**，不是两套系统。这比原计划的"二选一"更清晰，也更省工。**§2.3(d) 的"路线①/②"之争就此解决：两者都要，按场景分工。**

#### (c) 预览功能（连续长画布）能否实现？—— 能，但要分清"复用边界"

阅读器的连续模式（`_ContinuousModeState`）是一套成熟的**滚动 + 章节滑动窗口 + 预加载 + 错误跟踪**实现。工作室的"长画布预览"与它**同构**，但有一个**结构性差异**：

| 维度                | 阅读器连续模式               | 工作室预览                               | 能否复用                    |
| ----------------- | --------------------- | ----------------------------------- | ----------------------- |
| 滚动容器 / 分页加载 / 降采样 | ✅ 有                   | 需要                                  | ✅ **复用策略**（不是复用 widget） |
| 章节滑动窗口 / 预加载计数    | ✅ 有                   | 需要                                  | ✅ **复用策略**              |
| 交互                | 翻页 / 缩放 / 收藏          | **点选文字块 / 编辑 / 拖拽**                 | ❌ **必须新增**              |
| 渲染源               | `ReaderImageProvider` | 同款 `renderTranslatedPage` + 可选叠加编辑层 | ✅ 渲染可复用                 |

**建议方案**：工作室预览 = **新画布组件**（S7 的 `text_block_canvas.dart`）套一个**连续滚动容器**；"类似连续阅读"用于**复用滚动性能策略**（分页加载 / 降采样 / 预取），**不是**复用阅读器 widget（阅读器是只读的，无法承载点选/编辑）。

> 即：**不要试图把工作室塞进阅读器**，而是给工作室做一个"能编辑的连续画布"，其滚动体验对标阅读器的连续模式。

### 2.8 补充（你的第 8 条）：老 / 新工程**统一保存契约**

**你的要求**："把老工程和新工程的保存逻辑统一，都在**各自的漫画文件目录地址**下生成 `inpainted`、`mask`、`result`、相关 json 文件等等。……直接安排在阶段中一起实现是最稳定的选择。"

**结论：可行，而且应当作为 S6 的「写入契约」一次定死——越早定，后面越稳。** 这条正好把 §6.1 那个"待确认项"一并消掉。

#### (a) 统一的是什么、不统一的是什么

| 维度             | **统一**（同一套契约 / 同一份代码）                                                | **不统一**（按工程各自的根）                                                                                                                                                             |
| -------------- | -------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 产物集合           | **固定四件套**：`imgtrans_*.json` + `mask/` + `inpainted/` + `result/`     | ——                                                                                                                                                                           |
| 目录布局           | `<root>/<章>/<页>.webp` ↔ `<root>/{mask,inpainted,result}/<章>/<页>.png` | ——                                                                                                                                                                           |
| 写入器            | **一个 `ProjectWriter.save(root, project)`**，`root` 只是入参               | ——                                                                                                                                                                           |
| 原子写            | `.tmp` → `os.replace` 同款（`proj_imgtrans.py:1004`）                    | ——                                                                                                                                                                           |
| 未知字段           | 读到不认识就原样透传                                                           | ——                                                                                                                                                                           |
| **根目录 `root`** | ——                                                                   | **老工程**：`root = 漫画目录本身`（`downloads/<manga>/`，`workspace == directory`，就地布局）<br />**新工程**：`root = 工程目录`（`ComicLibrary/projects/<manga>/`，`workspace = 工程根`、`directory = 素材根`） |

> **一句话**：**结构、命名、字段、原子写、透传规则——全部统一；差异只在 `root` 一个变量。** 于是"老工程"和"新工程"在代码里是**同一种对象**，只是落在不同的根目录。

#### (b) 这正是 `workspace` 字段的标准用法（与 §2.3 的 A 方案自洽）

FT 的 `imgtrans_*.json` 顶层已有 `directory`（原图根）与 `workspace`（**产物根，可与 directory 不同**）：

| 工程类型          | `directory`          | `workspace`         | 布局      |
| ------------- | -------------------- | ------------------- | ------- |
| 老工程（FT 就地）    | `downloads/<manga>/` | **同 directory**     | 就地布局    |
| 新工程（工作室 A 方案） | `downloads/<manga>/` | `projects/<manga>/` | 原图与产物分家 |

**同一份 `ProjectWriter` 按各工程自己的 `root` 写入**，于是：

- 老工程被工作室保存后，**仍是 FT 能直接打开的样子**（root 没变）。
- 新工程的产物**天然就是 FT 形态**，`workspace` 已指向 `projects/`——FT 打开只需认这个路径。
- **"导出为 FT 工程"退化为"把 `workspace` 指回去 / 复制一份目录"**，不再需要单独的格式转换代码（S11 工作量下降）。

> 🔴 **S6/S7 前修正（2026-10-05，详见 `P6.3-S7前风险分析与评估.md` §1）**——上面"FT 打开只需认 `workspace`"这句**不成立**，两层原因：
> 1. **本版 FT 根本不读 json 里的 `workspace`**：`proj_imgtrans.py:216-223` 的 `mask/inpainted/result` 一律取 `osp.join(self.directory, …)`，`to_dict()` 也只写 `directory/pages/current_img/image_info`。
> 2. 更根本的是：**产物不能"就地躺在被 VeneraX 本地库扫描的目录里"**。`local_comic_scanner.dart:51-58` 规定**章节目录内出现任何子目录 → 整本漫画被拒绝导入**（实测 `downloads/Error the Echo` 现在就被拒，因为它根下有 `mask/0`、`inpainted/0`、`result/0`，章节 `0/` 内又有 `mask/` 等子目录）。
>
> 因此：S11 的"导出为 FT 工程"**必须真实铺设/搬迁产物到一个安全的 root**，不能只改路径；同时 A 方案（`projects/`）从"可选便利"升级为**结构性红线**。

#### (c) 保存时机 —— `result/` 纳入保存流程（回应 §6.1）

| 产物                     | 时机                            | 理由                                                |

### 2.11 补充（你的第 11 条）：翻译库的「组装」+ 工作室显示层（**与阅读器是两套逻辑**）　🟠 S7/S8 核心设计

**(a) 「组装」到底是什么：一个工程 = 两个根 / 六类文件**

FT 的工程是**就地**的（一个 `directory` 同时当原图根与产物根）；A 方案把它拆成两根，所以工作室"打开工程"必须先**组装**：

| 根 | 取值来源 | 内容 |
| --- | --- | --- |
| `sourceRoot` | json 的 **`directory`** 字段 | 原图 `<page>.<ext>`（顺序由 `page_order` 决定） |
| `artifactRoot` | **json 所在目录**（= `projects/<漫画>/`） | `mask/` `inpainted/` `result/`（`<页键去扩展名>.png`） |

🔴 **必须改一处取值来源**：S6 的 `TranslationProject.workspace` 目前**读 json 的 `workspace` 字段**，而 **FT 从不写这个字段**（§2.10(b)）→ 对 A 方案工程它回落成 `directory`（= `downloads`）**指错**。
**定案规则**：`artifactRoot = json 显式写了 workspace ? workspace : <json 的父目录>`。这一条**同时兼容两种情况**：

- 老工程（json 在 `downloads/<漫画>/`）→ 父目录 == `directory` → 就地布局，**行为不变**；
- 新工程（json 在 `projects/<漫画>/`）→ 父目录 == 产物根 → **正确**。

且**不写回 json**，保持 FT 往返**零字节 diff**（S6 验证约束不许破）。

组装后一页需要**六类信息**，且每条都要有降级：

| # | 信息 | 来源 | 缺件降级 |
| --- | --- | --- | --- |
| 1 | 页序 | json `page_order` | 无 → 空 |
| 2 | **底图** | `inpainted/<key>.png` | 缺 → **退原图**（FT 同策略） |
| 3 | **文字块** | json `pages[key]`（`xyxy` / `translation` / `fontformat`） | 空 → 只读底图 |
| 4 | 原图 | `downloads/<key>` | 缺 → 幻影页键，跳过 |
| 5 | `mask` | `mask/<key>.png` | 缺 → 不妨碍编辑，只影响"重做去字" |
| 6 | `result` | `result/<key>.png` | 缺 → 只影响成品预览 / 导出 |

**(b) 🔴 显示层是**三套**逻辑，不是两套**

| | ① 阅读器（现状） | ② 工作室 · 单页编辑画布 | ③ 工作室 · 连续长画布 |
| --- | --- | --- | --- |
| 输入 | 一个 page key | 底图 + **TextBlock 列表（结构化）** | 多页拼接的**虚拟化**场景 |
| 输出 | **一张 `Uint8List`**（不透明） | **图层**：底图 / 框 / 译文 / 选中态 | 位图流 + 可选红框 |
| 交互 | 缩放、翻页 | 拖拽、命中、双击编辑、属性面板 | 滚动、**框选跨页** |
| 坐标 | **不暴露**（渲染进像素里） | **必须暴露**（`xyxy` 就是编辑对象） | 暴露 |
| 现状落点 | `ReaderImageProvider` BT 分支：`renderBtPage` 用 `inpainted`+json 重绘、**丢弃 `result/`**（`reader_image.dart:130-142`） | **无，须新建** | FT 有 `continuous_canvas.py` 先例；VeneraX 可复用 `_ContinuousModeState` 的虚拟化/滚动策略 |

> **核心结论**：**阅读器把"渲染"封在 ImageProvider 里（一页进、一图出）；工作室必须把"底图 / 框 / 译文"作为三层结构交给 UI。**
> ⇒ 工作室**不能复用** `ReaderImageProvider`，须新建 `ProjectPageView`；只共用**解码预算**与**缩放/滚动**策略（细化 §2.7(c) 的"编辑层单写"）。

**FT 现成先例（`continuous_canvas.py` 文件头原文，可直接抄三条）**：

1. **浏览视图与单页编辑画布刻意分开**（`continuous_canvas` vs `canvas`）—— 与我们的结论一字不差；
2. **虚拟化**：任何时刻只有与视口相交（+1 屏缓冲）的页持有解码位图 → 上千页长画布不爆内存；
3. **默认显示 `inpainted`**（阅读干净），**无则退原图**；跨页框选时**强制显示原图**（要看被切开的原文）。

**(c) 顺带发现（S7 可顺手优化）**：阅读器 BT 分支现在**先把原图 bytes 读出来**（`reader_image.dart:100-126`），随后被 `renderBtPage` 的渲染结果**覆盖丢弃**（只有渲染失败才当兜底）。工作室可改成"**先判 `inpainted` 是否存在，再决定要不要读原图**"，省一次整页读盘。

**(d) 落到阶段**：**S7** = 组装（两根绑定 + 六类降级）+ 只读画布（`ProjectPageView` 只读版）+ 连续长画布预览；**S8** = 可编辑（命中 / 拖拽 / 属性面板 / Undo）。
