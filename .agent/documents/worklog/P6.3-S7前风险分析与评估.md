## 1. 风险一：本地扫描器不容忍"章节目录含子目录"

### 1.1 你的判断——基本正确，且有官方旁证

你说："软件默认了导入文件夹必定是一个漫画，里面只有各个章节……尤其是原本是章节的文件夹，如果里面有别的格式文件，就容易出现错乱，识别不了，必须全部都是纯图片，才能被认定成一个章节。"

FT 侧的 `utils/workspace.py` 文件头注释恰好是同一条结论的官方记录：

> *"Venera 的本地库扫描器要求章节目录内只能出现图片文件（**任何子目录都会让整本漫画失效**）。历史版本 BallonsTranslator 把工程产物（json / mask / inpainted / result / assets / txt / docx）以及下载清单 `_source_urls.json` 全部写在图片目录内，会直接破坏 Venera 布局。"*
> —— `Ballonstranslator_win_minium/ballontranslator/utils/workspace.py:6-9`

而且 FT 自己就为了这件事写了 `workspace.py`（把产物从图片目录搬到独立工作区），动机原文写着：**"就是 Venera 扫描器不容忍章节目录里有子目录"**。所以这不是我们的推测，是 FT 已经踩过并留档的坑。

### 1.2 扫描器的真实规则（VeneraX 侧代码级）

权威实现在 `VeneraX/lib/utils/local_comic_scanner.dart:21-135`，逐条翻译：

| 规则 | 代码位置 | 内容 |
| --- | --- | --- |
| **R1** | `:49-60` | 漫画目录下的**每个直接子目录 = 一个章节** |
| **R2** | `:51-58` | **章节目录内只要出现一个子目录 → 整个漫画 `return null`（拒绝导入）**，并打印 `Invalid Chapter: <目录名> / A directory is found in the chapter directory.` |
| **R3** | `:61-63` | 非图片文件（json/txt/docx…）**被静默忽略**，不致命 |
| **R4** | `:69-103` | 必须有封面图（根目录 `cover*` → 根目录首图 → 首个章节首图），否则 `Invalid Comic: … No cover image found.` |
| **R5** | `:8` | 图片后缀白名单：`jpg jpeg png webp gif jpe`（无 `avif` / `bmp`） |

> 补充：BT 工程的**另一个**扫描器（`bt_project/bt_project_manager.dart:305-327`）是另一套逻辑——按 `imgtrans_*.json` 找工程、深度 ≤6、跳过 `mask/inpainted/result/assets` 与隐藏目录。它与本地库扫描器互不干涉，这解释了为什么 BT 工程能"绕开" R2 出现在库里。

### 1.3 实测：逐本模拟判定（磁盘真实数据）

用 R1–R5 对 `ComicLibrary/downloads/` 逐本判定：

```
'Error the Echo'                        chapters=4  rootimgs=1  cover=cover.jpg -> REJECT(章节目录含子目录)
     违规章节: [('0','inpainted'), ('inpainted','0'), ('mask','0'), ('result','0')]
'My Dragon Girlfriend Has Returned'     chapters=1  rootimgs=1  cover=cover.jpg -> OK
```

**关键事实**：`Error the Echo` **当前会被本地库扫描器整体拒绝**。它的违规点正是"两套产物并存"：

- 漫画根的 `mask/`、`inpainted/`、`result/` 被当成 3 个**章节**，而它们内部还有 `0/` 子目录 → 触发 R2；
- 章节目录 `0/` 内部还有 `mask/`、`inpainted/`、`result/` 子目录 → 同样触发 R2。

它之所以还能以 `bt_` 卡片出现在库里，是因为 `BtProjectManager` **单独注册**（`bt_project_manager.dart:349-398`，id 前缀 `bt_`、tag `BT`），完全不经过本地库扫描器。

**结论**：本地库 tab 与 BT 卡片是**两条独立的注册链**。S7 的"本地库读成品"必须落在 BT/工作室这一侧（按已知路径读文件），**不能指望本地库扫描器去把 `result/` 认出来**。

### 1.4 由此产生的四条硬红线（必须写进契约）

A 方案（`projects/` 独立根）从"设计偏好"升级为**结构性必需**：

| # | 红线 | 违反后果 |
| - | --- | --- |
| **红线 1** | 新工程根 `ComicLibrary/projects/` 必须是**本地库根 `ComicLibrary/downloads/` 的兄弟目录**，不能落在其内部 | 落进去 → `mask/` 等被当章节 → R2 整本拒绝 |
| **红线 2** | **任何 `mask/ inpainted/ result/` 都不能写进"被扫描的章节目录"** | 同上，整本失效 |
| **红线 3** | "统一保存契约"（你的第 8 条）里的"各自的漫画文件目录"= **工程根**，不是"被扫描的素材目录" | 若照字面把四件套写进 `downloads/<manga>/`，会亲手制造 §1.3 那种坏布局 |
| **红线 4** | 若哪天要让**本地库**把工程/成品当"漫画"显示，**必须走管理器显式注册**（照 `BtProjectManager` 的路子），不能依赖扫描器 | 否则要么看不见，要么因 R2 被拒 |

> ⚠️ 同时给出一条**配置不变式**：本地库路径必须精确停在 `…/downloads`。若用户把本地库根改到上一级 `ComicLibrary/`，则 `projects/`、`translated/` 会各自变成"一本漫画"，其中 `projects/<manga>/mask/0/…` 会触发 R2 被拒——表现为"库里多出莫名其妙的条目 / 某些条目打不开"。建议在设置页给一句提示，或在启动时记一条 Log。

### 1.5 对后续各阶段的逐条影响

**S11 的影响（重要修正）**：P6 §2.8(b) 原文写"新工程的产物天然就是 FT 形态，`workspace` 已指向 `projects/`——FT 打开只需认这个路径"。**这句不成立**，两层原因：

### 1.7 顺带发现的一个设计机会（可选）

既然扫描器的判定这么简单（章节目录 = 纯图片即可），**成品库可以设计成"本地库能直接识别"的形态**：

```
ComicLibrary/translated/<manga>/
└── <章节>/
    ├── 001.jpg      ← 纯图片，无子目录
    └── ...
```

这样 `translated/` 只要落在本地库根内（或显式注册），成品就能作为**普通本地漫画**被阅读器直接打开，零特判。S11 做成品导出时值得优先考虑这个布局（CBZ/PDF 单文件同理——R3 会忽略非图片文件，不会误伤）。

## 2. 风险二：headless 命令全线卡死

### 2.1 现象与证据（用刚构建的产物实机复现）

```
$ ./venera.exe --headless bogus
[headless] init: App/data/translation
[headless] init: done
[headless] init: cookie jar
[headless] init: components        ← 停在这里，永不前进（70s 超时，EXIT=124）
```

`init()` 与 cookie jar 都过了；**卡点在 `App.initComponents()`**。此前 `project-check` 之所以一直正常，是因为它被特意安排在 `init()` **之前**执行，根本不走这条链。

### 2.2 根因：一个永远不会被完成的 Completer（确定性死锁，非环境问题）

三条互相咬合的链：

```
headless.dart        await App.initComponents();
                            │
app.dart:113-138     Future.wait([ … local.init() … ])
                            │
local.dart:428       await ComicSourceManager().ensureInit();   ← 等
                            │
utils/init.dart:12-19  ensureInit() 只是挂在一个 Completer 上，
                       只有 Init.init() → _markInit() 才会完成它
                            │
comic_source.dart:222  doInit() 里 await JsEngine().ensureInit();  ← 又等一层
                            │
js_engine.dart:88      doInit()（FlutterQjs 启动）
```

**而 `ComicSourceManager().init()` 与 `JsEngine().init()` 只在 `initDeferred()`（`init.dart:80-88`）里被调用——headless 从不执行 `initDeferred()`。**

于是：`local.init()` 等的 Completer **没有任何人会去完成它** → `App.initComponents()` 的 `Future.wait` 永不 resolve → **永久挂起**。

> 这不是"环境缺东西"或"网络慢"，而是**调用顺序假设失效导致的结构性死锁**：headless 沿用了"`initComponents()` 自给自足"的旧假设，而 `LocalManager.init()` 后来新增了 `await ComicSourceManager().ensureInit()`，使该假设不再成立。

### 2.3 为什么 GUI 不受影响

`initDeferred()` 把三者放在**同一个 `Future.wait` 里并发启动**：

```dart
var futures = [
  App.initComponents().wait(),
  JsEngine().init().wait(),              // ← 完成 JsEngine 的 Completer
  ComicSourceManager().init().wait(),    // ← 完成 ComicSourceManager 的 Completer
  …
];
await Future.wait(futures);
```

并发 → 互相的 `ensureInit()` 都能被满足 → 不卡。**只有 headless 因为跳过了 `initDeferred()`，把"并发"退化成了"串行等一个没人完成的 future"**。

### 2.4 隐患清单（这就是"已定位未修复"的风险）

| 隐患 | 严重度 | 说明 |
| --- | --- | --- |
| **验证通道只剩一条** | 🔴 高 | S6 起，`headless` 是我们验证"新代码真的编译进产物并能跑"的唯一手段。`project-check` 可用是**巧合**（它恰好排在 init 之前）。任何**新增的、排在 init 之后的** headless 命令都会静默挂死 |
| **用户/外部自动化静默阻塞** | 🟠 中 | `webdav up/down`、`updatescript all`、`updatesubscribe` 这些命令全走 init 之后 → 调用方会永久等待，且**无任何输出**（连错误都没有），极难排查 |
| **`main` 未 await 的连带** | 🟢 低（已修） | 之前 `runHeadlessMode` 是 fire-and-forget，`main` 直接返回，行为更加不可预期；S6 已改为 await |
| **掩盖后续回归** | 🟠 中 | 若 S7/S8 再往 `initComponents()` 链上加一个"只在 initDeferred 里启动"的组件，会再次静默死锁，且症状与本次完全一样（无输出），新人极难定位 |

### 2.5 修复方案（已落地）

**① 把"必须并发启动的三件套"收敛成一个共享入口**（`init.dart`）：

```dart
/// Stores that only resolve when started together.
/// LocalManager.init() awaits ComicSourceManager().ensureInit(), and
/// ComicSourceManager.doInit() awaits JsEngine().ensureInit(). Started
/// one-by-one they deadlock — this is the single place that starts them
/// concurrently.
Future<void> initInterdependentStores() {
  return Future.wait([
    App.initComponents().wait(),
    JsEngine().init().wait(),
    ComicSourceManager().init().wait(),
  ]);
}
```

- `initDeferred()` 改为调用它（GUI 行为等价，只是三个 future 换了个容器）；
- **headless 也调用它** → 死锁消失；
- **以后只有一个地方定义这条链**，不会再漂移。

**② headless 侧加超时护栏**（把"静默无限挂起"变成"限时报错 + 记日志"）：

```dart
try {
  await initInterdependentStores().timeout(const Duration(seconds: 120));
  _headlessTrace('init: components done');
} catch (e, s) {
  _headlessTrace('init: components failed: $e');
  Log.error('headless', 'App store init failed: $e\n$s');
}
```

这样即便未来顺序再次被改坏，症状会是"120s 后打印失败原因"而不是"什么都没有"。

### 2.7 关于"是否需要当场处理"的判断

**需要，且值得当场处理。** 理由：

1. **根因确定**（不是"偶发/环境"），修复是**顺序问题**，改动面极小、语义等价；
2. **它是我们的验证生命线**——留到 S7 之后再修，等于在"看不见新代码是否真的跑起来"的状态下开发一个新界面；
3. **隐患是"静默"型的**：不影响 GUI、不影响日常使用，只在需要它的时候（验证/自动化）以"无输出挂死"的形式爆发，越晚发现越贵；
4. 顺带把"并发启动"收敛为单一入口，**杜绝同类死锁复发**。
