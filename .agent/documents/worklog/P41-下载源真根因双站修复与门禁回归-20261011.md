## 1. 包子漫画：AMP/SSR DOM 改版（主战场）

### 1.1 真根因（运行时埋点实锤，非网络）

章节页现网 HTML 结构（四镜像一致，旧 URL 302 到带后缀新 URL，curl 需 `-L`）：

```html
<div class="comic-contain">
  <div data-v-xxxxxxxx>                                   <!-- 新增的包裹层 -->
    <amp-img id="chapter-img-1-1"
             class="comic-contain__item"
             data-src="https://s2.bzcdn.net/....jpg">     <!-- 真图在 data-src -->
  </div>
  ...
</div>
```

- 旧选择器 `.comic-contain > .chapter-img`：**直接子** + 把 `chapter-img` 当 class ⇒ 改版后**双重不匹配，0 命中**。
- 埋点（`logs.txt` 中 `[P41DBG]`，**取证后已全部移除**）实锤：
  `bodyLen≈134k hasContain=true hasChapterImg=true hasDataSrc=true`，但解析图片数 = 0；
  同一 URL `curl.exe -L` 取回 50 张 `data-src` 图片。
- 链路：0 图 → 四镜像（`cn.webmota.com / cn.kukuc.co / cn.twmanga.com / cn.dinnerku.com`）依次抛
  `DomainBlock: empty chapter images` → 全部被判"坏域名" → 兜底 `appcn.baozimh.com` → 该 App 域确有 Cloudflare → 用户看到的"每章验证/下载卡死"。
- **四镜像本机直连与走代理均 HTTP 200、无挑战**。所以 P39 修的域名问题确实存在但不是主因；P35/P39 后用户复测仍失败，缺的就是这一处 DOM 适配。

### 1.2 修复（baozi.js v1.2.3）

`loadEp::parseImages`（约 690–715 行）：

- 选择器：`.comic-contain > .chapter-img` → **`.comic-contain .comic-contain__item`**（后代选择，容忍包裹层变化）；
- 取图：**`attrs["data-src"] || attrs["src"]`**（AMP 的 `amp-img` 懒加载真址在 `data-src`）；
- `version = "1.2.3"`，头部加 P41 变更注释。

部署版与仓库版已同步，SHA256 一致：
`40B2EF984E80AA4B8D3FE0FAF763D8010076741D85571F9C904F659EA745AEA1`
（部署版 = `%APPDATA%\io.github.maelshiyan02\mangrove\comic_source\baozi.js`；仓库版 = `venera-configs-main/baozi.js`）。

### 1.3 验证（正反向闭环，反向不是装饰品）

- `node --check`（node 22.22.2）exit 0。
- **正向**：`download-check miemenjiazudezhongshengzhe-yangpyungpainkillersaintnine --source baozi --chapter 0 --timeout 120 --clean`
  → 末条 `[CLI PRINT] verdict=success`；`download_check.json`：`passed:true, total:50, downloaded:49, missing:0`。
  49/50 是墙钟窗口结束时 1 张仍在重试（**非缺页**）；50 张图片列表全部经 **webmota** 解析，**零 appcn 请求**（误兜底路径消失即旁证）。
- **反向**：把选择器临时注为 `.comic-contain .p41-injected-fault` 重跑 →
  `passed:false, timedOut:true, total:0`（FAIL，与线上故障同构）⇒ 该检查确实能抓住本故障。注入已还原，`git diff` 无 `p41-injected-fault`/`[P41DBG]` 残留。

### 1.4 重要运维事实

- 源文件**仅在 App 启动 `doInit()` 时扫描加载**（`comic_source.dart:241`），无文件 watch
  ⇒ **用户必须完全退出并重启 App** 才会加载 v1.2.3；在已运行的 App 里重试下载仍是旧解析器。
- 源的更新 URL 指向上游 jsdelivr（`venera-app/venera-configs`）。v1.2.3 版本号高于上游当前版本时不会提示降级；
  但**上游若先发布更新版本且仍含旧选择器，用户手动"更新源"会覆盖本次修复** ⇒ GUI 验收通过前勿对包子源点"检查更新"。

## 2. comix.to：出口 IP 封禁名单随时间变（P39 结论翻转）

### 2.1 全节点实测（19:03，34 个 SS 节点逐个 curl）

- **31 个 200**：香港 / 日本 / 新加坡 / 英国 / 加拿大 / 澳大利亚 / 法国 / 俄罗斯 / 土耳其 各节点；
- 403：美国 Y01、美国 Y02、印度；000（连不通）：韩国 000；
- **南京家宽直连 `58.209.131.5` → 同样 403**。

⇒ P39「curl 直连 200、代理 403 ⇒ 全域强制 DIRECT」的结论**在当时成立但不可钉死**：
封禁令按出口 IP 维护、随时间变（会话初期 orig = 美国 Y01，19:44 再看 Clash 当前已是英国 Y01）。
钉死任一方向（强制代理 / 强制直连）都会在名单变化后失效。**TUN 假设排除**：节点对照证明应用层代理切换真实生效。

### 2.2 修复：跟随用户代理 + 封禁页可操作提示

- `proxy.dart`：`kDirectProxyHostSuffixes = <String>[]`（**撤回 comix 全域强制直连**；
  白名单/`isDirectProxyHost`/`buildProxyBypassList` 机制保留，注释写清 P39→P41 的翻转原因）；
- `app_dio_io.dart`：`findProxy` 上方注释同步（dio 因此恢复"跟随用户代理"）；
- `comix_client.dart`：
  - `fetchPageHtml`（约 99–131 行）保留最近 HTML（`lastHtml`），命中硬封禁页时抛
    **`COMIX_IP_BLOCKED`** 带页面标题的异常，不再把封禁页误当"正常但缺 initial-data"；
  - `_getSharedWebViewEnvironment`（约 2271–2294 行）：bypass 列表为空时只传 `<local>`，
    **不再把 comix 域塞进 bypass** ⇒ WebView 与用户代理一致；
- `assets/comix_to.js`（约 242–297 行）：新增 `blockedHint` **中英双语**提示
  （请切换香港/日本/新加坡等节点；美国/印度节点当前被封；或稍后重试）；
  webview catch 识别 `COMIX_IP_BLOCKED`；dio 通道 200 但 body 含
  `attention required|blocked_why_headline|cf-error-details` 时同样引导，而非误报解析失败。

## 7. 本轮环境坑（供后续会话）

- Clash API 在 **8993**（非 9090）无 secret；切节点用 **PUT**（PATCH→405）；
  组名 `🔰 选择节点` 需 `[uri]::EscapeDataString`；body 用 `ConvertTo-Json -Compress` + UTF8 字节；切换后 sleep ~1s。
- curl 对照用 `curl.exe`，显式 `--noproxy '*'`；HTML 落盘后用 `[IO.File]::ReadAllText` 分析长度（PS 变量 `.Length` 对多行文本给行数）。
- `edit-check` 必须带工程参数：`edit-check "ComicLibrary/projects/My Dragon Girlfriend Has Returned-1 [Asura Scans]/imgtrans_My Dragon Girlfriend Has Returned-1 [Asura Scans].json"`。
