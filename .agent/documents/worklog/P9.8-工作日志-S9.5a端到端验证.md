## 一、为什么要造这个工装

`P9.6 §六 #8` 记着一条："`--headless` 无法跑管线（真实检测需要 ONNX 模型 + 原图）"。
本轮实测后，这条归因**是错的**（见 §三）：模型 6 个组件全部就位、原图也在，真正
缺的是**渲染表面**。但当时没人跑，所以没人知道；这条限制就以"模型问题"的形态
留在了文档里。

工装本身的设计约束只有一条：**必须复用工作室的每一条真实路径**。只要有一环"另写
一套"，它验的就不是工作室，而是工装自己。所以：

| 环节 | 复用的东西 |
|---|---|
| 语向配置 | `TranslationConfig.of(comicId, null)` |
| 页面解析 | `original → inpainted → mask`（同 `studio_page._resolvePageFile`） |
| 页宽 | `project.imageInfo[key]`（同 `studio_page._pageSizeInPixels`） |
| 单页管线 | `StudioPagePipeline().runPage(...)` |
| 去重 | `overlapsExistingBlock(page, rect)` |
| 落地 | `captureBlockListEdit` + `EditHistory.push`（**硬规矩 3** 的唯一入口） |
| 保存 | `ProjectWriter.save(root: project.workspace, keepBackup: true)` |
| 出图 | `ProjectWriter.writeArtifacts` + `renderInpaintedPage` + `renderProjectResultPage` |

用法：

```
venera.exe --headless pipeline-check <comicId|project.json>
    [--chapter <目录>] [--limit N] [--no-translate] [--repeat N] [--json out]
```

`--repeat N` 是验收里「**内容哈希与重跑一致（幂等）**」那一条的可执行形式：跑 N 轮、
从盘上重读工程、逐页比对 `result/` 的 sha256 前缀。刻意**不使用** `artifactReport`
的内存结果 —— 那就没验证到落盘的那一字节。

## 二、发现 1 🔴 `inpainted/` 无人生产 —— 出图腿从未工作

### 2.1 证据（不是推断，是应用日志）

```
info Translation Studio 2026-10-07 20:45:06.549264
result/ regenerated: artifacts written=0 skipped=1 failed=0 (dirty=1)
```

`dirty=1` 说明确实有一页被编辑过、也确实触发了重渲；`written=0 skipped=1` 说明
`renderProjectResultPage` **返回了 null**。而它返回 null 的第一条分支就是：

```dart
final inpainted = project.inpaintedPath(pageKey);
if (inpainted == null) return null;   // ← 走到这里，被 writeArtifacts 记成 skipped
```

### 2.2 账是怎么欠下的

| 时点 | 文档说了什么 | 代码做了什么 |
|---|---|---|
| P6 §2.8（**用户原话**） | "都在各自的漫画文件目录地址下生成 `inpainted`、`mask`、`result`、相关 json 文件" → `mask/` + `inpainted/` **保存时同步**产出 | —— |
| P8.1 §82 | "`mask/`、`inpainted/` 是本工程的**输入**，保存不改动它们（**去字/检测属 S9**）" | 保存只写 json + `result/` |
| S9 交付清单 | "渲染增强：字体资产 + `letter_spacing` + 描边宽度" | 没有"去字底图"这一项 |

三处合起来的结果：**去字被推迟给 S9，S9 的清单里没有它，于是没有任何代码生产
`inpainted/`**。而 `result/` 的第一个前提就是它 —— 出图腿从落地那天起就没工作过。

**这类"欠账在三份文档之间掉下去"的形态值得记一笔**：每一份文档单看都没错，错在
交接处。

### 2.3 修法

新增 `renderInpaintedPage(project, pageKey)`（`result_renderer.dart`）：

```
原图 → _decodeBounded → 按页 regions 的 eraseRects 擦除 → 编码 PNG
```

然后 `studio_page._regenerateResults` 改成**两阶段**：

```dart
// ① 先写底图（同步等待）
await ProjectWriter.writeArtifacts(kinds: {inpainted}, source: renderInpaintedPage);
// ② 再渲染成品 —— 它以 ① 的产物为输入位图
await ProjectWriter.writeArtifacts(kinds: {result}, source: renderProjectResultPage);
```

🔴 **顺序不可交换**：`writeArtifacts` 内部是并发 worker，把两个 kind 放进同一次
调用，`result` 会读到还没写出来的底图 —— 而且**在小数据量下会侥幸成功**，是那种
"跑得过一次、换台机器就坏"的写法。

两个刻意的设计选择：

- **底图只从原图取**，不对已有的 `inpainted/` 再擦一遍。对一份已经是去字结果的位图
  再擦，只会把背景越擦越糊，而且**每保存一次更糊一点**。
- **只在不需要降采样时产出**。`result/` 侧的坐标换算是
  `decoded.image.width / decoded.originalWidth`；当输入是 `inpainted/` 时这两个值
  是**同一个文件的宽**，于是 `scale == 1.0`，页面 regions 被当作源坐标直接使用。
  一旦写出一个被 `_decodeBounded` 缩过的底图，那个 `scale == 1.0` 就变成谎言：
  **框按源坐标落在缩小的图上，位置全错而不报错**。所以大页（> 12 MP 或 > 8000 px）
  宁可**不产出** `inpainted/`（`result/` 会如实记成 skipped），也不造一个破坏
  坐标契约的文件。

`eraseRects` 在工程模型里就是块的 `xyxy`（`TextBlock` 不存字形级矩形，FT 也没有
这个概念），但 `TextInpainter.erase` 内部的 Otsu + 笔画判定 + 膨胀只把传入矩形当
**搜索窗口**，真正被抹掉的像素由窗口内的笔画决定 —— 所以用外框是安全的。

## 三、发现 2 🔴 headless 无法解码/渲染图像

### 3.1 症状

```
ERR: SwapChain11.cpp:640 Could not create additional swap chains or offscreen
     surfaces, HRESULT: 0x887A0022
[ERROR:flutter/shell/platform/windows/egl/egl.cc(57)] EGL Error: Context Lost (12302)
     Surface creation failed.
[ERROR:flutter/impeller/renderer/backend/gles/description_gles.cc(92)]
     Impeller validation: Could not determine GL version.
[ERROR:flutter/shell/common/platform_view.cc(81)] Failed to create platform view
     rendering surface
...
page 0/1.webp failed: Exception: No Impeller context is available
```

94 页**全部**同一句错误，`elapsed 0.062s` —— 第一行就挂了，根本没走到检测。

### 3.2 为什么以前没人发现

**因为现有 headless 命令里没有任何一条会解码图片**：

| 命令 | 碰图像像素吗 |
|---|---|
| `project-check` / `edit-check` / `project-validator` | ❌ 只碰 JSON 与命令模型 |
| `export-check` | ❌ 只**规划**产物路径（文档原文 "Nothing is written"） |
| `studio-scan` / `page-reconcile` | ❌ 只 `existsSync` + 数页 |
| `download-check` / `comix-spike` | ❌ 只搬字节，不解码 |
| `pipeline-check`（本轮新增） | ✅ **第一条会解码的命令** |

所以这条限制一直在，只是被 `P9.6 §六 #8` 那句"需要 ONNX 模型 + 原图"挡在了后面 ——
那句是**推断**，不是观测。

### 3.3 试过什么，为什么都不行

| 尝试 | 结果 |
|---|---|
| 环境变量 `FLUTTER_ENGINE_SWITCHES=1` + `enable-software-rendering` | ❌ 输出**逐字节相同**，Impeller 仍介入 |
| 再加 `enable-impeller=false`（关 Impeller 走 Skia） | ❌ 同上 |
| 直接在本会话启动 `venera.exe`（绕过计划任务） | ❌ 进程秒退、stdout/stderr 皆空、json 未生成 —— 说明**窗口都没建起来**（`main.cpp` 的 `window.Create()` 失败即 `EXIT_FAILURE`） |

引擎开关机制本身**是存在的**（`flutter_windows.dll` 里 `FLUTTER_ENGINE_SWITCHES` /
`FLUTTER_ENGINE_SWITCH_` / `enable-impeller` / `enable-software-rendering` 四个
字符串都能 grep 到），所以问题不在"开关名写错"，而在**这个会话根本没有可用的
DXGI/GL 会话**（`0x887A0022` = `DXGI_ERROR_NOT_CURRENTLY_AVAILABLE`）。

> **结论**：`dart:ui` 的图像解码与 `Picture.toImage` 都需要渲染 context。
> WorkBuddy 运行命令的会话里没有（用户自己的 GUI 会话里**有** —— 20:45 那次
> 保存就是证据）。**所以 S9.5-a 的验收跑只能在 GUI 里做。**

### 3.4 顺带修正一条文档

`P9.6 §六 #8` 的归因"真实检测需要 ONNX 模型 + 原图"**是错的**。实测：
`text_detector` + `ocr_ja/zh/en/ko` 六个组件**全部已装**（`%APPDATA%/.../translation_models/`，
含 `vocab.txt` / `dict.txt` 附属文件），原图也在。真正的限制是渲染表面。

## 四、发现 3 🟠 没有"从下载创建工程"的入口

1–7 话齐全）。实测：`projects/` 下**只有** `Error the Echo`（原图已删）与 `S9Fixture`
（5 页）。要给真正的整章建工程，需要"从 `downloads/` 创建一个工程"这一步 —— 而：

- `BtProjectManager` 只有 `ensureProject` / `scan`，**没有 create**；
- `ProjectWriter.adopt` 存在，但调用方**只有** `project_validator.dart`（headless 校验）。

所以整章载体只能离线生成。补了 `tools/_make_chapter_carrier.py`：

```

```

- **原图不复制**：走 A 方案 —— `directory` 指向 `downloads/My Dragon Girlfriend Has Returned`，
  产物落 `projects/MDGH-ch1`（json 父目录即 `workspace` 的回落值）。
  复制 94×852KB 既慢又没意义。
- **json 只写实测到的字段**：`image_info` 只有 `width`/`height`（自解析 WebP 头，
  不依赖 PIL），**不编造** FT 的 `finish_code` / `translation_target`。
- **不写 `workspace` 键**：`TranslationProject.workspace` 会回落到 json 父目录，

## 五、工装的一次实测输出

`--headless pipeline-check bt_c3d2c83c`（整章 94 页）：

```
passed  : False   elapsed: 0.062 s
findings:
  * 94/94 page(s) failed detect/OCR — first error: Exception: No Impeller context is available
  * result/ is EMPTY — the 出图 leg produced nothing. inpainted written=0 skipped=94;
    per-page reasons: {"upstream failed: Exception: No Impeller context is available": 94}
```

### 5.1 🔴 报告的两条纪律（这一轮各踩了一次）

**① 顺序即诊断：上游先于下游报。**
第一版把 `result/ is EMPTY` 排在 `N pages failed` **之前**，阅读者第一眼会去找
渲染器的问题，而真正的断点在更上游。改后：`failedPages` → `imageInfoMissing` →
`result/ is EMPTY`。

**② 缺失原因必须报到根因那一层。**
第一版 `_absentReason` 按"页键缺失 → 无译文 → 无底图 → 渲染器返回 null"取**第一个
成立**的，于是 94 页全部报成 `no translated region` —— 字面没错（确实没有 region），
但它把 `No Impeller context is available` 藏到了第二层。**读起来像"这些页本来就没
文字"**。这和 `P9.6 §6.4` 那条"夹具必须落在正确值与故障值之间"是同一类病：
**观测量的选择决定了断言能否分辨对错**，而报告的措辞决定了人能否分辨根因。
现在第一支就是 `if (pageError != null) return 'upstream failed: ...'`。

**③ 同时也保留了一个真实的正面观测**：`imageInfoMissing: false`、
`base: "original"`、`save.artifactDirs: [mask, inpainted, result]`、`jsonBytes: 13737`
—— 说明**页面解析、`image_info`、保存契约这三段在 94 页规模上是好的**，
只是卡在第一行。

| 弯路 | 教训 |

## 八、🔴 需要用户人工验证的项（**S9.5-a 的验收跑**）

前提：**必须在你自己登录的桌面会话里打开 VeneraX 的 GUI**（WorkBuddy 运行命令的
会话没有渲染表面）。

### 8.1 主验收：整章 94 页

1. 打开 **翻译工作室**（主页 → `Translation Studio`），选 **`MDGH-ch1`** 卡片。
2. 画布上应出现第 1 页（原图，含英文对白）。
3. 点 **整章运行**（`Run chapter`）；语言若不对，先在阅读器里设成 日/英 → 简体中文。
   > 当前全局设置：`imageTranslationSource = auto`，`target = zh`，
   > 翻译走**免 Key 的公共 provider**（`谷歌翻译（免 Key）`）→ 不需要 API key。
4. 跑完看状态栏与 `logs.txt` 里的这一行（**本轮新增**）：

   ```
   info Studio Pipeline <时间>
   {"pages":94,"done":94,"blocks":N,"skipped":M,"failures":F,"stopped":false,
    "resumeFrom":null,"translate":true,"skipExisting":true,"rightToLeft":true}
   ```

   - **`failures` 必须为 0**；`blocks` 记下来（这就是"块数与 FT 对比"的那个数）。
   - `skipped`（`M`）是**漏检/误检的第一手线索** —— 它就是 `P9.6 §六 #3` 要校准的
     那个量：`M` 大说明检测器噪声大，不是聚类的问题。
   - 紧接着应有 `artifacts regenerated: inpainted=… result=…`。
5. 检查磁盘：

   ```
   ComicLibrary/projects/MDGH-ch1/inpainted/1 [Asura Scans]/  ← 应为 94 张 .png
   ComicLibrary/projects/MDGH-ch1/result/1 [Asura Scans]/     ← 应为 94 张 .png
   ```

   **`inpainted` 有 94 张**是 §2.3 那次回填生效的直接证据（此前恒为 0 张）。

### 8.2 抽样质量（`P9.6 §八` 的 6~10 条，现在才有数据可看）
