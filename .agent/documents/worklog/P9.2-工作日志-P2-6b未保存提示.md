## 一、🔴 本轮最重要的发现：`PopScope` 在本应用里拦不住任何一条真实离开路径

P9.0 盘点时把「未保存提示」记为「`isDirty` 与 `PopScope` 都已就绪，成本最小」。**动手前读 Flutter 源码后发现这句话是错的**，`PopScope` 在这个应用里只能覆盖一半路径，而且是**用户最不需要保护的那一半**。

### 1.1 `PopScope` 的机制

`_PopScopeState implements PopEntry`，`canPop` 只写进一个 `ValueNotifier`：

```dart
// pop_scope.dart
@override
void didUpdateWidget(PopScope<T> oldWidget) {
  canPopNotifier.value = widget.canPop;
}
```

这个 notifier 只被 `ModalRoute.popDisposition` 读取：

```dart
// routes.dart:2034
RoutePopDisposition get popDisposition {
  for (final PopEntry<Object?> popEntry in _popEntries) {
    if (!popEntry.canPopNotifier.value) return RoutePopDisposition.doNotPop;
  }
  return super.popDisposition;
}
```

而 `popDisposition` 只被 **`maybePop`** 查询（`NavigatorState.maybePop` → `route.popDisposition`）。

### 1.2 命令式 pop 完全绕过它

```dart
// navigator.dart:5642  NavigatorState.pop
final _RouteEntry entry = _history.lastWhere(_RouteEntry.isPresentPredicate);
...
entry.pop<T>(result, imperativeRemoval: true);   // ← 直接置 pop

// navigator.dart:3420  _RouteEntry.pop
void pop<T>(T? result, {required bool imperativeRemoval}) {
  pendingResult = result;
  currentState = _RouteLifecycle.pop;   // ← 没有 popDisposition 检查
  this.imperativeRemoval = imperativeRemoval;
}
```

`pop()` / `popUntil()` 这条路径**根本不读 `popDisposition`**。同样，窗口关闭直接 `exit(0)`，连 Navigator 都不参与。

### 1.3 本应用的全部离开路径

| 路径 | 机制 | `PopScope` 拦得住？ |
|---|---|---|
| 系统返回键 / AppBar 返回 | `Navigator.maybePop` | ✅ |
| iOS 边缘侧滑 | `maybePop` | ✅ |
| **侧栏切页** | `NaviPaneState.updatePage` → `popUntil(isFirst)` | ❌ |
| **标题栏 X 按钮** | `WindowFrameController.addCloseListener` → `exit(0)` | ❌ |
| **Alt+F4 / 任务栏关闭** | `windowManager.onWindowClose` | ❌ |

> 🔴 **如果按 P9.0 的原计划只加 `PopScope`，会得到一个"看着做了、实际三条漏两条"的未保存提示** —— 而侧栏切页恰恰是用户离开工作室最常用的方式。这正是本仓库反复踩的那类静默半成品。

## 二、方案：统一守卫注册表 + 三处接入

### 2.1 `LeaveGuardRegistry`（新增 `lib/foundation/leave_guard.dart`）

```dart
typedef LeaveGuard = Future<bool> Function();   // true = 可以走

class LeaveGuardRegistry {
  static bool get hasGuards;
  static void add(LeaveGuard guard);      // 同一 closure 重复 add 是 no-op
  static void remove(LeaveGuard guard);   // 未注册也安全
  static Future<bool> requestLeave();     // 逆序问；任一拒绝即拒绝
}
```

**为什么是全局注册表而不是把对话框塞进每个调用点**：离开路径有 3 条、且还会增加（S10 跨页编辑、S11 术语记忆）。注册表的语义是「**有编辑器在 Screen 上，它有话要说**」——新增编辑器时注册一个 guard，而不是去改 5 个调用点。这与窗口关闭监听链已有的 LIFO 约定一致（`_WindowFrameState._onClose` 就是 `closeListeners.reversed`）。

两条硬规则：
- **守卫抛异常＝拒绝离开**。对话框构建失败就丢改动，比多点一次按钮糟糕得多。
- **重复 `add` 幂等**。`initState` 因某种重建重跑，栈不能涨，否则用户会被问两次。

### 2.2 工作室侧

```dart
// initState
_guardRegistered = true;
LeaveGuardRegistry.add(_leaveGuard);

// dispose
if (_guardRegistered) LeaveGuardRegistry.remove(_leaveGuard);
```

```dart
Future<bool> _leaveGuard() =>
    _leaveCheckInFlight ??= _resolveLeave().whenComplete(() => _leaveCheckInFlight = null);
```

- **重入合并**：同帧内 Back + 标题栏关闭可能连着触发两次；第二次 await 同一个 future，而不是把第二个对话框叠在第一个上。
- **`_save()` 改为返回 `Future<bool>`**：原实现 `catch` 后只弹提示、不告诉调用方成功与否。「保存并离开」必须知道写盘是否成功，否则用户点了「保存并离开」、写盘失败、页面照样关掉——**提示说已保存、实际改动只在内存里**。这是比不提示更糟的失败模式。
- **`canPop: !dirty` + 批准后走 `Navigator.pop()`**：既然命令式 pop 不查 `canPop`，批准后就不需要"再放行一次"的标志位。实现期我一度加了 `_leaveApproved`，读源码确认多余后**删掉了**（少一个状态字段，少一类"标志位没被复位"的 bug）。
- **批准后再查一次 `_history.isDirty`**：守卫返回 `true` 不等于工程干净（写盘失败时 `isDirty` 仍为 true）。不查就是"用户点了保存→写盘失败→照样离开"。

### 2.3 三处接入点

| 文件 | 改动 |
|---|---|
| `studio_page.dart` | 包一层 `PopScope(canPop: !dirty)`；`_attemptLeave()` 重新发起 pop |
| `navigation_bar.dart` | `updatePage` 改 `async`，`popUntil` 前 `await LeaveGuardRegistry.requestLeave()` |
| `window_frame.dart` | `_onClose()` 在 `exit(0)` 前插入 `_closeAfterGuards()` |
| `message.dart` | 新增 `showUnsavedChangesDialog` + `UnsavedChangesChoice` 枚举 |

`updatePage` 的签名从 `void` 变 `Future<void>`（无外部调用者，`explore_page.dart` 只用 `addNaviItemTapListener`）。

### 2.4 对话框：`canPop: false` + 三选项

```dart
enum UnsavedChangesChoice { cancel, discard, saveAndLeave }
```

「取消 / 放弃修改 / 保存并离开」。两点不是默认值：

- **`barrierDismissible: false` + 对话框内 `PopScope(canPop: false)`**：误触遮罩或按返回**不得**等于"放弃"。
- **`showDialog` 返回 `null`（被 dismiss）一律当 `cancel`**：用户没说 yes，就不能当 yes。

| 场景 | 结果 |

| 工程干净时按 Back | 直接离开，无对话框 |

### 🔴 未覆盖（**已知缺口，不是遗漏**）

1. **Alt+F4 / 任务栏关闭，且「最小化到托盘」关闭** → 进程被窗口管理器直接销毁，**完全不经过 Dart**，任何 close listener 都跑不到。
   - 根因：`tray.dart:63` 在托盘关闭时 `setPreventClose(false)`，等于把关闭权交还给原生。
   - 要堵需要把 `setPreventClose` 改成常开、再把原生关闭全部路由进守卫链 —— 这是改**整个应用的退出语义**，而现在全应用只有工作室一个编辑器，收益不抵风险。
   - **归属**：留到 S10/S11（届时跨页编辑让编辑器数量从 1 变多个，这条才值得动）。
2. **托盘菜单里的「退出」** → `tray.dart` 里 `exit(0)`，同上。
3. **`pop_up_widget` 的 `App.pop()`** → 命令式 pop，但该组件不与工作室共存，本轮不动。

### 5.1 为什么断言打的是注册表而不是对话框

`PopScope` 与对话框都需要活的 Navigator，headless 里没有。所以断言落在**承载全部安全论证的纯 Dart 部分**——「一个拒绝就否决整个离开」与「抛异常的守卫不得放行离开」。这两条如果错了，`_resolveLeave` 写得再对也没用。

| 断言 | 验证的规则 |
|---|---|
| `guard.empty_allows` | 守卫栈空时 `hasGuards` 为 false（窗口关闭不会被无谓地拦） |
| `guard.empty_request_is_true` | 空栈询问恒放行 |
| `guard.no_duplicate_ask` | 重复 `add` 同一 closure 只问一次 |
| `guard.deny_vetoes` | 一个 `false` 否决整个离开 |
| `guard.lifo_order` | 后注册的先问（与 closeListeners 同约定） |
| `guard.short_circuits` | 拒绝后**不再问**下面的守卫（后来的 yes 不能复活已被否决的离开） |
| `guard.remove_is_scoped` | 移除拒绝者后放行 |
| `guard.removed_clean` | 栈回到空 |
| `guard.throw_vetoes` | 守卫抛异常 ⇒ 拒绝 |
| `guard.final_clean` | 不污染后续检查 |

> `guard.short_circuits` 用的是判别性设计：先注册 allow 再 deny，若实现是"问完全部再合并"，`asked` 会是 `[deny, allow]`，该项必挂。

### 5.2 一处误判的修正

首次核对产物时发现 `VeneraX/build/windows/.../app.so` 与 `builds/venera/data/app.so` **不一致**（9/30 vs 12/22）。一度以为是陈旧安装，查证后确认：构建输出目录已迁移到 `builds/`，`VeneraX/build/` 下那个是 9/30 的历史残留，**新产物一直在 `builds/venera/data/app.so`**（含全部 6 个新串）。**不是安装失败**，但"源=产物"这条一致性断言从此不能再指向 `VeneraX/build/`。

## 七、本轮经验（写给下一个开工的人）

1. 🔴 **`PopScope` 只能拦 `maybePop`**。任何用`pop()` / `popUntil()` / `exit()` 的离开路径都会绕过它。给编辑器加返回保护前，先把所有离开路径列出来，逐条确认机制——**默认假设"框架自带的保护覆盖全部路径"是错的**。
2. 🔴 **"保存并离开"必须让保存返回成功与否**。原来的 `_save()` 只弹提示不返回结果，接上守卫后这会变成"提示已保存、实际写盘失败、页面照样关掉"——**比没有提示更坏**，因为用户是被骗走的。
3. **守卫抛异常要当拒绝**。任何"出错就放行"的兜底，在丢数据的场景下都是反向的。
4. **对话框的"取消"路径要堵全**：遮罩点击、返回键、返回 `null` —— 三者都必须等价于"取消"。用户没点 yes 就不该丢改动。
5. **实现期自我修正**：`_leaveApproved` 标志位在读 Flutter 源码确认"命令式 pop 不查 `canPop`"后被判定为多余并删除。**一个状态字段少留，就少一类"忘记复位"的 bug**。
6. `VeneraX/build/` 下的产物已陈旧（9/30），**判断新代码是否进产物一律看 `builds/venera/data/app.so`**。
