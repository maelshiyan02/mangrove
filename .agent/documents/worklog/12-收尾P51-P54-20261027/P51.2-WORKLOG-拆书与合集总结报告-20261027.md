## 二、三个根因（都有取证，不是推测）

### 根因 1：目录名加语言前缀，直接摧毁了排序与 key

`chapterDirectoryName` 在 P49 里加了 `languageTag` 参数，落盘成 `[zh-Hans] 120 [baozimh]`。后果是连锁的：

- **本地漫画的章节 key 就是目录名**。排序器 `double.tryParse("[zh-Hans] 120 …")` 返回 `null` → 整本退化成**字典序**：`0, 1, 10, 100, 101 …`。
- 目录名同时是**源站 key**。改了它，下载断点、阅读进度、翻译工程归属（`mangrove_project.json` 指向的目录）全部对不上 → 用户看到的「拷贝漫画章节集体报错」。
- 语言信息**并没有因此变得可读**：它被埋在 600 多个目录名里，界面上没有任何一处去解析并显示它，于是「有前缀」和「分不清」同时成立 —— 用户说「两者起了冲突」，就是这个意思。

### 根因 2：话号解析把 UUID 读成了话号

`^(\d+)` 这类正则会把 `003b54f5-31b5-11f1-…` 的**首段 8 位十六进制数字**读成「第 003 话」，于是 63 话 UUID 章节被渲染成 `第003话 / 第28话 / 第2820话`。

更隐蔽的是排序判据：原先写的是「**至少有一个**能读出话号就按话号排序」。UUID 首段全为 0-9 的概率约 (10/16)^8 ≈ 2.3%，63 话里几乎必然出现一个 —— 于是整本 62 个普通章节被拖去和一个假话号比较，按字符串重排。这正是恢复数据后仍然乱序（`orderedHead [27, 33, 35, 40, 8, 22, 56, 21]`）的原因。

### 根因 3：覆盖表从 P11 起就没生效过（潜伏 40 个版本的老 bug）

`ComicOverrideStore` 里五处都写 `DomainDatabase()`，但 **`DomainDatabase` 不是单例** —— 每次 `new` 出来的是从未 `init` 过的对象，`.db` 恒抛 `StateError`。而 `_loadFromDb` 的 `catch` 只写一行日志就 `return {}`，写入路径同样静默吞掉。

净效果：**「读永远说没有覆盖、写永远静默失败」**。整条覆盖层（per-comic 显示模式、标题/简介/封面覆盖、三种章节标注）自上线起全是死的。日志里刷屏的 `Bad state: DomainDatabase is not initialized` 一直被当噪声。

顺带发现第二颗雷：`domain_database._openDatabase` 对**任何** open 失败都调 `_backupDatabaseFiles` —— 把**正在使用**的库 + 活的 WAL 改名搬走，等于静默丢库。

### 3.2 记录表 = 密码本（key 一个字节没动）

`comic_field_overrides` 现有三个**章节级**字段：

| 字段 | 语义 | 例 |
|---|---|---|
| `chapter_languages` | 语种 | `{"0": "zh-Hans", "153": "en"}` |
| `chapter_labels` | 展示标签 | 自定义章节名 |
| `chapter_numbers` | 展示话号 | `{"152": 153.0}` |

读取顺序固定为 **记录表 > 目录名 > key 本身**。这条顺序是整套方案的支点：目录名继续归源站所有（可随时被源站覆盖回来），所有"我们想让它多表达的信息"都活在记录表里。

## 五、遗留问题（诚实清单，不要当已解决）

### 🔴 5.1 第一次告白：界面显示 UUID 章节标签，而闸门报绿

**现象**：GUI 章节格子里是 `第44059405话` + 灰字 `-279f-11f1-9704-fa163e02432f`，其余是裸 UUID。

**已取证**：

- `local.db` 的 `chapters` 列结构是 `{ "<uuid>": [{"title": "第1话", "key": "<uuid>"}, …] }` —— **顶层键是 UUID、值是数组**，不是应有的 `{"默認": {"<uuid>": "第1话"}}`。
- `details_cache.db` 里 `copy_manga / dycgb` 那条**结构是对的**：`{"默認": {"<uuid>": "第1话", …}}`。
- 同一份 DB，`--headless chapter-order` 读出 `第1话 … 第63话`、`orderedHead 0..7`、0 违规。

**结论**：**闸门与界面不一致 = 疑似假绿**。闸门读到的和界面渲染的不是同一份东西，必须查清是哪一层在做"宽容解析"，否则这轮所有"PASS"都要打折。这是下一轮第 1 优先事项。

### 5.2 用户诉求 ④ 只完成了一半

覆盖表能写能读（`taggedLanguages` 从 0 变 152/5/8 为证），但**语言小字在 GUI 里是否真的显示出来，没有完成视觉验证**（截图读取额度在中途耗尽）。原计划验证的两处：合集 tab 标签（`简体中文 · 包子漫画` / `英文 · Asura Scans · comix.to`）、拆出来的英文记录在本地库的「语言」字段。

### 5.3 合集 tab 目前仍是「一节 tab 一个成员」

恰好等于用户要的按来源切语言。若还想要**网络模式下按源分组的章节列表**（不依赖合集），那是另一件事。

## 七、GUI 自证的坑（代价最大，已升格为规则）

### 7.1 沙盒里根本拉不起 GUI

`cmd start` / S4U 计划任务起的 exe **拿不到渲染表面**：日志停在 `SystemFonts` 之后，`EGL Context Lost` → 无窗口 → 十几秒自行退出。必须用 **`InteractiveToken`** 计划任务落到交互桌面 → `tools/launch_gui_task.py`。

### 7.2 `PrintWindow` 能截被遮挡窗口 ≠ 输入能到达（最阴的一条）

截图永远正常，但**真实鼠标事件走系统命中测试**：光标位置上最上层的窗口才是收件人。实测光标处 `WindowFromPoint` 返回 `Chrome_RenderWidgetHostHWND`，滚轮全滚给了 Chrome，Mangrove 一像素没动，而截图看起来"有内容" —— **典型的假动作**。

### 7.3 三条 API 级坑

1. pywin32 的 `EnumWindows` 回调**必须恒返回 `True`**；返回 `False` 会让它抛 `error(6,'EnumWindows','句柄无效')`，明明找到窗口却报错。
2. 必须 `SetProcessDpiAwarenessContext(-4)`；否则 2560 宽的窗口按 2048 算，差 1.25 倍，点 A 命中 B。
3. Flutter 窗口第一次真实点击常常只用于激活；`PostMessage` 版则**必须先发 `WM_MOUSEMOVE`**，否则 Flutter 认为鼠标不在窗口内，`WM_LBUTTONDOWN` 被丢弃。

### 7.4 🔴 用户明令（自本轮起为硬规则）

> 「本次操作前台频繁占用我的鼠标键盘，我需要你后台操作后台截图。这一点计入规则。」

**规则**：Agent 做 GUI 核验时**一律后台**——
- ✅ 截图：`PrintWindow(hwnd, dc, 2)`（被遮挡也能画）
- ✅ 交互：`PostMessage` 投递 `WM_MOUSEMOVE / WM_LBUTTONDOWN / WM_LBUTTONUP / WM_MOUSEWHEEL`
- ❌ 禁用：`SetCursorPos`、`mouse_event`、`SendInput`、`SetForegroundWindow`、`SetWindowPos(HWND_TOPMOST)`、任何键盘注入
- 实测（2.8.26+270）：滚轮与点击经 `PostMessage` **均生效**，光标不动、前台窗口不变。工具：`builds/ui_bg.py`
- 每次操作必须输出截图 md5 与 `CHANGED / SAME`，避免"看着像变了"的假验证。
