## 三、根因分析

单张失败图之所以要等满 30s，是**多层重试预算相乘**的结果：

```
单图最坏等待 ≈ webviewTimeout(30s) × wrapper内部重试 × images.netRetries × retryLimit重签
```

叠加另两个放大因素：

1. **5 张一批等满整批**：任一张被 403 挂起就撑满整批，整章停在 page0。
2. **误加的全局 `_imageSlots` 与 comix 全局 WebView 通道打架**：`_ComixImageWorker.laneCount = 3` 是全局共享的 3 条 WebView 通道，再叠一层全局槽位互相阻塞。

## 四、改动清单

### 1. 多轮渐进超时（`lib/network/download.dart`）

- 新增 `_roundTimeouts = [5, 10, 15, 30]`（秒），`_downloadChapterPool` 改为跑 4 轮。
- 第 1 轮 5s：把能快速下载的图**一次性全部下完**，单张超时即记失败、让出窗口。
- 每轮结束只对**仍缺失的页**用更宽松超时重新攻坚（10s → 15s → 30s）。
- **仅末轮（30s）**的失败页写入 `missing_pages.json`；中间轮只统计 host-block 提示、不落盘。
- `_imageRetryLimit` 由 1 改为 **0**——wrapper 内部不再递归重试，重试预算统一交给多轮。
- `_ImageDownloadWrapper` 构造函数新增 `timeoutSeconds` / `recordMissing` 两个参数；`_run()` 改为**单轮单次尝试**。

> **🔴 关键修复（自查发现）**：滚动窗口填充时**不能复用"已终态但未完成"的旧 wrapper**——那张图不会再次 `_run()`，失败页会被永远跳过，导致多轮机制失效。现改为：仅 `isComplete` 的页复用，其余（失败/超时）**每轮重建新 wrapper** 重新攻坚。

### 2. 单图超时透传（`lib/network/images.dart`）

- `loadComicImageUnwrapped` / `_loadComicImage` 新增 `downloadTimeoutSeconds` 参数，WebView 分支据此设置 `webviewTimeout`。
- 下载态 `netRetries` 由 1 改为 **0**（去掉乘数，避免 30s+ 陪跑）。
- 下载态 `retryLimit` 保持 **1**（仅保留一次重签，覆盖 comix.to 过期签名 URL）。

### 3. 并行默认改 1（`lib/foundation/appdata.dart`）

- 默认 `maxParallelDownloads` 由 3 改为 **1**。
- **移除** `doInit` 里的 1→3 自动升级迁移及 `implicitData.maxParallelDownloadsUpgraded` 标记。
- 设置页滑块保持 min1 / max3 不变——只有用户手动调高才并行。
- 同步修改已落盘的 `appdata.json`（3→1）与 `implicitData.json`（删除标记）。
- 队列调度 `_advanceQueue` 原生按序从上到下自动衔接，无需改动。

### 4. 章节排序改正序（`lib/foundation/comic_source/models.dart`）

- `_sortVersioned` 章节号排序由**降序改为升序**：`_compareChapterNumbersDesc` → `_compareChapterNumbersAsc`（ch1 → 最新）。
- 该顺序直接决定章节列表、阅读器翻页顺序、下载顺序。
- **组内版本仍按 `uploadedAt` 降序**（最新翻译组优先），满足"翻译组按最新排"。
- 同步对齐 `lib/network/comix_client.dart` 两处构建排序（API 路径与 DOM 路径）。
- 同步修改 `test/comic_state_repository_test.dart` 两处排序断言。

## 八、新增两个 headless 命令

### 8.1 `download-check`：走真实下载链路

```
venera.exe --headless download-check <comicId> \
  [--source comix_to] [--chapter <话号|key>] [--group <翻译组>] \
```

- 逐轮快照：观察第几轮、该轮超时预算、成功/缺页数、是否疑似主机封锁。
- `--group` 是关键：comix.to 每话有 11 个翻译组，不指定就取第一个（Asura，宿主正常、测不出封锁）。
- 新增 `ImagesDownloadTask.debugSnapshot()` 只读诊断快照（GUI 不用，纯为 headless）。

**实测结果（Asura 第 1 话，94 页已存在）**：

```

```

### 8.2 `comix-spike`：多策略取字节对照

```
venera.exe --headless comix-spike --comic <comicId> [--chapter N] [--sample N] \
  [--timeout 秒] [--json <out.json>]
# 或直接给 URL：venera.exe --headless comix-spike <imageUrl>
```

**必须用 `--comic` 取新鲜 URL**：轮换域图片是**单次签名、会过期**的 URL（日志里捞回来的老 URL 一律 404），拿旧 URL 测不出封锁效果——这是第一次实测踩到的坑。

5 条策略依次尝试：`navigation-landing`（导航落地判据）→ `img-natural-wxh`（位图是否解码）→ `canvas-read`（canvas 读已解码位图，零网络请求）→ `same-origin-fetch`（生产基线）→ `warmup-dynamic-img`（回主站拿 cf_clearance 后动态 `<img>` 加载）。

## 九、🔴 Spike 决定性结论：Diva 组 403 无法用「有头环境」绕过

**实测数据**（Diva 组第 6 话，5 条策略全灭）：

| 策略 | 结果 |
|---|---|
| `navigation-landing` | **`about:blank`** — 请求在 TLS/WAF 层就被拒，连 HTTP 都没到 |
| `img-natural-wxh` | `no-img`（落地空白页没有 `<img>`） |
| `canvas-read` | `no-img` |
| `same-origin-fetch` | 无字节 |
| `warmup-dynamic-img` | `img-onerror`（主站暖身 + 动态 `<img>` 仍失败） |

**对照组（正常宿主 `static.comix.to`）**：导航**正常落地**到真实 URL，只有 fetch 403。

### 9.1 为什么"有头环境"救不了（重要认知修正）

`HeadlessInAppWebView` 跑的**就是完整的 WebView2 浏览器进程**——flutter_inappwebview 只是不给它窗口（离屏），并没有向 Chromium 传 `--headless`。所以：

- **TLS 指纹、JA3、HTTP/2 帧序与有头 Chrome 完全一致**，服务端无从区分。
- 日志里的 `lane hard timeout, resetting: image timeout` + 导航落地 `about:blank`，说明连接在**握手/响应阶段就被丢弃**，不是"页面加载慢"或"缺 cf_clearance"。

结论：**这不是环境问题，是源侧按 IP/地区/ASN 级的定向封锁**。新开一个真正的有头窗口，握手结果不会变。

### 9.2 真正剩下的候选（都需站方放行，客户端无解）

1. 换出口 IP / 代理（最直接，值得让用户试）。
2. 站方放行或换 CDN 域名。
3. 走站方自己的"打包下载"接口（若有），而不是逐图取。

## 十、🔴 顺带修掉一个真实性能缺陷（headless 暴露）

首次跑 `download-check` 直接超时 >240s。根因：**每张图的 wrapper 启动都自己 `saveTo.listSync()` 扫一遍章节目录**——94 页的章节就是 94 次同步目录扫描，Windows 上把"整章秒完成"的续传拖成分钟级。

修复（`download.dart`）：

1. 新增 `_existingPageIndexes(dir)`：**每章扫一次**目录，缓存下标集合，wrapper 复用。
2. `_downloadChapterPool` 开头新增**续传短路**：整章页都已在磁盘上时直接收尾，不再为每页分配 wrapper 空跑。

效果：同一命令 **>240s 超时 → 3008ms 通过**。

顺带清理 analyze 报出的死代码：`_launched`、`_imageRetryLimit`、`_onImageFailed` 里未用的 `err`、`comix_client` 三处多余 `!`、`headless.dart` 未用的 `app.dart` import。

## 十一、🔴 意外收获：Diva 组其实能下大部分

跑 spike 期间发现，第 6 话 DivaScans 目录已积累到 **61 页**，日志里有：

```
info ImageLane1  fetched 344138 bytes
info ImageLane2  fetched 138536 bytes
```

**即 Diva 组并非全封锁**——同章内部分图片能取到字节，失败的是特定几张。这修正了此前"Diva 组系统性不可下"的判断（那是被 449 次 lane 超时 + 660 处 403 的噪声误导）。多轮渐进超时正好适配这种"多数能下、少数失败"的形态。

另外确认：本地已下的 7 章全是 **Asura Scans**（843 页、零缺页），每话另有 10 个翻译组可选。

## 十二、🔴 又一个 headless 阻塞：无窗口下的空指针

`download-check` 首次跑 Diva 组时静默中断，只在日志里留下一条：

```
[ERROR:flutter/runtime/dart_vm_initializer.cc(40)] Unhandled Exception: Null check operator used on a null value
#0  _App.rootContext (package:venera/foundation/app.dart:74)
#1  DataSync._.<anonymous closure> (package:venera/utils/data_sync.dart:58)
```

根因：`DataSync` 在 `init()` 里注册了一个 1 秒后的定时器，桌面端要挂"关窗前同步"监听，走的是 `App.rootContext`——而 `rootContext` 内部是 `rootNavigatorKey.currentContext!`，**`--headless` 从不 `runApp`，没有 navigator context**。这个定时器在命令主体之外触发，异常直接把进程打断，表现就是"命令跑着跑着没动静了"。

修复：改用 `App.rootNavigatorKey.currentContext` 判空，无窗口时跳过关窗监听（对 headless 本就无意义）。

> 教训：headless 命令要防的不止是自己写的代码，**`init()` 链路里任何依赖 UI context 的副作用都可能成为定时炸弹**。这是本次补入口时连续踩到的第三个坑（前两个：轮换域 URL 过期、续传目录扫描过慢）。

## 十三、Diva 组 download-check 实测结果（headless 入口的真正价值）

用 `--chapter 6 --group DivaScans` 跑真实下载链路，**67 页成功落盘**（原目录为空），失败页分布：

```
5, 17, 19, 21, 23, 25, 27, 29, 31, 33, 35, 37, 39, 41, 43, 45,
46, 47, 49, 51, ... 115, 116, 118, 120, ... 130
```

**🔴 自我纠正**：第一眼看着像"奇数页系统性失败"，但做了奇偶计数后**这个判断是错的**：

| 组 | 偶数页 | 奇数页 | 合计 |
|---|---|---|---|
| Diva 第 6 话 | 32 | **35** | 67 |
| Asura 第 6 话（对照） | 64 | 64 | 128 |

奇数页其实**下得比偶数页还多**。真实形态是**均匀随机丢页**（成功率约 47%），失败页在 0~130 全域随机分布——与页号奇偶、与网络时序都无关。

这个纠正很重要：它说明 Diva 组不是"分片部署"这类结构性问题，而是**同一宿主对同一批请求的高比例随机拒绝**（可能叠加了单次签名 URL 的一次性消费）。因此：

- ❌ "换一组下标就能补齐"的思路不成立。
- ✅ 仍然值得试的：**换出口 IP / 代理**（若封锁含 IP 维度，重复下载即可提高成功率）、**多轮重试**（已验证有效：61→65→67 稳步回升）。
- ✅ 也可考虑用**同章的其他翻译组**（该话共 11 个组）。

多轮机制在此场景的行为完全符合设计：第 1 轮 5s 快速拿掉能下的页，后续轮次持续攻坚失败页，页数从 61 → 65 → 67 稳步推进，**全程没有出现"一张失败图卡满 30s"的冻结**——这正是本次改造的目的。

> 补记：后续几轮重试把该章推到 **145 页**，进一步印证"多轮 + 重复尝试确实能持续提高成功率"，只是无法保证 100%。

### 十四、🔴 headless 入口的第四个坑：残留任务占满队列

第 1 话能 3 秒通过、第 7 话却两次超时，查出原因是 `downloading_tasks.json` 里残留了 **3 个被强杀的任务**（含一个 `wasRunning=true`）。这些任务在下次启动时会被恢复并**占满 `maxParallelDownloads` 槽位**，新任务只能排队等着——headless 命令表现为"跑着跑着没动静"。

处置：清空残留任务后立即 `PASS (138/138 pages, 0 missing, 1539ms)`。

> 这是 headless 固有的使用约束（GUI 里用户会手动点暂停/清队列，CLI 没有）。**后续应给 `download-check` 加 `--clean`**，在跑之前清空残留队列，避免测试互相干扰。本次未加，先记为待办。

## 十五、`--clean`：解决残留任务堵死队列

### 问题

被 SIGTERM / 超时强杀的任务会留在 `downloading_tasks.json`，下次启动时 `restoreDownloadingTasks()` 恢复它们并占满并发槽位。`maxParallelDownloads` 现在默认 1，所以**只要有一个残留任务，本任务就永远排不上队**，只能干等墙钟超时。

实测就是这样：第 1 话能过（队列干净），随后两次跑第 7 话（138 页早已全部在本地）都超时——卡在排队而非下载。GUI 里有"取消全部"按钮，**命令行没有清队列的途径**。

### 方案

新增 `LocalManager.dropAllTaskRecords()`（`lib/foundation/local.dart:1005`）：

```dart
for (final t in downloadingTasks.toList()) {
  t.pause();                 // 停掉在途工作，但保留已下载的页
  downloadingTasks.remove(t);
}
saveCurrentDownloadingTasks();
```

🔴 **刻意不用现成的 `cancelAll()`**——`DownloadTask.cancel()` 会**删掉部分下载的章节目录**（`download.dart:177-188`）。那是 GUI"取消"按钮该有的语义，但会毁掉 CLI 已跑完的工作。`pause()` 只停工作不删数据。

headless 侧 `--clean` 在跑之前调用，清理数量记进报告的 `droppedStaleTasks` 字段。

### 用法与实测

```bash
venera.exe --headless download-check <comicId> --clean \
  --source comix_to --chapter 7 --group "Asura Scans" --json out.json
```

实测：人为注入 2 个假残留任务后运行 ——

```
{"status":"running","message":"Cleared stale download queue","data":{"droppedTasks":2}}
{"status":"success","message":"Download check PASS (138/138 pages, 0 missing, 1507ms)"}

passed = True / droppedStaleTasks = 2 / downloaded = 138 / total = 138
```

**数据零损失核验**（清理后）：`1 [Asura Scans]` 94 页、`7 [Asura Scans]` 138 页、`6 [DivaScans]` 145 页，全部完好。

构建 **BUILD_OK**。改动文件：`lib/foundation/local.dart`（新增 `dropAllTaskRecords`）、`lib/headless.dart`（`--clean` 开关 + 报告字段）。

## 十七、🔴 事故复盘：`6 [DivaScans]` 缺页静默损伤 + 翻译组分类 UI 消失

> 用户报告（2026-10-06）：
> 「本地下载的 `My Dragon Girlfriend Has Returned`，Diva 来源第 6 章，点过一次**修复**之后出问题：
> ① 文件夹里明明**缺了 `150.webp`**，但**没有红色缺页报错**；
> ② 章节栏里**理应出现的翻译组分类 UI 消失了**。多半是点了下载修复之后导致的。」
>
> 结论：**是两个独立的缺陷叠在同一本漫画上**（缺页账本漏记 + 章节矩阵被覆盖），
> 外加**一个新工具自身的 bug** 让第一次取证失败。三个都已修。

### 17.1 现场取证（三条独立证据链）

**① 磁盘：缺口是真实存在的，而且远不止 1 张。**

```
6 [DivaScans] : 145 个文件 / min 0 / max 176  → 应有 177 页，实缺 32 页
  空洞 = 33,41,47,55,63,72,76,84,88,96,108,115,121,126,130,134,138,142,
         146,150,153,155,157,159,161,163,165,167,169,171,173,175     （含用户看到的 150）
6 [Asura Scans]: 128 个文件 / 0..127 连续 / 0 空洞      ← 对照组，同话同源
1,2,3,4,5,7 [Asura Scans]                                ← 全部 0 空洞
```

**② 缺页账本：`missing_pages.json` 当时根本不存在。** 对账前 `missingBefore = 0`。
日志里只有一次修复记录：

```

ImageLane2 fetched 149332 bytes
```

而 `6 [DivaScans]/5.webp` 的 mtime 正是 `22:04:38` —— 说明当时表里**只有 index 5 一条**，
"修复"补回的就是它。其余 32 个洞**从来没进过表**。

文件 mtime 分三批（`20:17–20:19` / `20:25` / `20:34–20:37`）→ 这一章被**多次独立下载**过，
每一次都在"末轮落盘"之前就结束了。

**③ `local.db`：章节矩阵已经退化，而且和 `downloadedChapters` 分属两个翻译组。**

| 字段 | 内容 | 数量 |
|---|---|---|
| `chapters` | ch1–ch6，**全部是 DivaScans**（第 7 话整个消失） | **6** 个版本 |
| `downloadedChapters` | 7 条，**全部是 Asura** 的 chapter URL | **7** 条 |
| 二者交集 | — | **空集** |
| `details_cache.db`（源侧实况） | ch1–ch4 各 11 组、ch5/ch6 各 10 组、ch7 2 组 | **66** 个版本 |

源侧 11 个组：`Asura Scans` / `DivaScans` / `Genz Toons` / `Lagoon Scans` / `Luster Scans` /
`MadaraScans` / `MistScans` / `Nyx Scans` / `QI Scans` / `Thunderscans` / `Vortex Scans`。

### 17.2 根因 A：缺页账本只在**末轮**落盘 → "既缺页又不报错"

`ImagesDownloadTask._downloadChapterPool` 跑 4 轮渐进超时（预算 `[5,10,15,30]s`），
**只有末轮（第 4 轮）失败页才写 `missing_pages.json`**。

于是任何在末轮之前结束的运行（用户取消 / 崩溃 / 只跑了两轮就补上了别的东西），
整章的失败页会同时满足三个条件：

- 磁盘上没有 → 阅读器打不开；
- 表里没有 → 不画红色缺页标记、不进"修复"目标；
- 章节状态还被判成 `downloaded`（`LocalManager.getComicStatus` 只看目录里"有没有东西"）。

➡️ **用户看到的就是"缺了 150 但一片祥和"。** 而"修复"按钮的目标集来自缺页表，
所以点一次修复**永远修不到那 32 页**——它根本不知道有这些页。

### 17.3 根因 B：`add()` 的 `INSERT OR REPLACE` 把 66 个版本冲成 6 个 → 翻译组 chips 消失

`LocalManager.add()`（`completeTask()` → `task.toLocalComic()` 的**唯一入口**）分两条腿写法不同：

```dart
var downloaded = { ...comic.downloadedChapters, if (old != null) ...old.downloadedChapters }.toList();  // ← 并集
...
'INSERT OR REPLACE INTO comics (… chapters …) VALUES (…)', jsonEncode(chapters ?? comic.chapters)   // ← 整行覆盖
```

- `downloadedChapters` 走**并集** → Asura 的 7 条 key 活了下来；
- `chapters` 走**整行覆盖** → 被"这次任务自己的（按组过滤后的）矩阵"替换成只剩 DivaScans 的 6 个版本。

🔴 这就是"翻译组分类 UI 消失"的直接原因：**详情页的组 chips 需要 2 个以上组才渲染**，
退化成单组后整行分类凭空消失。第 7 话也一起丢了。

而且两条腿现在**描述的是两个不同的翻译组**（`chapters` = DivaScans、`downloadedChapters` = Asura），
交集为空 —— 于是任何"用 `downloadedChapters` 反查目录名"的逻辑都必然查不到磁盘上真实存在的目录。

### 17.4 根因 C：新工具自己的 bug —— `entity.uri.pathSegments.last` 对**目录**恒为空

新增 `page-reconcile` 第一次跑出来是 `{"chapters":[]}`、`0 gaps`，看着像"源选错了"，
实际是两个叠加的坑：

1. **`Directory.uri` 必带结尾斜杠** → `pathSegments.last` 是 `''`，
   而循环里紧接着就是 `if (dirName.isEmpty) continue;` → **每个目录都被跳过了**，报告恒为空。
2. 就算不空，**段是百分号编码的**：`6 [DivaScans]` → `6%20%5BDivaScans%5D`，
   直接拿去和 `chapterDirectoryName(...)` 比对必然不等 → 缺页表的 `chapterId` 也会写错。
3. 我第一版还犯了个方向性错误：按 `downloadedChapters` 推导目录名。
   而 `6 [DivaScans]` **不在** `downloadedChapters` 里（从没走完 `completeTask`），
   按登记表推断永远看不见它 —— 正是 17.3 那个"两条腿不同组"的直接后果。

➡️ 修法：改用本仓库已有的扩展 `FileSystemEntityExt.name`（＝`p.basename(path)`，
`lib/utils/io.dart:41`），并**一律扫描磁盘上的章节目录**而不是登记表。

⚠️ 同样的写法在 `LocalManager.reconcileMissingPages` 里也抄了一份，**同一个 bug 两处**。
（另有两处 `entity.uri.pathSegments.last` 在 `download.dart` / `_pageIndexesIn`，
但它们前面都有 `if (entity is! File) continue;` —— **文件** URI 没有结尾斜杠，所以是安全的。
**教训：这个写法对文件安全、对目录致命，抄的时候看不出来。**）

### 17.7 教训

1. **"账本"不能只在成功的终点写。** 只在末轮落盘＝把"取消/崩溃"的语义定义成"什么都没缺"。
   凡是"失败记录"，写入门槛必须低于"任务完成"。
2. **真相要落在不可伪造的载体上。** 页文件名是下载器自己按 `0..n-1` 生成的，
   `{0..max}` 的空洞**离线即可判定**，不需要联网、不需要信任任何登记表。磁盘 > 内存 > 数据库。
3. **`INSERT OR REPLACE` + 多来源写入 = 静默数据丢失。** 只要有一个"视图更窄"的写入源，
   整行就会退化。要么每条腿各自写各自的列，要么显式加"只增不减"守卫。
4. **`downloadedChapters` 与 `chapters` 是两条腿，可能不同组。** 任何"用 A 反查 B"的逻辑
   都要假设它们**不一致**。这次事故里，正是这个假设的缺席让缺页和组分类一起消失。
5. **`entity.uri.pathSegments.last` 对目录永远是空串，且段是百分号编码的。** 用 `entity.name`。
6. **离线判据有边界，必须写在文档里**：`pageIndexGaps` 只能发现**内部与头部空洞**；
   **尾部截断**（最后几页没下完、目录里也没有更大的下标）**无法离线判定** ——
   那需要联网取章节页列表比对，是 S12 的事（见 §六 遗留）。

### 17.8 续（10-07）：登记表侧的同一性质缺陷 —— 详见 `docs/P8.1` §十二～§十六

§17 只修了**缺页表**这一条腿。用户随后又发现**另一半**："`6 [DivaScans]` 修复后磁盘 177 张齐全，
下载页却显示 `Ch.6` 未下载、卡片也不上蓝"。根因同源但对象不同：

- `downloadedChapters`（`local.db`）是 **UI 的唯一判据**（章节配色 / 下载页勾选框 / 阅读器列表 /
  `preferDownloaded`），但它**只有 `completeTask()` 一条写入路径**；
- `RepairDownloadTask` **按设计不写**这一列（`toLocalComic()` 返回 `downloadedChapters: const []`）；
- 而 `6 [DivaScans]` 当初是**半截下载**，从没走过 `completeTask` → 它的 key 从来没登记过。

**修法与 §17 同源：磁盘 > 数据库。** 新增 `LocalManager.reconcileDownloadedChapters()` 与
`reconcileDiskState()`（一次扫描同时补两张表），在 `completeTask()` / `RepairDownloadTask._finalize()`
（**都在 `removeTask` 之后**，否则 `isDownloading` 守卫会让对账静默空转 = `return 0`）/
详情页三处调用。实测 `downloaded_7 -> 8`、`6 [DivaScans] registeredBefore=false → registeredAfter=true`。
