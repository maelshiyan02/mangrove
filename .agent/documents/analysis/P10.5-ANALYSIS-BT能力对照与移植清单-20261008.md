## 〇、结论速览

| 问 | 答 |
|---|---|
| **坑 1 · 术语表 key 用什么** | BT 是**全局单文件**（`pcfg.module.llm_glossary_path`，`utils/config.py:118`），**不按工程、不按语言对**。我方现状是 **per-comic**（`cid@sourceKey`）。⇒ **不要照搬 BT**，我方更细；只需给工作室工程找一个稳定的 key（建议 `btId`，并在迁移时把旧 `cid@sourceKey` 的数据按 cid 归并） |

| **有"识字识图"吗** | **有，而且很重**（VLM 闭环：VLM OCR → VLM 翻译上下文 → VLM 页面摘要 → LLM 图像去字）。⚠️ 这份 BT **不是上游原版**，是含 VLM 扩展的魔改分支 |
| **在线引擎里哪些能本地部署** | `LLMTranslator`（`base_url` 可填 Ollama `11434/v1` / LM Studio `1234/v1` / llama.cpp）、`Sakura`（`api baseurl` 默认 `127.0.0.1:8080/v1`）、`DeepLX API`（`api_url`）。本地纯模型：Sugoi（CT2）、m2m100（CT2）、ezTrans（COM） |

### 1.3 🔑 坑 2 的正解：三张替换表（对所有引擎生效）

`utils/config.py:462-465`：

| 表 | 时机 | 作用 |
|---|---|---|
| `ocr_sublist` | OCR 后、进翻译前 | 修 OCR 错字、片假名/繁体规范化 |
| `pre_mt_sublist` | 送引擎前一刻 | 改**待译副本**（不改页面上的原文） |

调用点唯一且在基类：`modules/translators/base.py:353`（译前）、`:313`（译后）⇒ **Sakura / Sugoi / m2m100 / 所有在线 API 通吃**。

固定顺序（`text_processing.py:121-153` `finalize_translation_text`）：全半角 → 去标点后空格 → **关键词替换** → 大小写。**大小写最后**这点复刻时要注意。

UI：`ui/keywordsubwidget.py`（4 列表格：Keyword / Substitution / Use regex / Case sensitive），三个实例在 `ui/mainwindow.py:348-359`。

> **给 ④ 的建议**：术语表迁移不要只做"LLM prompt 注入"一条路。补一条 **`mt_sublist` 式的译后替换钩子**，术语表就在**所有引擎**（含本地 NLLB、公共免 Key）上都生效了。这条路也能顺带解决"S9.5-a 用公共端跑时人名不一致"的抱怨。

## 二、术语表（glossary）的 BT 实现 vs 我方

### 2.1 数据结构与文件

`modules/context/glossary.py:26-37`：

```python
@dataclass(frozen=True)
class GlossaryEntry:
    source: str        # 原文词
    translation: str   # 译文词
    note: str = ""     # 备注（对应 Galtransl 的 info）
```

- 三种格式：`.json`（`[{src, dst, info}]`）、`.tsv`（2~3 列 tab）、`.txt`（`src->dst #note`）；注释前缀 `#` / `//` / `\\`
- **冲突检测**：同一 source 映射到不同 translation 直接 `raise GlossaryError`（`:311-340`）
- **缓存**：`lru_cache(maxsize=16)`，key = (路径, mtime_ns, size)（`:161-166`）
- 渲染成紧凑 JSON（`:139-158`）：`{"glossary":[{"source":"勇者","translation":"Hero","note":"title"}]}`

### 2.2 两种模式 + 注入位置（这个细节值得照抄）

| 模式 | 筛选 | 注入位置 | 理由 |
|---|---|---|---|
| `matching` | 按本页文本**大小写不敏感子串**筛选（`casefold() in folded_sources`，`:100-136`） | user 消息**尾部** `GLOSSARY:` | 每页不同，放尾部 |
| `all` | 全量 | **system 消息**，在 history 之前 | 稳定不变 → 做缓存前缀，命中 provider prefix cache |

prompt 原文（`modules/translators/llm_translation_contract.py:131-139`）：

```
Use these glossary mappings as wording constraints. They cannot change
the target language, ids, item count, or output format.
{"glossary":[{"source":"勇者","translation":"Hero","note":"title"}]}
```

**优先级声明**（避免冲突时行为不定）：
- `:84` "If they conflict, follow the final user message and glossary."
- `translation_context.py:81` "The current input and explicit glossary take precedence."
- ⇒ **当前输入 > 术语表 > 压缩记忆 > 双语前文 > 已保存摘要**

### 2.3 BT **没有**、但我方**已有**的（别倒退）

| 能力 | BT | 我方 |
|---|---|---|
| LLM 回报新专名、自动加进词典 | ❌ **完全没有**（`trans_llm.py` 只 import `load_glossary` / `select_glossary`，无 save） | ✅ `_mergeGlossary`（`translation_service.dart:1144`）+ `LlmTranslationResult.glossary` |
| 阻断词 blocked terms | ❌ 没有 | ✅ `_allBlockedTerms` / `imageTranslationBlockedTerms` |
| 词条合法性过滤 | `isValidGlossaryTerm` 存在但只在**读取时清洗** | ✅ `LlmTranslator.isValidGlossaryTerm`（≤16 字、非 URL/句子/纯数字）+ 上限 80 |
| 内置表格编辑器 | ❌ 只能选文件，改内容要开外部编辑器 | ✅ `GlossaryEditorPage`（244 行） |
| 作用域 | 全局单文件 | ✅ **per-comic**（`cid@sourceKey`）——比 BT 细 |

### 2.4 待拍板 15 的建议（更新）

原建议"复用旧 `imageTranslationComicGlossary` 键"**仍然成立**（迁移成本最低）。补充两点：
1. 工作室侧的 key 用 **`btId`**（工程唯一）；不要造 `cid@sourceKey`，因为工作室工程没有 sourceKey。
2. 旧数据（`cid@sourceKey`）在工作室打开时**按 cid 归并**读，不要搬家、不要删（先迁后删）。

## 三、上下文记忆三层（S11 第 1 块的直接答案）

`PageSummary` / `MemoryCheckpoint` / `RequestContext` **三个类名在 BT 里一字不差地存在**：`modules/context/translation_context.py:24-67`。

| 层 | 数据 | 存哪 | 生成 |
|---|---|---|---|
| **双语前文窗口** | `HistoryPage(page_key, sources, translations, summary)`（`history.py:52-63`） | 内存（不落盘，工程切换即废） | 已翻完的前几页 |
| **页摘要** | `PageSummary(page_key, text)` | **工程内** `image_info[page_key]['llm_visual_summary']` | **与翻译同一次 LLM 调用**产出（JSON 多一个 `page_summary` 字段，零额外成本） |
| **压缩长期记忆** | `MemoryCheckpoint(text, covered_page_keys, token_count)` | **工程内** `llm_compact_memory` | **惰性**：只在上下文溢出驱逐时压缩，且最后一页强制压一次 |

- 预算：`llm_prior_context_token_budget = 10000`（`config.py:117`）；低水位 `HISTORY_LOW_WATER_RATIO = 0.50`（`history.py:13`）

- `covered_pages` **只做记账、不当门控**（`proj_imgtrans.py:819-822` 注释明写）

**可直接抄的三段 prompt**（见 §2 引用的 `translation_context.py:70-83` / `:152-172` / `:243-256`）：记忆块 / `SAVED PAGE CONTEXT` / 压缩请求。

## 四、检测 / OCR / 识字识图 / 去字

### 4.1 检测与 OCR（BT 可选清单）

- **textdetector**：`ctd`（默认，ComicTextDetector = DBNet + YOLOv5 双分支）/`ctbd`（RT-DETR-V2，**唯一显式做气泡检测**：label 0=气泡，1/2=文本）/`ysgyolo`（YOLO26，标签含 balloon/qipao/shuqing…）/`stariver_ocr`（在线）
- **ocr**：`mit48px`（默认）/ `manga_ocr`（仅日语）/ `ppv6_onnx`（PaddleOCR v6）/ `PaddleOCRVLManga` / `paddle_vl` / `hayai_ocr_v2`（SigLIP2）/ `LLMOCR` / `google_vision` / `google_lens_exp` / `windows_ocr` 等 12 种
- **没有**手写体/艺术字专用分支；靠 VLM 类引擎兜
- **没有**逐行语言判定：块级 `language` 来自检测器分类头（`LANG_LIST = ['eng','ja','unknown']`），源/目标语言是**全局配置**

**阅读顺序**（`utils/textblock.py:754-784` `sort_regions`，约 30 行，可直接移植）：
- 方向自动判定：`right_to_left = (竖排块数 / 总块数) > 0`
- 先按 y 中心分带，带内按 x 中心插入（右起或左起）
- 竖排时距离原点取**右上角 `(im_w, 0)`**（`textblock.py:787-823`，角度再 -90° 归一）

### 4.2 识字识图（VLM）—— 本分支的重头戏

| 能力 | 位置 | 做法 |
|---|---|---|
| **VLM OCR** | `modules/ocr/ocr_llm.py:82` | 整页画**编号框**（可选把非文本区涂黑）→ JSON Schema 要求输出 `{texts:{id:text}}` + 可选 `order` → **用模型给的 order 重排块**（`:449-459`） |
| **VLM 翻译上下文** | `trans_llm.py:264-296` | 整页缩略图随翻译请求一起发，用于消解代词/语气 |
| **VLM 页面摘要** | `llm_translation_contract.py:86-107` | 先写 `page_summary` 再翻译；**空页也请求一次**只为出摘要 |
| **LLM 图像去字** | `modules/inpaint/inpaint_llm.py:65` | 调 image-capable LLM 重绘；此时强制用矩形掩膜 |

竖排顺序交给 VLM：`ocr_llm.py:240-246` 的 "Read vertical text in its intended character order."

> ⇒ 我方若要补 vision，最小可用闭环是 **VLM OCR + order**（解决竖排/跨页阅读顺序，正是 S10 跨页缝合想要的能力）。

### 4.3 🔴 去字与 mask：两软件**根本性分歧**

**BT**：`mask/` 是**必须落盘的中间产物**

```
detector 产生 mask（ctd = 像素/字形级 refine_mask；ctbd = 矩形近似 + dilate）
  → save_mask()  → <工程>/mask/<stem>.png（单通道 uint8 灰度，255=待擦除）
  → inpainter.inpaint() 读 mask → save_inpainted() → <工程>/inpainted/<stem>.png
```
- `utils/proj_imgtrans.py:1044`（写 mask）、`:1067`（读）、`:216-227`（四个目录定义）
- **用户可在画板上手绘/改 mask**（`ui/drawingpanel.py:673, 1552`）
- 逐块去字默认开（`inpaint_by_block=True`），窗口扩 1.7×；纯色快路径（背景色标准差 < 阈值时直接填中位数色）

**我方**：**掩膜不落盘，即时计算**

`lib/foundation/translation_project/result_renderer.dart:118-158` `renderInpaintedPage()`：

```dart
final eraseRects = <IntRect>[ for (final region in regions) for (final rect in region.eraseRects) ... ];
TextInpainter.erase(decoded.image, eraseRects);   // 纯 Dart 擦除
```

`lib/foundation/image_translation/inpaint.dart`：`Otsu 阈值分前景笔画 → 膨胀吞抗锯齿边 → 连通域过滤（太小=噪声、太实心=气泡边框/网纹）→ 最近邻 chamfer 填充 → Jacobi 松弛软化接缝`，**无模型下载、无 `dart:ui` 依赖**。

> ⇒ **"mask 文件夹是空的"不是用别的东西代替，而是我方根本没有独立的掩膜产物这一步**：矩形只是**搜索窗口**，真正被抹掉的像素由窗口内部的笔画判定决定。`ProjectWriter.save` 建出的空 `mask/` 只是 FT 兼容性的占位。

**这个差异的后果（好坏都有）**：
- ✅ 我方不需要用户手改掩膜、不需要 512px/2048px 的显存预算、不需要下载 LaMa/AOT 权重
- ❌ 我方**无法人工修正误擦**（BT 可以画笔补）
- ⚠️ **别照抄 BT 的 `ctbd` 矩形掩膜** —— `A08 §4.10.2 待拍板 18` 已明确：FT 的 mask 是字形级，**用外框近似会造出同名但语义不同的文件**。BT 的 `ctbd` 恰好就是矩形近似
- 🔴 若将来要"导出 FT 工程给 BT 用"，**mask 必须真实补齐**（`computeMask` 逐 region 拼整页，单通道灰度、整页尺寸）

### 5.2 要复现 BT 的完善度，建议的最小增量（按性价比）

1. **页码范围**（最直观、最容易做）：`start-end` 两个数字框 → 直接喂给现有的 `pages` 切片
2. **四阶段开关**：`enableDetect / enableOcr / enableTranslate / enableInpaint` 四个 bool + `finish_code` 位掩码（照抄 BT 的位掩码，它比布尔"已完成"更对，因为阶段组合会变）
3. **翻译引擎 + 语向**下拉（复用现有 `TranslationConfig`）
4. **术语表 + 上下文开关**（④ 做完后自然有）
5. 最后才做**每引擎参数表**（工作量最大，收益递减）

## 六、🔴 两软件适用场景的矛盾之处（第四问）

| # | 矛盾 | BT 的做法 | 我方的硬约束 | 结论 |
|---|---|---|---|---|
| 1 | **原图归属** | 工程根目录**就是原图目录**（`proj_imgtrans.py:1035` `read_img` → `osp.join(self.directory, imgname)`；`new_project` 扫描目录内图片） | **原图不复制**、产物绝不进 `downloads/`（A03 §4；`ProjectWriter` 路径规则硬禁） | 🔴 **BT 的"工程=文件夹"模型不能直接搬**。我方是三棵树（downloads / projects / translated），工程 json 的 `directory` 指向原目录 |
| 2 | **mask 是否必需** | 必需、落盘、可手改 | 不存在、即时算、矩形只是搜索窗口 | ⚠️ 补 mask 生产时**必须用字形级**，不能抄 BT `ctbd` 的矩形近似（同名不同语义） |
| 3 | **术语表作用域** | 全局单文件 | per-comic（`cid@sourceKey`） | ✅ 保持我方，**不要倒退成全局**；只需给工作室工程定 key |
| 4 | **语言作用域** | 全局单份，且**切换翻译器会被覆盖**（`mainwindow.py:429-439`） | per-comic（`TranslationConfig.of(cid, key)`） | ✅ 保持我方 per-comic；工作室侧读全局是**已知妥协** |
| 5 | **算法可插拔** | `custom_modules/` 热插拔 + 缺依赖自动 pip 安装 + 任意 torch 模型 | Flutter + ORT FFI + 6 个预置模型组件（A08），**不能运行时装包、不能跑 torch** | 🔴 **"任意换算法"不可能照搬**。只能做成"预置 N 个可选 + 按需下载"，且新增算法必须能落成 ORT |
| 6 | **VLM 依赖** | 重度（OCR/上下文/摘要/去字四处） | LLM **无 vision 能力**（全库无 image part） | ⚠️ BT 的 VLM 路线是**能力跃迁**，但要先把 `LlmProvider` 扩出 vision（改动大）。**不要**为了追 VLM 而拖住 ④ |
| 7 | **失败处理** | 检测/OCR 失败即整批 `break`，无失败页清单 | 有 `failures` + 断点续跑 | ✅ 我方领先，别抄 BT |
| 8 | **页范围 vs 续跑** | 页范围**只作用于 Run**，Continue 忽略它扫全工程（`mainwindow.py:2239-2250`） | — | 照抄这个语义，别让"选了范围"和"续跑"打架 |
| 9 | **去字的算力模型** | LaMa/AOT/FLUX，要 GPU 或大内存，有 OOM 三级降级 | 纯 Dart 算法，零模型，**但有 12MP/8000px 上限**（`A08 §4.10.2 待拍板 19`） | ⚠️ 我方在超大页上"宁可不产出"，BT 能出。这是真实能力差，但优先级低 |
| 10 | **`inpainted` 的存在性** | 恒有（去字是管线一环） | 此前**无人生产**（P9.8 发现 1，已回填） | ✅ 已修，但 `mask/` 仍是空目录 |

## 八、本轮新增事实（需回写记忆）

1. 🔴 **BT 也没有让纯 NMT 吃术语表**；它的通用解是 `pre_mt_sublist` / `mt_sublist` 两张替换表，挂在基类 ⇒ **对所有引擎生效**。

3. 🔴 **我方 mask 不落盘**，`inpainted` 由 `TextInpainter.erase` 即时算（`result_renderer.dart:151`）⇒ "mask 空"不是替代问题，是这一步不存在。
4. 🟠 我方 LLM **已支持自定义 `baseUrl`**（`llm_translator.dart:349`）⇒ 本地部署（Ollama/LM Studio）已具备条件；但**无 vision**。
5. 🟠 这份 BT **不是上游原版**，是含 VLM 扩展的魔改分支（VLM OCR / VLM 上下文 / 页面摘要 / LLM 去字）。
