## 1. `downloads\Error the Echo` 导入为什么失败 —— 两个独立阻塞点

日志（`logs.txt:373-380`）给出了完整答案：

```
info  Import Comic 14:04:32  Comic already exists: Error the Echo
error Import Comic 14:04:43  FormatException: Invalid radix-10 number (at character 1)
                                  bt_5be94984
                                  ^
                                  #4 LocalManager.findValidId (local.dart:516)
                                  #5 ImportComic.registerComics (import_comic.dart:446)
```

| # | 阻塞点 | 位置 | 性质 | 已修 |
| --- | --- | --- | --- | --- |
| ① | **重名守卫把工程卡当成"已存在的漫画"** | `local_comic_scanner.dart:42` → `findByName` | 语义错：导入的行 id 都是 `findValidId` 发的**纯数字**；`bt_…`（FT 工程）/ `ft_…`（已发布译文）是**从漫画派生出来的**，不是漫画本身。工程卡的 `title` 恰好等于源漫画标题，于是导入被自己的工程挡下 | ✅ 新增 `findImportedByName()`（`id GLOB '[0-9]*'`），扫描器改用它 |
| ② | **`findValidId` 对非数字 id 直接崩** | `local.dart:504-517` | **既有潜伏 bug**：SQL 用 `ORDER BY CAST(id AS INTEGER)`，SQLite 把 `'bt_5be94984'` CAST 成 **0**，于是它排最后；库里有它且没有别的 local 行时，`int.parse('bt_5be94984')` → `FormatException`。**任何 `bt_` 卡都会让下一次文件夹导入崩掉** —— 与 S7 无关，但 S7 让它显形了 | ✅ SQL 加 `AND id GLOB '[0-9]*'`，并把 `int.parse` 换成 `int.tryParse` 兜底 |

> **教训**：`findValidId` 假设"id 永远是数字"，而 `bt_`/`ft_` 打破了它。派生型 id 的引入者（`BtProjectManager`、`FinishedExport`）与消费者（导入流程）之间**没有契约**。这次是同一个库里第一次同时存在数字 id 和前缀 id。

**修复后你应能正常导入** `downloads\Error the Echo`（97 张 webp + cover，扫描器判定通过）。

## 2. 合集 UI：章节下方的「翻译版」缺翻译组标签

### 2.1 结论：数据**已经在库里**，只是没人读

`ComicChapters.toJson()`（`models.dart:607-612`）**完整序列化版本化结构** `{话号: [{group, lang, title, key}, …]}`，`fromJsonOrNull` 能还原；`LocalComic.toJson/fromRow` 原样往返 `chapters`；下载时 `download.dart:977` 是 `chapters: comic?.chapters` **原样落库**。

→ **翻译组信息在 `local.db` 的 `chapters` 列里，不需要文件名标记，也不需要新的边车文件。**

### 2.2 但导入的漫画会丢

`local_comic_scanner.dart:128` 给导入的漫画建的是**扁平** `ComicChapters(Map.fromIterables(章名, 章名))` → 没有任何组信息。

| 来源 | `chapters` 内容 | 组标签能否显示 |
| --- | --- | --- |
| **网络下载** | 版本化（含 group/lang/key） | ✅ 可以 |
| 纯本地导入 | 扁平（只有章名） | ❌ 不可能 |
| BT 扫描注册的 `bt_` 卡 | 扁平（`chapters: null`） | ❌ |

**所以你的判断是对的**：本地的 `Error the Echo` 是"没带翻译组信息下载的旧文件"，只能重下。

### 2.3 方案（复用现成 UI 代码）

详情页章节区**已经**有翻译组 chips：`chapters.dart:559-584 _buildScanlationGroupChips()`（`FilterChip` + `chapters.scanlationGroupsSorted`）。合集/译文标签直接复用这套视觉与筛选逻辑即可，不另造。

需要的改动只有一处：`LocalComic` 侧提供一个 `groupAt(ep)`（版本化时取该话**首个版本**的 group），详情页在章节行/译文 tab 旁渲染它。

## 3. 下载选章器"显示不全" —— 根因是**模型的一维投影**，不是 UI 漏了

### 3.1 证据

下载侧栏 `_SelectDownloadChapter`（`comic_page.dart:1997-2085`）吃的是：

```dart
_SelectDownloadChapter(
  details.chapters!.titles.toList(),   // ← 折叠后的一话一行
  …
  chapterGroups: [ … scanlationGroupAt(i) … ],   // ← 每行取首个版本的组
)
```

而 `ComicChapters` 的 `ids` / `titles` 在版本化模式下**只 yield `versions.first`**（`models.dart:807-828`）：

> 一个话号下有 N 个翻译组 → `ids` 只给 1 个（最新的那个），**其余 N-1 个被丢弃**。

截图完全对上：详情页 11 个组、7 个话号 → 选章器只有 **Ch.1–Ch.6** 六行、组全是 `DioScans`（每话首个版本恰好同组）。

### 3.2 更严重的后果：目录名碰撞

`download.dart:294-300 _chapterDirectoryName()`：

```dart
final parsed = parseChapterTitle(chapterKey);
final dirName = parsed.chapterNumber?.toString() ?? chapterKey;
```

**只用话号**。若同一话下载了两个组，二者都写进 `downloads/<漫画>/6/` → **页面互相覆盖，且 `downloadedChapters` 只记一个 `6`**。这是真正的数据损坏风险，也是"必须带组信息重下"的技术根据。

### 3.3 方案：新增"版本矩阵"投影

给 `ComicChapters` 加一个**扁平化版本列表**（不改变既有 `ids`/`titles` 语义，避免波及阅读器与历史键）：

```dart
/// 话号 → 该话的全部版本，按 (组名, 上传时间) 稳定排序。
List<({String chapterNumber, ComicChapterVersion version})> get allVersions;
```

下载侧栏改成：
- 按**翻译组**分节（`scanlationGroupsSorted`，含"未分组"兜底），
- 每节可**折叠/展开**，标题为 `组名 (该组作品数)`，
- 每行勾选的是 `version.chapterKey`（**不是索引**），
- 全选/全不选作用于**当前可见（展开）的组**。

这样一次性解决：显示不全、无法按组选、需要计数、需要折叠 —— 四个要求同源。

## 4. 命名带标记 vs 额外元数据 —— 结论

| 用途 | 需要额外标记吗 | 理由 |
| --- | --- | --- |
| **UI 显示组标签**（合集/详情页/下载栏） | **不需要** | 版本化 `chapters` 已在 `local.db`；`.tl` 无关 |
| **不丢数据**（同话多组并存） | **需要目录可区分** | 这是"允不允许并存"的决策，不是"怎么标记"的决策 |

**推荐路线（两步走）**：

1. **默认一问一组**（本轮不做存储改动）：下载侧栏每话只允许选**一个**版本 → 目录名 `6/` 永不变 → **零碰撞、零迁移、向后兼容**。这已经满足"我要一个带组信息、能喂给 FT 的干净素材"。
2. **"同话多组并存"作为显式开关**（将来）：开启时章节目录改为 `6 [DioScans]/`。仍然满足"章节目录只含图片"（扫描器兼容），排序也正常。**注意绝不要把组名编码进每个图片文件名** —— 那才是真正的冗余灾难（97 个文件全部改名，且每次改组都要重命名）。

配套的边车（P6 §2.9(d) 已规划的 `chapters.json`）仍然值得做，但它的作用是**给导入的漫画补组信息**和**给成品库保留页键映射**，不是承载组名。

## 5. 合集编辑页能否加成员 —— 已有功能，缺入口

`comic_collection_edit_page.dart:391` 明确写着：

> "Long-press a comic in any list and choose 'Add to collection'."

**功能存在**（`components/add_to_collection.dart` → `ComicCollectionStore.addMembers`），但合集编辑页里**没有按钮**，只能长按漫画 → 选「添加到合集」。截图 3 证实了这一点。

**方案**：在合集编辑页的「N 部漫画」区加一个 **＋ 添加漫画** 按钮，行为与长按路径完全一致（复用 `add_to_collection.dart` 的选择器），成功后回填成员表。这是纯 UI 补齐，无新逻辑。
